# ETL 설계 문서

> **현재 상태: 설계 및 준비 단계.** 이 디렉터리에는 아직 실행 가능한 Python ETL 코드, 의존성 설정, 실행 명령이 없습니다. 아래 구조와 절차는 향후 구현 계획입니다.

## 역할과 목적

ETL은 공공데이터를 서비스 DB에 미리 적재하는 별도 배치 작업입니다. 웹 사용자의 분석 요청을 처리하지 않으며 API 서버로 동작하지 않습니다. 목표는 출처가 다른 원본 데이터를 검증 가능한 형태로 정리해 PostgreSQL/PostGIS에 반복해서 적재하는 것입니다.

RecycleYoungs는 점포 좌표와 서울시 상권별 매출·인구·개폐업 등의 데이터를 함께 사용합니다. 일부 자료는 CSV 다운로드 형태이고 데이터의 업종 코드, 기간, 공간 단위가 서로 다릅니다. 매 요청마다 CSV를 읽으면 같은 정제 작업을 반복하게 되고 분석 결과의 기준 시점을 관리하기 어렵습니다. 따라서 **공공데이터 → ETL → DB → Spring Boot API → React 화면**의 흐름을 계획합니다.

## Extract · Transform · Load

| 단계 | 예정 작업 | 확인할 결과 |
| --- | --- | --- |
| Extract | 수동 다운로드 파일 입력, 공식 파일 URL 다운로드 또는 공식 API 배치 수집을 출처별로 선택 | 원본 파일·응답, 출처 URL, 수집일, 기준 기간, 해시와 전체 범위를 기록 |
| Transform | 인코딩·열 이름·자료형 정리, 업종 코드 매핑, 날짜·분기 통일, 중복·결측·서울 밖 좌표 검사 | 유효 행·제외 행과 사유, 원본에서 정제 데이터로의 변환 규칙 |
| Load | 검증을 통과한 점포와 상권·분기 통계를 DB에 일괄 적재 | 재실행해도 중복되지 않는 적재, 건수와 실패 기록 |

상권별 집계값과 점포별 좌표는 다른 공간 단위입니다. ETL은 이 차이를 보존하고 상권 코드·경계와 점포 좌표를 혼동하지 않도록 합니다. 실제 CSV의 열과 단위가 확인되기 전에는 최종 테이블과 변환식을 확정하지 않습니다.

## 향후 Python 프로젝트 구조

다음은 **제안 구조**이며 `README.md` 외에는 아직 생성하지 않았습니다.

```text
etl/
├── README.md
├── pyproject.toml              # 예정: Python 버전과 의존성
├── .env.example                # 예정: DB 연결 등 비밀값을 제외한 설정 예시
├── data/
│   ├── raw/                    # 예정: 내려받은 원본, Git 제외
│   └── processed/              # 예정: 정제 중간 파일, Git 제외
├── src/
│   └── recycleyoungs_etl/
│       ├── sources/            # 예정: 출처별 입력 형식
│       ├── transform/          # 예정: 공통 검증·정규화
│       ├── load/               # 예정: DB 적재
│       └── pipeline.py         # 예정: 단계 실행 조정
└── tests/                      # 예정: 변환·적재 검증
```

실제 파일 구성과 Python 라이브러리는 원본 데이터 형식과 팀의 개발 환경을 확인한 뒤 정합니다. 현재 존재하지 않는 실행 명령은 문서에 제시하지 않습니다.

## 수집 및 적재 방침

최종 MVP에서는 서울과 선정한 3~5개 업종, 데이터 간 연결이 가능한 최근 4~8개 분기를 대상으로 합니다. **1차는 카페 한 업종·상권 2~3곳·공통 분기 하나의 매출·점포 자료부터 시작**하고 검증 후 공통 4개 분기와 다음 자료로 확대합니다. 개발 기간 중 수동 파일 적재부터 시작하고 자동 수집·정기 실행은 필요가 확인되면 도입합니다.

활용 예정 자료의 공식 링크와 목적은 [루트 README의 데이터 목록](../README.md#활용-예정-데이터와-공식-링크)에서 관리합니다. 점포 좌표, 기준 지역 경계, 추정매출, 점포·개폐업, 길단위·상주·직장인구, 집객시설, 상권변화지표를 검토합니다. CSV·공간 파일 ZIP·Sheet 내보내기·공식 API 등 출처별 제공 형태에 맞춰 수집할 계획이며, 실행 가능한 수집·정제·적재 기능은 아직 없습니다. 개별 파일의 사전 분석과 프로젝트 적재 완료는 구분합니다.

서울시 통계에는 표준단위구역 전환 및 제공기간 변경 안내가 있으므로 경계 코드·버전·통계 기간의 호환성을 먼저 검증합니다. 출처 간 업종 코드도 별도 매핑합니다. 원천 갱신 값이 여러 분기에 반복되는 인구 통계는 독립적인 신규 관측치로 처리하지 않습니다.

- 원본 파일과 정제 중간 파일은 코드와 분리하고 Git 추적에서 제외할 예정입니다. 현재 `csv_server/data/raw/stores.csv`는 기존에 추적 중인 샘플이며 이 문서 작성으로 이동하거나 삭제하지 않습니다.
- 적재 전 파일별 헤더·인코딩·단위·행 수를 확인하고, 제외된 행 수와 사유를 남길 예정입니다.
- 적재는 트랜잭션과 안정적인 식별자를 사용해 중간 실패와 중복 실행을 처리할 계획입니다. 적재 완료 시점과 데이터 기준 분기를 기록합니다.

### API가 없는 파일 전용 자료

**CSV만 제공되는 자료도 ETL의 정상 입력으로 지원할 계획입니다.** 팀원이 공식 사이트에서 파일을 내려받아 `data/raw/`에 보관하고, ETL이 해당 파일을 검증·정제·적재하도록 구현합니다. 이 경로와 파일 입력 기능은 아직 생성하지 않았습니다.

- 원본은 출처·기간·수집일을 구분해 보존하고 기존 파일을 덮어쓰지 않습니다. 출처 URL, 파일명, 파일 해시, 데이터 기준 기간, 다운로드일과 이용 조건을 기록합니다.
- 원본 형식별 입력 처리를 `sources/`에서 담당하고 공통 변환·품질 검사는 `transform/`, DB 적재는 `load/`에서 담당하는 구조를 계획합니다.
- 안정적인 공식 다운로드 URL과 이용 조건이 확인되면 파일 다운로드 자동화를 검토합니다. 로그인이나 수동 선택이 필요한 경우에는 수동 다운로드부터 유지합니다.
- 사용자 분석 요청은 적재된 DB를 조회하므로 파일 전용 자료를 위해 별도 API 서버나 사용자 CSV 업로드 화면을 추가하지 않습니다.

### 공식 API 자료와 함께 수집

공식 API가 제공되는 자료는 ETL이 인증키·요청 명세·기간 필터·요청 제한을 확인해 배치 수집하도록 계획합니다. 페이지별 응답과 전체 건수를 대조하고, 요청 실패를 재시도해도 중복되지 않도록 구현합니다. 인증키는 환경 변수로 관리하며 원본 보관 기록과 로그에 비밀값을 넣지 않습니다.

수집 방식과 원본 형식은 별도로 관리합니다. API의 JSON 응답과 사이트에서 내려받은 JSON 파일은 필드 대소문자나 바깥 구조가 다를 수 있으므로 입력 형식을 각각 확인합니다. 파일·API 모두 같은 내부 데이터 형식으로 변환한 뒤 공통 검증·적재 절차를 적용할 계획입니다.

## PostgreSQL/PostGIS 및 Spring Boot와의 관계

PostgreSQL은 점포와 상권 통계를 저장하고, PostGIS는 좌표·상권 경계와 공간 조회를 지원할 예정입니다. ETL은 확인된 좌표계와 위경도 순서를 지켜 공간 데이터를 적재합니다. DB 스키마와 변경 이력은 `backend/`의 마이그레이션으로 관리하는 방향이며, ETL은 그 스키마에 맞춰 데이터를 넣습니다.

**공용 DB 하나에 자료별 테이블을 둡니다.** 초기에는 매출·점포·인구를 서로 다른 DB로 나누지 않습니다. 자료와 기능이 늘면 같은 DB 안의 스키마로 임시 적재·서비스 조회 영역을 구분할 수 있습니다. 예정 테이블과 연결 기준은 [루트 README의 공용 DB 설계](../README.md#공용-db-하나와-자료별-테이블)를 따릅니다.

ETL 프로젝트도 하나로 유지하되 자료별 수집·변환 작업을 모듈로 나눕니다. 공통 DB 연결·검증·적재 이력을 공유하고, 갱신된 자료만 선택해서 처리할 수 있도록 설계합니다. 지역 기준 정보·업종 매핑 등 선행 데이터가 준비되어야 하며, 일부 자료만 갱신한 경우에도 다른 자료와 기간·공간·버전 호환성을 검증합니다.

`backend/`의 Spring Boot는 적재된 데이터를 조회하고 반경·상권 분석과 점수 계산을 수행하여 `frontend/`에 API로 제공합니다. 원본 파일 다운로드, CSV 정제, 대량 적재는 ETL의 책임입니다. 사용자 API 요청 중에 ETL을 실행하거나 원본 CSV를 읽지 않습니다.

공용 DB 구성은 향후 프로젝트 루트의 `docker-compose.yml`에서 RecycleYoungs에 맞게 새로 정의할 계획입니다. MVP에서는 DB만 Compose로 실행하고 Spring·React는 로컬 개발 서버, Python ETL은 구현 후 수동 배치로 실행합니다. 공용 DB 설정과 영속 볼륨·백업·복구를 검증하여 `csv_server/`에 대한 실행 의존성을 제거합니다. 자세한 계획은 [루트 README의 DB·Docker 구성](../README.md#dbdocker-구성-계획)을 참고합니다.

현재 `csv_server/docker-compose.yml`은 그대로 유지합니다. 루트 Compose·환경 변수 파일은 아직 생성하지 않았고, 이 문서 작성 단계에서 Docker 서비스나 ETL 컨테이너를 추가하지 않습니다.

## 실행 및 갱신 계획

초기 실행은 팀원이 데이터 파일과 DB 상태를 확인한 뒤 **수동 배치**로 진행할 예정입니다. 같은 자료를 다시 적재해도 결과가 중복되지 않도록 만들고, 자료가 갱신되면 출처·기준 분기·적재 시각을 확인해 재실행합니다. 스케줄러와 자동 다운로드는 MVP 이후 판단합니다. 현재는 실행 가능한 ETL이 없으므로 실행 명령도 없습니다.

갱신은 다음 절차로 구현할 계획입니다.

1. 출처별 새 자료 공개 여부를 확인하고 신규 분기 또는 기존 기간의 정정 자료를 확보합니다.
2. 파일 해시·기준 기간·기존 적재 이력으로 동일 입력인지 확인하고 중복 처리를 방지합니다.
3. 헤더·기간·단위와 행 수를 검증합니다. 형식이 바뀌면 변환 규칙을 수정하고 재검증합니다.
4. 신규·정정 자료의 반영 범위를 정해 적재하고 품질 검사를 통과한 데이터 버전만 서비스에 제공합니다.
5. 원본·이전 버전·변경 이력과 적재 결과를 보존하고 Spring이 기준 기간·최종 적재 시점을 제공하도록 연결합니다.

수집·적재 실패 시 마지막으로 검증된 서비스 데이터 버전을 유지합니다. 자료가 아직 공개되지 않은 분기를 임의로 채우지 않습니다. 파일 방식에서 API 방식으로 전환할 때에도 동일 기간의 식별자·건수·집계 결과를 비교해 데이터 의미가 유지되는지 확인합니다.

## 구현 계획

### 데이터 도입 순서

다음은 향후 구현 순서이며 현재 완료한 ETL 기능은 없습니다. 프로젝트 전체 순서와 완료 기준은 [루트 README의 구현 순서](../README.md#프로젝트-구현-순서)에서 관리합니다.

| 단계 | ETL 대상 | backend·frontend까지 확인할 결과 |
| --- | --- | --- |
| 1차 | 추정매출·점포/개폐업, 지역·업종 기준 정보와 적재 이력 | 상권·업종·분기 목록 선택 후 실제 DB의 매출·점포 조회. 한 분기 검증 후 공통 4개 분기 추세 |
| 2차 | 호환되는 상권 경계·개별 점포 좌표와 기관 간 업종 매핑 | 지도 좌표의 기준 상권 연결, 반경 경쟁 점포와 후보지 비교 |
| 3차 | 길단위인구 | 수요·고객 특성 표시와 첫 시연 |
| 4-1차 | 상주·직장인구 | 주거·직장 고객 기반 보완 |
| 4-2차 | 집객시설 | 시설 기반 접근성·집객 환경 |
| 4-3차 | 상권변화지표 | 변화 유형·영업 지속기간 설명 |

먼저 매출·점포 원본의 공통 키와 단위를 확인한 뒤 backend와 최소 스키마를 확정합니다. DB 마이그레이션 이후 파일 입력·변환·적재·재실행 검증을 구현하고 Spring 조회 결과를 대조합니다. 자료를 추가할 때마다 같은 순서를 반복합니다.

1차 또는 첫 시연 완료는 ETL 전환 전체 완료와 구분합니다. 합의한 최종 필수 자료와 품질·재실행·Spring 조회·공용 DB 재현 기준이 모두 충족된 후 기존 코드 정리를 진행합니다.
