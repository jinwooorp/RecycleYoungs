# RecycleYoungs

공공데이터를 바탕으로 서울의 창업 후보지를 비교하는 팀 프로젝트입니다. 서비스 가칭은 **“여기 창업해도 돼?”**입니다. 지도에서 위치, 업종, 분석 반경, 타깃 고객의 연령대를 선택하면 경쟁 점포와 상권 지표를 조회하고, 설명 가능한 규칙으로 계산한 창업 적합도와 근거를 보여주는 것을 목표로 합니다.

> **현재 상태: 기본 개발 환경 구축 및 데이터·ETL 설계 단계.** 분석 API, 실제 공공데이터 적재, 서비스 화면은 아직 구현되지 않았습니다. `etl/`에는 설계 문서만 있으며 실행 가능한 Python 기능은 없습니다. 아래의 목표 구조, DB 구성, API와 점수 정책은 구현 계획입니다.

## 서비스 범위

**MVP**

- 서울의 후보 위치 선택 및 경쟁 점포 지도 표시
- 업종 3~5개: 카페·한식·주점·헬스장·미용실 등을 후보로 삼고 원본 업종 코드 확인 후 확정
- 분석 반경 300m·500m·1km, 타깃 연령대 선택
- 데이터 간 연결이 가능한 최근 4~8개 분기의 추세
- 시장 수요·경쟁·성장성·고객 적합도·접근성, 종합점수와 근거 문장
- 동일 분석 조건으로 후보지 최대 3곳 비교
- 개발 기간에는 수동 데이터 수집·적재 1회부터 시작

**후순위:** 지역별 업종 추천, AI/머신러닝 예측, 실시간 동기화, 전국 확대, 수익 예측, 전체 서비스의 컨테이너 배포.

위 MVP는 단계적으로 완성할 최종 범위입니다. **1차는 카페 한 업종·상권 2~3곳·공통 분기 하나의 매출과 점포 통계 조회부터 시작**하고, 3차까지를 첫 시연 목표로 잡습니다. 종합점수는 필요한 자료와 계산식 검증이 끝난 뒤 추가합니다.

## 현재 구성과 역할

| 디렉터리 | 현재 상태 | 완성 방향 |
| --- | --- | --- |
| `backend/` | Spring Boot 프로젝트, 시작점·CORS·기본 테스트 | 서비스 API, 공간 조회, 분석·점수 계산, DB 마이그레이션 |
| `frontend/` | React + TypeScript + Vite 프로젝트, 기본 화면·API 프록시 | 지도, 분석 조건·결과, 차트, 후보지 비교 |

| `etl/` | Python 기반 ETL 전환을 위해 새로 생성한 디렉터리, `README.md`만 존재 | 별도 Python 배치 프로젝트로 구현 |

- [x] Spring Boot와 React 프로젝트 생성
- [x] `backend/`의 CORS 및 `frontend/`의 `/api` 개발 프록시 설정
- [x] `csv_server/docker-compose.yml`에 PostgreSQL/PostGIS DB 초안 작성
- [x] `etl/README.md`에 Python ETL 설계·준비 계획 작성
- [ ] 실제 공공데이터, DB 스키마, API, 서비스 화면 구현

기존 최상위 구조를 유지합니다. 서비스 API는 `backend/`, 화면은 `frontend/`에 구현합니다. `csv_server/apps/api`, `csv_server/apps/web`은 기존 실험 코드입니다.

현재 `csv_server/data/raw/stores.csv`는 Git에 추적된 소규모 샘플입니다. 매출 적재 코드는 미완성이며 `import-popilation.ts`는 빈 파일이고 `package.json`의 인구 적재 명령과 파일명도 다릅니다. 기존 스크립트를 완성된 공공데이터 파이프라인으로 취급하지 않습니다.

## 목표 아키텍처와 책임

```text
공공데이터 파일 / 공식 API
          ↓ 수집·검증·정제·배치 적재
        etl/ (Python)
          ↓
    PostgreSQL + PostGIS
          ↑ 조회·공간 분석
    backend/ (Spring Boot)
          ↑ /api 요청
 frontend/ (React + TypeScript)
```

| 영역 | 책임 |
| --- | --- |
| Python ETL | 원본 수집, 업종·기간·좌표 변환, 품질 검사, 대량 적재, 적재 이력 |
| PostgreSQL/PostGIS | 점포·상권 경계·통계 저장, 공간 인덱스와 공간 조회 |
| Spring Boot | 입력 검증, DB 조회, 공간 기준 적용, 점수·근거 계산, API 응답, 스키마 변경 이력 |
| React | 조건 입력, 지도·차트·결과 표시, 같은 조건의 후보지 비교 |
| 루트 Docker Compose — 예정 | 프로젝트 공용 개발 DB의 실행·영속 저장 설정 |

사용자 요청마다 원본 CSV를 읽거나 ETL을 실행하지 않습니다. 프론트엔드가 DB에 직접 연결하거나 점수를 별도로 다시 계산하지 않습니다.

### 데이터 도입 단계와 완료 기준

| 단계 | 구현할 기능 | 완료 기준 |
| --- | --- | --- |
| 1차: 기본 통계 조회 | 상권 목록에서 선택하고 업종별 매출·점포·개폐업 표시. 공통 분기 하나 검증 후 4개 분기의 추세로 확대 | 매출·점포 원본이 ETL → DB → Spring → React로 연결되고 원본 수치와 일치 |
| 2차: 지도·경쟁 분석 | 후보 좌표의 기준 상권 연결, 반경 300m·500m·1km의 경쟁 점포 표시, 최대 3곳 비교 | 호환 경계·업종 매핑을 검증하고 반경 통계와 공식 상권 통계를 구분해 표시 |
| 3차: 인구 기반 수요 | 길단위인구의 규모·변화와 확보 가능한 연령·시간대 특성 표시, 매출·경쟁·인구의 근거 문장 구성 | 같은 지역·기간의 자료로 수요와 고객 특성을 설명하며 첫 시연 가능 |

| 4-2차: 집객 환경 보완 | 교통·학교·병원 등 시설 통계 표시 | 시설 수의 기준 지역·기간·한계를 설명 |

1차에서는 지도·반경·연령대 입력과 종합점수를 구현하지 않습니다. 단계별로 확보된 원지표·추세부터 제공하고, 필수 지표와 계산식·정규화·가중치가 검증된 뒤 점수를 추가합니다. 최종 범위는 업종 3~5개·공통 4~8개 분기로 확대합니다.

원본을 미리 확보하거나 사전 분석한 자료가 있더라도 실제 기능 도입은 위 순서를 따릅니다. 단계별 다음 작업 순서는 [프로젝트 구현 순서](#프로젝트-구현-순서)에서 관리합니다.

### API·파일 제공 방식에 따른 수집

**공공 API가 없어도 CSV 파일을 내려받아 분석에 사용할 수 있습니다.** 자료별 제공 방식에 맞춰 ETL의 입력을 확보하고, 이후 검증·정제·DB 적재는 공통 절차로 처리할 계획입니다. 수집 방법은 데이터별로 선택하므로 API 자료와 파일 전용 자료를 함께 사용할 수 있습니다.

| 제공 방식 | 초기 수집 방법 | 향후 자동화 조건 |
| --- | --- | --- |
| CSV·JSON·공간 파일 ZIP만 제공 | 팀원이 공식 사이트에서 다운로드하여 ETL 입력으로 등록 | 안정적인 공식 다운로드 주소와 이용 조건이 확인되면 파일 다운로드 자동화 검토 |
| 공식 API 제공 | 인증키·요청 명세를 확인해 ETL에서 배치 수집. 초기에는 파일 내보내기 자료도 활용 가능 | 페이지별 수집, 요청 제한·실패 재시도·전체 건수 검증을 구현한 뒤 갱신 자동화 검토 |
| 파일·API 모두 제공 | 필요한 기간·항목·전체 범위를 확보하기 쉬운 방식 선택 | 방식 변경 시 필드·단위·기간·식별자와 집계 결과가 일치하는지 검증 |

서울시 데이터 상세 페이지에서는 데이터 정보 아래의 **`Sheet / Open API` 탭**에서 API 안내를 찾습니다. 예를 들어 [상권변화지표 OpenAPI 안내](https://data.seoul.go.kr/dataList/OA-15576/S/1/datasetView.do?tab=A)에서 인증키 신청과 샘플 URL을 확인할 수 있습니다. API 제공 여부와 응답 형식은 데이터별로 확인하며, API가 있다고 원본이 실시간으로 갱신되는 것은 아닙니다.

### 파일 전용 데이터의 보관·갱신 절차

다음은 **향후 ETL 구현 후 사용할 절차**이며 현재 파일 입력 기능이나 실행 명령은 없습니다.

1. 공식 사이트에서 필요한 지역·기간의 전체 파일을 다운로드합니다.
2. 예정 경로인 `etl/data/raw/`에 출처·기준 기간·수집일을 구분해 원본을 보관하고, 출처 URL·파일명·해시·이용 조건을 기록합니다. 기존 원본은 새 파일로 덮어쓰지 않습니다.
3. 파일별 인코딩·헤더·단위·기간·좌표계·행 수를 검증하고 출처별 변환 규칙을 적용합니다. 필요한 중간 결과는 예정 경로인 `etl/data/processed/`에 보관합니다.
4. 검증된 데이터만 DB에 적재하고 입력·유효·제외 행 수, 적재 결과와 데이터 버전을 기록합니다.
5. 새 분기 자료나 같은 분기의 정정 파일이 공개되면 동일 절차를 다시 수행합니다. 같은 파일은 중복 적재하지 않고 정정 자료는 변경 범위와 이전 버전을 기록해 반영합니다.

수집·적재에 실패하면 마지막으로 검증된 데이터 버전을 유지하고 화면에 실제 기준 기간·최종 적재 시점을 표시합니다. 새 자료가 없는 기간을 임의로 생성하지 않습니다. 로그인·수동 선택이 필요한 다운로드는 초기에는 수동으로 유지하고, 자동 수집·정기 실행은 MVP 이후 검토합니다.

React는 Spring의 서비스 API로 분석 결과를 요청하고 Spring은 DB를 조회하는 구조로 구현합니다. 파일 전용 데이터를 위해 별도 다운로드 API 서버나 사용자용 CSV 업로드 화면을 만들 필요는 없습니다.

### 수집·연결 시 확인할 사항

- **공간 단위 변경:** 서울시는 2024년부터 표준단위구역을 사용하며 2026-07-03부터 해당 통계를 2021년 이후 자료로 제공한다고 안내합니다. 오래된 상권 경계와 최신 통계가 자동으로 연결된다고 가정하지 않고 코드·경계 버전·대응 관계를 검증합니다. [공식 변경 안내](https://data.seoul.go.kr/together/notice/datasetNoticeView.do?bbsCd=10008&ditcCd=&pageIndex=1&seq=a2197dabd5a3a52edd6fe0d4eead6bd3)
- **기간:** 페이지 수정일, 다운로드일, 원본 기준 기간, 적재일을 각각 기록합니다. 최근 4~8개 분기는 필요한 데이터의 공통 기간과 경계 호환성을 확인한 뒤 확정합니다.
- **갱신:** 상주·직장인구 등은 원천 갱신 값이 여러 분기에 반복될 수 있습니다. 반복 값을 새로운 분기 관측치로 해석하지 않습니다. [상주인구 안내](https://data.seoul.go.kr/dataList/OA-15584/S/1/datasetView.do), [직장인구 안내](https://data.seoul.go.kr/dataList/OA-15569/S/1/datasetView.do)
- **업종:** 소상공인시장진흥공단의 업종 분류와 서울시 서비스 업종 코드는 별도 매핑표로 연결합니다. 명칭이 비슷하다는 이유로 같은 코드로 취급하지 않습니다.
- **점포 이력:** 스냅샷에서 점포가 사라진 것만으로 폐업을 확정하지 않습니다. 개·폐업 추세는 서울시 점포 집계의 정의와 기준 기간을 사용합니다.
- **단위·이용 조건:** 금액·인구·비율 단위, 추정 방식, 이용 조건과 출처 표시 의무를 데이터별로 기록합니다. 추정매출을 실제 창업 매출이나 수익 예측으로 표시하지 않습니다.
- **재현성:** 출처 URL, 파일명·해시, 다운로드일, 공간 기준, 기준 기간, 업종 매핑 버전을 남깁니다. 원본·정제 데이터와 API 키·DB 비밀번호는 향후 Git에서 제외합니다.

## 공간 기준과 분석 정책

MVP에서는 **점포 반경 분석**과 **공식 지역 집계 분석**을 함께 제공하되 각각의 기준을 표시합니다.

| 지표 | 적용 기준 |
| --- | --- |
| 경쟁 점포 수·비율·밀집도 | 선택 좌표 중심의 300m·500m·1km 반경 안 점포 |
| 매출·인구·개폐업·시설 통계 | 선택 좌표가 포함된, 경계·코드 호환성이 검증된 하나의 공식 지역 단위 |
| 분기 추세 | 같은 업종·지역 단위·경계 기준으로 연결 가능한 기간 |

반경을 바꿔도 공식 지역 집계값은 그대로일 수 있습니다. 지역 매출·인구를 반경 면적에 비례해 임의 배분하지 않습니다. MVP가 지원할 공식 지역 유형은 실제 데이터와 경계 검증 후 하나로 확정합니다.

지원 경계 밖이거나 연결할 통계가 없으면 경쟁 점포 조회와 데이터 부족 상태를 표시하고, 근처 지역의 통계를 대신 넣어 종합점수를 만들지 않습니다. 경계 중첩·경계선 위 좌표의 선택 규칙도 구현 전에 정합니다.

### 점수와 비교 기준

초기에는 설명 가능한 규칙 기반 모델을 사용합니다. 아래 가중치는 검증 전 초안입니다.

| 항목 | 계산에 사용할 근거 | 초안 가중치 |
| --- | --- | --- |
| 시장 수요 | 인구와 업종별 추정매출 | 30% |
| 경쟁 여유 | 동일 업종 점포 수·비율·밀집도 | 25% |
| 성장성 | 매출·점포·인구 변화, 개·폐업 추이 | 20% |
| 고객 적합도 | 선택 연령대와 확보 가능한 시간대별 특성 | 15% |
| 접근성·집객 환경 | 공식 지역 내 교통·집객시설 수 | 10% |

원지표의 경쟁강도는 별도로 제공하며, 점수는 모든 항목에서 **높을수록 창업에 유리한 방향**으로 맞춥니다. 같은 업종·기준 분기·공간 유형의 비교 집단으로 정규화하고 계산식·비교 집단·가중치를 모델 버전으로 관리합니다. 시간대별 데이터가 없으면 임의로 고객 적합도를 계산하지 않습니다.

필수 항목이 부족하면 해당 점수와 종합점수는 `null`로 반환하고 부족한 자료를 설명합니다. 결측을 0점으로 바꾸거나 후보지마다 가중치를 재분배하지 않습니다. 0~100점은 정의한 비교 기준에 따른 상대 평가이며 창업 성공 확률을 뜻하지 않습니다.

후보지 비교는 **업종·반경·타깃 연령대·기준 분기·공간 유형·데이터 버전·점수 모델 버전**을 동일하게 맞춥니다. 최신 분기를 후보지별로 따로 선택하지 않습니다.

## DB·Docker 구성 계획

### 현재 상태

DB 정의는 `csv_server/docker-compose.yml`에만 있습니다. 기존 초안은 `postgis/postgis:16-3.4`, DB 이름 `recycle_analysis`, 호스트 포트 `5432`, 명명된 볼륨 `postgres_data`를 사용합니다. Spring Boot에는 PostgreSQL 드라이버가 있지만 데이터 접근 계층·연결 설정·스키마 마이그레이션은 아직 구현되지 않았습니다.

### 공용 DB 하나와 자료별 테이블

**서비스용 PostgreSQL/PostGIS DB 하나를 사용하고 자료별 테이블로 구분합니다.** 매출·점포·인구를 같은 지역·기간 기준으로 함께 조회해야 하므로 초기에는 데이터 출처별 DB를 나누지 않습니다. 개발·테스트 환경의 분리는 데이터 종류별 DB 분리와 별도로 판단합니다.

PostgreSQL 연결은 기본적으로 하나의 DB에 접근하며 그 DB 안의 스키마·테이블을 함께 조회할 수 있습니다. 필요해지면 같은 DB 안에서 스키마를 사용해 서비스 자료와 임시 적재 영역 등을 그룹으로 나눕니다. [PostgreSQL 스키마 문서](https://www.postgresql.org/docs/16/ddl-schemas.html)

아래는 **테이블 설계 초안**입니다. 실제 열·고유키·자료형·인덱스는 원본 검증 후 backend 마이그레이션으로 정의하며, 모든 테이블을 처음부터 생성하지 않습니다.

| 예정 테이블 | 역할 | 도입 단계 |
| --- | --- | --- |
| `commercial_areas` | 상권 코드·이름·공간 기준 정보. 1차는 통계의 코드·명칭부터 관리 | 1차 |
| `industries` / `industry_mappings` | 서비스 업종과 출처·버전별 원본 업종 코드 매핑 | 1차부터, 기관 간 매핑은 2차에 확대 |
| `sales_quarterly` | 지역·분기·업종별 매출 | 1차 |
| `store_stats_quarterly` | 지역·분기·업종별 점포·개폐업 | 1차 |
| `ingestion_runs` | 출처·파일 해시·기간·데이터 버전·적재 결과 | 1차부터 공통 사용 |
| `area_boundaries` | 상권 경계·좌표계·경계 버전 | 2차 |
| `store_snapshots` | 수집 시점별 개별 점포·좌표·업종 | 2차 |
| `floating_population` | 길단위인구의 기준 기간·연령·시간대 등 확보 항목 | 3차 |
| `resident_population` / `workplace_population` | 상주·직장인구와 원천 기준 시점 | 4-1차 |
| `facilities` | 지역별 집객시설 통계 | 4-2차 |
| `commercial_changes` | 상권 변화 유형·영업 지속기간 | 4-3차 |

**연결 기준:** 매출·점포는 상권 + 분기 + 업종, 인구·시설·변화지표는 상권 + 실제 기준 기간, 점포 스냅샷은 출처별 점포 식별자 + 수집 시점, 경계는 상권 + 경계 버전을 기본으로 검토합니다. 공간 기준과 데이터 버전의 호환성도 함께 관리합니다. 업종이 없는 지역 인구를 업종별로 연결한 뒤 반복 합산하지 않습니다.

**ETL 프로젝트도 하나로 유지합니다.** 자료별 수집·변환 모듈을 나누고 공통 DB 연결·검증·적재 이력을 공유합니다. 매출만 갱신되면 매출 작업만 실행할 수 있도록 설계하며, 지역 기준 정보·업종 매핑 등 선행 작업이 준비된 뒤 해당 자료를 적재합니다. 서로 연결 가능한 데이터 버전이 검증된 경우에만 분석에 사용합니다.

### 프로젝트에 맞춘 새 구성

**기존 실험용 Compose를 그대로 최종 구성으로 사용하지 않고, 프로젝트 루트의 `docker-compose.yml`을 공용 개발 DB 설정으로 새로 작성할 계획입니다.** `csv_server/` 삭제 이후에도 `backend/`와 `etl/`이 같은 DB를 사용하도록 DB 설정의 소유 위치를 루트로 정합니다.

| 항목 | 구현 방향 |
| --- | --- |
| 로컬 실행 | MVP에서는 Compose로 PostgreSQL/PostGIS DB만 실행. Spring·React는 현재 개발 명령 사용, Python ETL은 구현 후 수동 배치 실행 |
| DB 이미지 | 실제 환경에서 검증한 PostgreSQL/PostGIS 조합으로 버전 고정 |
| 접속·비밀값 | 루트 `.env.example`에 공용 설정 항목 설명, 실제 비밀번호는 Git에서 제외한 환경 변수로 관리. Spring과 ETL이 같은 DB 이름·포트·계정을 참조 |
| 포트 | 개발 DB는 로컬 호스트에만 노출. 기존 DB와 같은 포트로 동시에 실행하지 않도록 확인 |
| 영속 저장 | 프로젝트·볼륨 식별자를 명시하고 재기동 후 데이터 유지 확인. Compose 위치 변경에 따른 볼륨 연결도 검증 |
| 준비 상태 | DB healthcheck 및 연결 재시도 정책 정의 |
| 스키마 | `backend/src/main/resources/db/migration/`에서 PostGIS 확장·테이블·인덱스를 관리하고, ETL은 생성된 스키마에 적재 |
| 데이터 구조 | 점포 좌표·스냅샷, 기준 지역 경계·버전, 업종 매핑, 지역·업종·분기 통계, 출처·적재 이력 |
| 공간 조회 | 저장 좌표계를 검증하고 미터 단위 반경 조회에 맞는 형식·공간 인덱스 사용 |
| 초기화·복구 | 마이그레이션 후 Python ETL로 실제 공공데이터 적재. 기존 실험 DB의 보존 여부와 백업·복구 검증 후 정리 |

새 구성은 기존 샘플 테이블과 임시 적재 코드를 복사해 완성하는 방식이 아니라 서비스에 필요한 스키마와 연결 설정을 정의하는 작업입니다. 기존 DB 자료가 필요하면 백업·복구 또는 검증된 이전 절차를 먼저 마련합니다. 볼륨 이름·프로젝트 이름 관련 기준은 [Compose 볼륨 문서](https://docs.docker.com/reference/compose-file/volumes/)와 [프로젝트 이름 문서](https://docs.docker.com/compose/how-tos/project-name/)를 참고합니다.

**이번 작업은 README 설계 반영까지입니다.** 루트 Compose·환경 변수 파일은 아직 생성하지 않았고 기존 Docker 설정도 변경하지 않았습니다. ETL 컨테이너·Dockerfile·스케줄러는 실제 기능 구현 이후 검토합니다.

## 프로젝트 구현 순서

기존 `backend/`·`frontend/` 골격에서 시작합니다. **지금 첫 작업은 추정매출·점포 원본 두 자료의 연결 가능성을 확인하는 것**입니다. 공통 상권·분기·업종을 확인한 다음 DB 스키마와 첫 조회 응답을 확정합니다.

### 1차: 실제 데이터 조회를 화면까지 연결

| 순서 | 작업 | 다음 작업으로 넘어가는 기준 |
| --- | --- | --- |
| 1 | 추정매출·점포 원본 확보, 카페·상권 2~3곳·공통 분기 하나 선정 | 지역·분기·업종 코드, 필드·단위와 누락 여부 확인 |
| 2 | 공통 키·업종 매핑·최소 테이블·조회 API 응답 합의 | backend·ETL이 같은 저장 규칙을 사용하고 frontend가 같은 응답 형식을 사용 |
| 3 | 루트 공용 DB Compose·환경 변수, Spring DB 연결·마이그레이션 구현 | 개발 DB 기동·연결·테이블 생성·재기동 후 데이터 유지 확인 |
| 4 | Python 환경·Git 제외 규칙, 매출·점포 파일 입력·검증·적재 구현 | 원본과 DB 수치 일치, 동일 파일 재실행 시 중복 없음, 적재 결과 기록 |
| 5 | Spring의 상권·업종·분기 목록 및 통계 조회 API 구현 | 적재된 값·출처·기준 기간·데이터 버전·결측 상태를 API로 확인 |
| 6 | React의 목록 선택·결과 표·로딩·오류·데이터 부족 상태 구현 | 조건 변경에 따라 실제 DB 조회 결과가 표시됨 |
| 7 | 공통 4개 분기로 확대해 추세 표시, 실행·검산 절차 문서화 | 팀원이 같은 데이터로 전체 흐름을 재현하고 첫 기능 병합 가능 |

이 단계의 조회는 상권 코드·업종·분기 기반으로 시작합니다. 좌표 기반 `POST /api/analysis`는 2차 이후 공간 조회를 연결하면서 확장할 계획이며, 현재 존재하는 API가 아닙니다. frontend는 합의한 예시 응답으로 UI 개발을 병행한 뒤 실제 API로 검증합니다.

### 2~4차: 기능과 데이터 확대

- [ ] **2차:** 통계와 호환되는 경계·개별 점포 원본 확인 → 좌표·기관별 업종 매핑 및 공간 인덱스 구현 → 반경 점포·기준 상권 조회 API → 지도 선택·점포 표시·후보지 최대 3곳 비교 → 수작업 공간 검산
- [ ] **3차:** 길단위인구의 기간·지역·단위·연령·시간대 확인 → 적재·조회 확장 → 수요·고객 특성·추세와 근거 표시 → 실제 후보지로 첫 시연
- [ ] **4-1차:** 상주·직장인구 추가, 원천 갱신 시점과 반복 값 검증 → 고객 기반 설명 보완
- [ ] **4-2차:** 집객시설 추가, 시설 분류·공간 기준 확인 → 접근성·집객 환경 표시
- [ ] **4-3차:** 상권변화지표 추가, 유형·영업기간 확인 → 변화 유형과 영업 지속기간 설명
- [ ] **점수·최종 검증:** 필수 항목과 공통 기간 확보 → 비교 집단·계산식·가중치·모델 버전 검증 → 종합·항목별 점수·결측 정책 구현 → 업종 3~5개·공통 4~8개 분기의 시연과 재현 확인

각 자료 추가 시 원본 확인 → backend 마이그레이션 → ETL 적재·검증 → Spring 조회·응답 → React 표시의 순서를 반복합니다. 자동 API 수집·스케줄러는 수동 파일 적재 흐름이 검증된 이후 필요에 따라 추가합니다.

### 작업 분담과 기존 코드 정리

| 영역 | 우선 책임 | 함께 합의할 사항 |
| --- | --- | --- |
| backend | 공용 DB·스키마 변경 이력, 조회·공간 API, 점수·근거 계산 | ETL과 열·키·단위·데이터 버전, frontend와 요청·응답 형식 |
| ETL | 출처별 파일 입력·수집·정제·적재·품질 및 재실행 검증 | backend 스키마, 자료의 공간·기간·업종 기준 |
| frontend | 단계별 조건 입력·표·지도·차트·비교 및 상태 표시 | backend 응답, 통계의 기준 지역·기간·결측 표시 |

작은 기능 단위로 검증·병합하고 팀의 기준 코드에 반영된 변경을 각 작업에도 적용합니다. 1차 조회 완료나 첫 시연만으로 ETL 전환 전체를 완료했다고 판단하지 않습니다. **합의한 최종 필수 자료와 아래 ETL 완료 기준을 충족한 후** 공용 DB·필요 자료를 보존하고 미사용 `csv_server/` 코드부터 점진적으로 삭제합니다.

## 현재 개발 환경 실행

현재 설정 파일 기준으로 백엔드는 **Java 21**을 사용합니다. 프론트엔드는 `package-lock.json`의 Vite·ESLint 엔진 조건을 함께 만족해야 합니다. Node.js 22 계열을 사용한다면 **22.13 이상**이 필요하며, 팀 공통 버전은 실행 검증 후 고정합니다.

프로젝트 루트에서 각각 별도 터미널로 실행합니다.

```sh
cd backend
./gradlew bootRun
```

```sh
cd frontend
npm ci
npm run dev
```

프론트엔드 기본 주소는 `http://localhost:5173`, 백엔드는 `http://localhost:8080`입니다. Vite의 `/api` 요청은 백엔드로 전달되며 CORS 설정도 마련되어 있습니다. 현재 실행하면 프론트 기본 화면과 Spring 골격을 확인할 수 있고 실제 분석은 DB·ETL·API 구현 이후 가능합니다.

루트 Compose와 Python ETL은 아직 구현되지 않았으므로 실행 명령을 제시하지 않습니다. ETL의 단계별 설계와 준비 상태는 [ETL 설계 문서](etl/README.md)를 참고합니다.
