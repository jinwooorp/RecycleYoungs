# 여기 창업해도 돼? — RecycleYoungs

서울의 창업 후보 위치를 공공데이터로 분석·비교하는 대학 캡스톤 웹 서비스입니다. 예비 창업자가 지역 통계와 주변 경쟁 점포를 살펴보고 최대 3곳을 같은 조건으로 비교하도록 돕는 **카페 업종 우선 MVP**입니다.

**최신 검증일: 2026-10-14 · 캡스톤 MVP 검증 완료 · 최종 마감: 2026-10-31**

2026-10-14에 **새 일회용 tmpfs 격리 DB**에서 실제 서울 자료 적재부터 PostGIS·Spring·React·Kakao Maps까지 검증했습니다. 실제 지도 클릭, 3후보 비교·오류 복구, 대표 source 경계 2개 SQL→HTTP, bridge abort·재요청·cleanup을 확인했습니다. 완료 범위는 캡스톤 MVP와 격리 실자료 시연이며 운영 준비 완료를 뜻하지 않습니다. 기존 개발 DB에는 접속하지 않았고 **NOT_READY**를 유지합니다. 카페는 첫 번째 검증 업종이며 서비스를 카페 전용으로 제한하지 않습니다.

## 개발 로드맵

✅는 각 단계에 적힌 범위의 구현·검증 완료를 뜻합니다. **7~10단계 완료는 2026-10-14에 검증한 캡스톤 MVP 및 일회용 격리 실자료 시연 범위**입니다. 기존 개발 DB 적용, 운영 배포, 원천 snapshot·역사적 경계 검증까지 완료했다는 뜻은 아닙니다. [개발 과정](docs/project.md#구현-과정과-주요-결정)과 [단계별 근거·한계](docs/project.md#구현-상태와-검증-수준)에서 과거 검증과 현재 상태를 구분합니다.

1. **서비스 기획 및 공공데이터 조사 — ✅**
   예비 창업자가 후보지를 비교할 수 있도록 서비스 목표를 세우고, 서울시 공공데이터와 소상공인 점포 자료를 조사했습니다.

2. **DB 설계 및 기본 CSV ETL 구현 — ✅**
   PostgreSQL 기반 기본 데이터 구조와 서울시 통계 CSV 처리 코드를 구현하고 당시 검증했습니다. 기존 개발 DB에 모든 최신 자료가 적재됐다는 뜻은 아닙니다.

3. **행정동 통계 Backend API 구현 — ✅**
   Spring Boot와 JdbcClient로 행정동·업종·분기 목록 및 점포·추정매출 조회 API를 구현했습니다. 단위 테스트와 당시 격리 조회 검증 기록이 있습니다.

4. **React 통계·추세 조회 화면 구현 — ✅**
   조회 조건 선택, 점포·추정매출 조회, 2025년 1~4분기 추세와 결측·요청 오류 처리를 구현했습니다. 테스트와 당시 API 연결 검증 기록이 있습니다.

5. **공간 데이터 및 카페 업종 분석 기반 준비 — ✅**
   행정동·상권 경계와 SEMAS 카페 업종 연결을 위한 DB 변경·ETL 코드를 작성하고 격리 검증했습니다. 완료 범위는 코드와 격리 검증이며, 기존 개발 DB의 공간 변경 적용과 실제 Polygon 적재는 미완료입니다.

6. **카카오맵 연동 및 단일 위치 선택 — ✅**
   지도 클릭, 위도·경도의 React 상태 저장·표시, 단일 마커 이동과 표준 줌 버튼을 구현했습니다. Mock 회귀와 v2 실제 Chrome의 SDK·실자료 API 연결을 확인했습니다.

7. **좌표 기반 행정동·상권 분석 — ✅**
   실제 source Polygon 경계 좌표 2개에서 정확한 SQL→HTTP 대조와 복수 membership·경계 모호성 처리를 확인했습니다. 모든 경계 좌표나 역사적 경계 호환성까지 검증한 것은 아닙니다.

8. **반경 내 카페 경쟁 점포 분석 — ✅**
   실제 I21201/CAFE의 반경 500m count·list·distance를 SQL·API·UI와 대조했습니다. 4개 클릭의 SQL/API와 최종 후보 UI 및 100개 목록이 일치했으며 snapshot UNVERIFIED는 유지합니다.

9. **최대 3곳 후보 위치 비교 — ✅**
   실제 지도에서 최대 3후보 등록·삭제·교체·분기 변경·늦은 응답 차단·단일 실패 복구를 검증했습니다. 최종 3후보의 Q3 통계 9개 지표가 SQL·API·UI와 일치했습니다.

10. **통합 테스트 및 최종 시연 — ✅**
    실제 서울 자료 ETL→PostGIS→Spring→React→Kakao Maps E2E와 bridge의 실제 TCP RST·정상 재요청·cleanup을 검증했습니다. 전후 데이터 무결성도 일치했습니다. [검증 결과와 재현 안내](docs/technical.md#실자료-격리-시연)에서 운영·데이터 한계를 확인합니다.

## 어떤 문제를 해결하나요?

후보지를 비교하려면 점포와 매출 자료를 찾아야 하지만, 자료마다 제공 사이트·기준 시점·집계 지역이 다릅니다. 이 서비스는 수치와 함께 출처·기간·집계 단위를 보여줘 비교의 근거를 확인하도록 돕는 것이 목표입니다.

자료는 특정 가게의 실제 매출이나 이익을 뜻하지 않습니다. 지역 통계로 후보지의 환경을 살펴볼 수 있지만, 창업 성공·수익·폐업 가능성을 예측하거나 보장하지 않습니다. 반경 안의 수요를 지역 통계의 면적 비율로 계산하지도 않습니다.

## 지금 구현된 사용자 기능

지도에서 위치를 클릭하면 위도·경도와 마커 하나를 확인할 수 있습니다. 다른 곳을 클릭하면 같은 마커가 이동하며 지역 판정과 지원 조건의 500m 경쟁 카페 조회를 요청합니다. 행정동이 하나로 확정되고 통계 lookup에 있으면 동 조건에 반영하며, 통계·추세는 사용자가 **조회하기**를 눌러 조회합니다. 모호한 동이나 lookup에 없는 동을 다른 동으로 대체하지 않습니다.

선택 위치를 **후보지에 추가**해 최대 3곳을 저장·삭제하고 공통 CAFE/500m/분기로 비교할 수 있습니다. 새 지도 탐색에도 저장 좌표를 유지하며 후보별 지역·상권·카페·통계의 로딩, 오류와 재시도를 독립적으로 표시합니다. 비교 분기를 바꾸면 기존 후보 통계를 지우고 **비교 통계 조회**로 다시 조회합니다. 기존 수동 행정동 조회도 유지합니다.

지역 결과에는 실제 dataset version·품질·기준일과 경계 모호성을, 경쟁 카페 결과에는 전체 수와 최대 100개 반환 목록, SEMAS/I21201 출처와 snapshot **UNVERIFIED** 한계를 표시합니다. 데이터 미준비와 정상 0개를 구분하며 점포 원본 기준일·완전성이나 후보 간 동일 snapshot은 보장하지 않습니다. 같은 행정동의 후보들은 같은 지역 집계를 공유할 수 있고, 행정동 추정매출은 후보 반경 500m의 매출이 아닙니다.

행정동 통계는 다음 순서로 조회하도록 구현돼 있습니다.

1. 행정동을 선택합니다.
2. 지원하는 업종을 선택합니다.
3. 통계를 조회할 분기를 선택합니다.
4. **조회하기** 버튼을 누릅니다.
5. 선택 분기의 점포 수·유사점포 수·개업/폐업 점포 수·프랜차이즈 수와 추정매출·거래 건수를 확인합니다.
6. 같은 행정동·업종의 **2025년 1~4분기 추세 표**를 확인합니다.

선택 분기는 5번의 단건 통계에만 적용됩니다. 6번의 추세는 항상 2025년 네 분기를 보여줍니다. 현재 고정 입력의 지원 업종은 카페(CAFE)·미용실(HAIR)·한식(KFOOD)·주점(PUB)입니다. 모든 선택 조합에 자료가 있는 것은 아닙니다.

화면은 실제 0과 자료가 없는 경우를 구분합니다. 조회 중 안내, 오류 후 재조회, 조건 변경 시 요청 취소도 있으며, 단건과 추세 중 한쪽이 실패해도 다른 쪽의 결과는 표시합니다. 모바일에서는 표 안을 가로로 스크롤하고 키보드로도 입력과 조회를 할 수 있도록 구현했습니다.

과거 합성/Mock·2026-10-13 v2와 2026-10-14 최종 검증을 구분합니다. [날짜별 수치와 실제 클릭 근거](docs/technical.md#실자료-격리-시연)는 technical 문서에 둡니다.

## 최종 MVP 사용자 흐름

MVP는 처음 완성할 핵심 서비스 범위입니다. 2026-10-14에 위치 선택부터 지역 판정·경쟁 카페 조회·후보 비교까지 실제 자료와 Kakao Maps의 핵심 흐름을 검증했습니다. 원천 기간·운영 검증과 Git 최종 승인은 별도입니다.

| 하고 싶은 일 | 현재 구현 | MVP 검증 결과·후속 한계 |
| --- | --- | --- |
| 위치 고르기 | 단일 좌표 선택·최대 3후보 저장 | 실제 SDK·지도 클릭 및 실자료 연결 PASS |
| 어느 지역인지 확인하기 | 좌표로 행정동·상권 판정·경계 모호성 표시·통계 조건 연결 | 실제 Polygon 대조·대표 정확한 경계 2개 PASS |
| 점포 살펴보기 | 행정동 집계와 500m 경쟁 카페 수·목록을 별도 표시 | 실제 SEMAS 안전 적재·조회 대조 PASS, snapshot UNVERIFIED |
| 통계 해석하기 | 선택 분기·고정 네 분기 통계, 공간 version·품질·점포 출처/한계 표시 | 최종 3후보 Q3 지표 대조 PASS, 원천 기준일·완전성 후속 검증 |
| 후보 비교하기 | 공통 CAFE/500m/분기로 최대 3곳 비교·부분 실패와 자료 한계 표시 | 실자료 비교·삭제/교체·늦은 응답·실패 복구 PASS |

**새 격리 환경의 실제 원본 적재·SQL/HTTP/UI 대조와 live 지도 3후보 핵심 시연은 통과했습니다.** 2025년 행정동 통계와 SEMAS 점포는 기준 시점·집계 단위가 다르며, 공간 version 차이와 점포 snapshot UNVERIFIED를 숨기지 않습니다. 추가 인구·시설·변화 지표와 설명 가능한 점수는 자료와 계산식을 검증한 뒤 검토합니다. AI 예측·전국 확대·실시간 수집·수익 예측은 현재 MVP 범위가 아닙니다.

## 기술 스택과 시스템 흐름

화면은 React, 요청 처리는 Spring, 자료 저장과 조회는 PostgreSQL이 맡습니다. Python ETL은 CSV를 읽고 검증·변환해 DB에 미리 적재하는 별도 작업입니다. PostGIS는 좌표의 행정동·상권 판정과 미터 단위 반경 경쟁 카페 조회에 사용하며, 해당 SQL·JDBC·HTTP는 합성 및 실자료 격리 환경에서 검증했습니다. 기존 개발 DB 적용은 미완료입니다.

| 영역 | 구성 |
| --- | --- |
| Frontend | React 19·TypeScript 6·Vite 8·Tailwind 4·shadcn Button/Card |
| Backend | Java 21·Spring Boot 4.1.1·Spring MVC·JdbcClient |
| DB | PostgreSQL 16·PostGIS 3.4·Flyway |
| 자료 처리·실행 | Python 3.12·Docker Compose·Makefile |

공공자료 → Python ETL → DB에 저장 → Spring API로 조회 → React에 표시하는 구조입니다. **일반 API 조회는 적재된 DB를 사용하며 ETL을 다시 실행하지 않습니다.** 격리 demo는 안전 검사로 매 요청 원본 hash를 재확인합니다. [실제 조회 한 번 따라가기](docs/technical.md#통계-조회-한-번-따라가기)와 [기술 스택](docs/technical.md#기술-스택과-선택-이유)에서 세부 구현을 확인합니다.

## 기존 개발 DB 상태

**기존 개발 DB는 NOT_READY이며, V2/V3와 행정동·상권 Polygon 적용은 마지막 확인 기록에서 미완료입니다.** 격리 테스트 성공은 기존 개발 DB 적용 성공을 뜻하지 않습니다. 기능 개발은 mock 또는 승인된 격리 환경에서 진행할 수 있지만, 실제 기존 DB 변경에는 별도의 검증과 명시적 승인이 필요합니다. 이번 문서 작업에서 DB를 재조회하지 않았으며, 상세 절차는 [db-safety](docs/db-safety.md)에 있습니다.

## 안전하게 개발 시작하기

먼저 Git branch/HEAD와 변경 파일을 확인하고 [착수 가능한 작업](docs/project.md#현재-위치와-지금-시작할-작업)에서 범위를 고릅니다. 실제 DB 없이 가짜 응답으로 화면·계약을 확인하는 mock 작업과 [DB 없는 검증](docs/technical.md#db-없는-검증)부터 준비할 수 있습니다. 의존성은 기존 lockfile을 따르고 새 clone에는 원본 자료가 없다는 점도 확인합니다.

`make db`/`db-info`/`etl`, Spring bootRun·dbTest는 기존 DB에 영향을 줄 수 있습니다. migration은 DB 구조를 SQL로 바꾸는 작업이고, full loader는 기존 자료를 지우고 다시 채울 수 있습니다. 실행 전에 [위험 명령](docs/technical.md#위험-명령과-알려진-blocker)과 대상·범위의 별도 승인을 확인합니다. 문서 수정은 DB 변경이나 Git stage/commit/push 승인이 아닙니다.

활성 문서는 README·AGENTS·project·technical·db-safety 5개입니다. [legacy](legacy/README.md)는 이전 실험의 보존 영역이고 과거 상세 보고는 고정 Git 링크로 남깁니다.
