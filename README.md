## 프로젝트 소개

서울에서 창업을 준비하는 사람들을 위한 공공데이터 기반 MVP 서비스입니다. **MVP에서는 카페 업종만 지원할 예정입니다.**

사용자가 관심 지역의 상권 데이터를 탐색하고, 자체 평가 알고리즘으로 산출한 창업 환경 점수를 확인하며, 여러 후보지를 비교할 수 있도록 하는 것을 목표로 합니다.

복잡한 상권 통계를 처음부터 모두 보여주기보다, **100점 만점의 창업 환경 점수를 먼저 제공하고 사용자가 원하는 경우 세부 분석 근거를 확인할 수 있도록** 구성할 예정입니다.

창업 환경 점수는 실제 창업 성공 확률이나 예상 수익을 의미하지 않으며, 창업 후보지를 검토할 때 참고할 수 있는 자체 평가 지표입니다.

현재 개발 환경, Flyway V1~V4 및 행정동·자치구 경계·서비스 업종·점포·추정매출·유동인구 통계 ETL을 구현했습니다. 로컬 개발 DB에는 행정동 425개·자치구 25개·서비스 업종 100개·점포 통계 211,832행·추정매출 통계 100,431행·유동인구 통계 9,350행을 적재했습니다. V4 카페 테이블은 개발 DB 적용을 완료했습니다. 카페 ETL은 실제 API 검증과 로컬 개발 DB 21,996건 게시(`PUBLISHED`)를 완료했으며, 재실행 `SKIPPED`와 기존 게시 출처 보존을 확인했습니다. 백엔드 행정구역 조회 API를 구현했으며, 상권 통계·주변 카페 조회·점수 기능은 후속 단계입니다.

## 화면 미리보기

현재 개발 기반과 경계·서비스 업종·점포·추정매출·유동인구 통계·카페 ETL 구현 및 실제 적재를 완료했습니다. 실제 서비스 화면은 아직 구현되지 않았습니다.

향후 메인 페이지, 지도 기반 상권 탐색 화면, 창업 환경 점수 및 상세 분석 화면, 후보지 비교 화면을 개발한 후 스크린샷이나 시연 이미지를 추가할 예정입니다.

아래는 현재 계획 중인 기능이며, 실제 구현 범위와 우선순위는 데이터 연동 및 개발 과정에서 조정할 수 있습니다.

### 추후 도입 검토 기능

- **최근 탐색 기록:** 사용자가 이전에 조회한 지역이나 위치를 다시 확인
- **관심 후보지 저장:** 창업 후보지를 저장하고 이후 다시 확인
- **회원 기능:** 필요한 경우 개인별 후보지 저장과 관리 기능 제공
- **추가 데이터 분석:** 상주인구, 직장인구, 집객시설, 지하철 이용량 등 활용 범위 확대
- **개별 위치 평가 점수:** 충분한 위치 기반 데이터와 검증 기준이 확보되면 후보지별 반경 단위 점수 검토
- **분석 결과 공유:** 선택한 지역이나 후보지의 분석 결과를 다른 사람과 공유하는 기능 검토

추후 검토 기능은 MVP의 필수 구현 범위에 포함하지 않으며, 핵심 기능의 구현과 검증을 우선합니다.

## 사용 흐름

아래는 현재 구상 중인 서비스 이용 흐름이며, 실제 기능과 화면 구성은 개발 과정에서 변경될 수 있습니다.

### 메인 페이지

메인 페이지에서는 서비스의 목적과 주요 기능을 소개하고, 사용자가 상권 탐색을 시작할 수 있도록 안내합니다.

1. **서비스 소개**
   - 공공데이터를 활용한 카페 창업 상권 분석 서비스의 목적과 주요 특징을 소개합니다.
   - 지도 기반 탐색 화면과 창업 환경 점수의 미리보기를 제공합니다.
   - `시작하기` 버튼을 통해 탐색 페이지로 이동할 수 있도록 합니다.

2. **주요 이용 과정 안내**
   - 스크롤에 따라 서비스 이용 과정을 단계별로 소개합니다.
   - 각 단계에는 간단한 설명과 실제 서비스 화면의 미리보기를 제공합니다.
   - 소개할 주요 과정은 다음과 같습니다.
     1. **관심 지역 탐색:** 서울 지도에서 구·행정동을 선택하거나 역명·장소명 등을 검색해 관심 지역을 찾아봅니다.
     2. **창업 환경 점수 확인:** 해당 지역의 공공데이터를 바탕으로 산출한 100점 만점의 창업 환경 점수를 확인합니다.
     3. **상권 상세 분석:** 점수 산출 근거와 점포 현황, 추정매출, 유동인구, 주변 경쟁 카페 등의 정보를 살펴봅니다.
     4. **후보지 비교:** 관심 있는 후보지의 주요 지표를 비교하고 추가로 확인할 사항을 살펴봅니다.

3. **상권 탐색 시작**
   - 주요 이용 과정 안내가 끝나면 실제 탐색을 시작하도록 안내합니다.
   - `시작하기` 버튼을 통해 탐색 페이지로 이동합니다.

메인 페이지는 스크롤 기반 애니메이션과 단계별 화면 전환을 활용하는 방향으로 구성할 예정입니다.

### 탐색 페이지

탐색 페이지에서는 서울 지도를 중심으로 관심 지역을 찾고, 관련 공공데이터와 자체 평가 알고리즘을 활용해 카페 창업 환경을 분석·비교합니다.

#### 1. 지역 및 위치 탐색

탐색 대상 지역은 **서울특별시로 고정**하며, 행정구역 탐색과 장소 주변 탐색을 구분하여 제공합니다.

**행정구역 탐색**

- 지역 필터는 `서울시 → 구 → 동` 순서로 구성합니다.
  - **시·도:** 서울특별시 고정
  - **구:** 전체 또는 특정 자치구 선택
  - **동:** 전체 또는 선택한 구에 속한 행정동 선택
- 특정 구를 선택하면 해당 구의 행정동 목록을 제공합니다.
- 동 필터의 `전체`는 선택한 구에 속한 전체 행정동을 의미합니다.
- 행정구역을 선택하면 해당 구 또는 행정동을 기준으로 지도와 상권 정보를 표시합니다.
- 지도 이동 및 확대·축소를 통해 관심 지역을 자유롭게 살펴볼 수 있습니다.

**장소 주변 탐색**

- 검색창에서 지하철역, 주요 장소, 주소, 구·행정동 이름 등의 키워드 검색을 지원합니다.
- 장소를 검색하면 해당 위치로 지도를 이동하고 설정된 탐색 범위를 표시합니다.
- 장소 검색으로 이동한 위치가 기존 지역 필터와 다르더라도 기존 필터를 즉시 변경하지 않습니다.
- 검색 위치의 탐색 범위와 겹치는 서울시 자치구를 확인합니다.
  - 하나의 자치구만 포함되면 해당 자치구를 안내합니다.
  - 여러 자치구가 포함되면 사용자가 분석할 자치구를 직접 선택하도록 합니다.
- 예를 들어 `염창역 9호선`을 검색했을 때 탐색 범위에 강서구와 양천구가 포함된다면 `강서구 / 양천구 / 모두` 중 선택할 수 있습니다.
- 3개 이상의 자치구가 포함되는 경우에도 각 자치구와 `모두` 선택지를 제공합니다.
- **`모두`는 검색 위치의 탐색 범위와 겹치는 모든 자치구를 선택한다는 의미**이며, 해당 자치구 전체로 주변 탐색 반경을 확장하는 것은 아닙니다.
- 사용자가 자치구 선택을 확정하면 관련 구·동 필터와 분석 정보를 갱신하고, 검색한 장소의 위치는 유지합니다.
- 여러 자치구가 선택되면 관련 행정동을 자치구별로 구분하여 제공합니다.

#### 2. 탐색 범위 및 조건 설정

- 사용자가 선택한 행정구역 전체를 탐색하는 방식과 특정 위치 주변을 탐색하는 방식을 구분합니다.
- 장소 주변 탐색은 기본 반경을 500m로 시작하고, 1km까지 변경할 수 있도록 검토합니다.
- 장소 주변 탐색에서 특정 자치구를 선택한 경우, **설정된 반경과 선택한 자치구가 겹치는 영역**을 위치 기반 조회 대상으로 사용합니다.
  - 예: `염창역 → 반경 500m → 강서구`를 선택하면 염창역 반경 500m 중 강서구에 속하는 영역의 주변 카페를 조회합니다.
  - `모두`를 선택하면 해당 반경 내에서 확인된 모든 서울시 자치구의 관련 위치 정보를 조회합니다.
- 분석 기간과 관심 지표 등 필요한 조건을 설정합니다.
- 행정구역 단위의 통계와 특정 위치 주변에서 조회한 데이터를 구분하여 제공합니다.
- 지도를 이동하거나 확대·축소하더라도 적용된 분석 조건은 유지합니다.
- 필요한 경우 `이 지역에서 다시 검색` 기능으로 현재 지도 위치를 기준으로 탐색할 수 있도록 검토합니다.

#### 3. 창업 환경 점수 확인

사용자가 분석할 구 또는 행정동을 선택하면 해당 지역의 주요 공공데이터를 바탕으로 **100점 만점의 카페 창업 환경 점수**를 제공합니다.

**점수 표시 방식**

- 상세 통계보다 창업 환경 점수를 먼저 표시해 사용자가 해당 지역의 전반적인 특성을 빠르게 파악할 수 있도록 합니다.
- 점수는 `0~100점` 범위로 표시하며, 지역명과 평가 기준 지역을 함께 안내합니다.
- 예를 들어 염창역 검색 후 강서구를 선택했다면 다음과 같이 표시합니다.

  **강서구의 카페 창업 환경 점수는 70/100 (예시)**

- 위 점수는 화면 구성 설명을 위한 예시이며, 실제 점수는 데이터 확보 및 평가 알고리즘 구현 후 산출합니다.
- 구를 선택하면 해당 자치구 전체의 데이터를 기준으로 점수를 계산하고, 행정동을 선택하면 해당 행정동의 데이터를 기준으로 계산합니다.
- 여러 자치구를 선택하거나 `모두`를 선택한 경우에는 각 자치구의 점수를 개별적으로 표시합니다. 서로 다른 지역의 점수를 임의로 합산하여 하나의 점수로 만들지 않습니다.

**점수 평가 범위**

- 창업 환경 점수는 구 또는 행정동 등 명시된 행정구역을 기준으로 산출합니다.
- 장소 검색 시 사용하는 탐색 반경과 창업 환경 점수의 평가 범위는 별도로 관리합니다.
- 결과 화면에는 **점수 평가 범위**와 **주변 탐색 범위**를 함께 표시합니다.
- 예를 들어 `염창역 → 반경 500m → 강서구`를 선택한 경우 다음과 같이 구분합니다.
  - **창업 환경 점수:** 강서구 전체의 공공데이터를 기준으로 산출한 점수
  - **주변 탐색 정보:** 염창역 반경 500m 중 강서구에 속하는 영역의 위치 기반 데이터
- 따라서 강서구 전체의 점수를 염창역 주변 500m만을 평가한 점수처럼 표현하지 않습니다.
- 행정동을 선택한 경우에는 해당 행정동 전체를 기준으로 산출한 점수임을 명시합니다.
- 서로 다른 집계 단위인 구와 행정동의 점수를 동일한 기준의 점수처럼 직접 비교하지 않도록 안내합니다.

**점수 조회 상태 및 예외 처리**

- **초기 진입:** 분석 대상이 선택되지 않았다면 구 또는 행정동을 선택하도록 안내하고, 임의의 기본 점수는 표시하지 않습니다.
- **조회 및 계산 중:** 점수 데이터를 불러오거나 계산하는 동안 로딩 상태를 표시합니다.
- **조회 완료:** 지역명, 평가 범위, 최종 점수를 우선 표시합니다.
- **데이터 부족:** 점수 산출에 필요한 데이터가 충분하지 않다면 `산출 불가` 상태와 사유를 안내합니다.
- **조회 실패:** API 오류 등으로 결과를 불러오지 못한 경우 오류 메시지와 다시 시도할 수 있는 기능을 제공합니다.
- 실제 데이터가 없거나 계산할 수 없는 상황에서 임의의 점수를 생성하지 않습니다.

**점수 산출 방식**

- 카페 수, 추정매출, 유동인구, 개업·폐업 현황 등 확보한 공공데이터를 활용하여 자체 평가 알고리즘을 설계합니다.
- 지표별 특성과 방향성을 고려해 정규화 및 가중치를 적용하고, 최종 점수를 100점 만점으로 환산합니다.
- 주요 평가 항목은 다음과 같이 검토합니다.
  - **소비 및 상권 수요:** 추정매출, 유동인구 등의 지표
  - **경쟁 환경:** 카페 수와 밀집도 등 경쟁 점포 관련 지표
  - **상권 변화 및 안정성:** 개업·폐업 현황과 지역 변화 관련 지표
- 단순히 유동인구가 많거나 카페 수가 적다는 이유만으로 높은 점수를 부여하지 않고, 지표 간 관계를 함께 고려합니다.
- 구와 행정동은 규모와 특성이 다르므로 각각의 비교 기준을 설계하며, 서로 다른 집계 단위의 점수를 직접 비교하지 않도록 합니다.
- 행정동 단위 자료를 이용해 구 단위 점수를 산출해야 하는 경우에는 지표별 집계 가능 여부와 산출 방법을 별도로 검증합니다.
- 평가 항목, 가중치, 정규화 방식 및 점수 구간은 실제 데이터의 품질과 분포를 확인한 뒤 확정합니다.
- 점수 계산에 필요한 데이터가 부족하거나 기준이 맞지 않으면 임의의 점수를 생성하지 않고 `산출 불가` 또는 데이터 부족 상태를 안내합니다.

**점수 산출 근거 확인**

- 기본 화면에서는 지역명과 최종 점수를 중심으로 간결하게 표시합니다.
- 사용자가 `점수 산출 근거 보기` 또는 `더보기`를 선택하면 상세 분석 정보를 펼쳐서 확인할 수 있도록 합니다.
- 상세 정보에는 다음 내용을 제공합니다.
  - 평가 항목별 점수 및 반영 비중
  - 실제 계산에 사용된 주요 공공데이터 지표
  - 지역별 특징과 점수에 영향을 준 주요 요인
  - 데이터 출처 및 기준 시점
  - 적용된 평가 알고리즘의 기준과 한계
- 사용자가 점수를 맹목적으로 신뢰하지 않고 직접 분석 근거를 확인할 수 있도록 합니다.

**점수 해석 시 유의사항**

창업 환경 점수는 공공데이터를 기반으로 자체 산출한 상대적 평가 지표입니다. 실제 창업 성공 확률이나 예상 수익을 의미하지 않으며, 임대료·입지의 세부 조건·운영 역량 등 반영되지 않은 요인이 존재할 수 있습니다.

#### 4. 지도에서 관심 대상 선택

- 지도에서 기존 카페의 위치와 분포를 확인합니다.
- 카페 마커를 선택하면 상호명, 위치, 업종 등 확인 가능한 기본 정보를 제공합니다.
- 마우스 호버 시 간단한 정보를 미리 표시하고, 클릭 또는 터치 시 상세 정보를 확인할 수 있도록 구성합니다.
- 지도에서 사용자가 직접 관심 지점을 선택해 창업 후보지로 지정할 수 있도록 합니다.
- **창업 후보지는 실제 입점 가능한 상가 매물이 아니라, 주변 상권을 분석하고 비교하기 위해 사용자가 지정한 관심 위치**로 정의합니다.
- 실제 입점 가능 여부, 임대 조건 및 영업 관련 요건은 별도로 확인해야 함을 안내합니다.
- 기존 카페를 선택한 경우와 창업 후보지를 선택한 경우를 구분하여 관련 정보를 제공합니다.
- 선택한 대상에 따라 상세 정보 패널을 열고, 지도를 유지한 상태에서 정보를 확인할 수 있도록 합니다.

#### 5. 상권 상세 분석

- 창업 환경 점수의 산출 근거와 관련 상권 데이터를 확인합니다.
- 선택한 지역의 점포 수, 개업·폐업 현황, 추정매출, 유동인구 등을 살펴봅니다.
- 주변 경쟁 카페의 위치와 분포를 지도 및 목록으로 확인합니다.
- 기간별 변화 추이와 주요 지표를 차트 및 표로 제공합니다.
- 상세 분석 정보는 집계 범위에 따라 구분합니다.
  - **선택 위치 주변 정보:** 설정된 반경 내 경쟁 카페의 위치와 수 등 위치 기반으로 조회할 수 있는 정보
  - **행정구역 단위 통계:** 선택한 구 또는 행정동 전체를 기준으로 집계된 점포 현황, 추정매출, 유동인구 등
- 장소 주변 탐색에서 자치구를 선택한 경우, 위치 기반 데이터는 해당 자치구와 탐색 반경이 겹치는 영역을 기준으로 조회합니다.
- 행정동 단위 통계는 탐색 반경과 겹치는 행정동의 전체 집계값을 참고 정보로 제공하며, 반경 내 실제 통계로 해석하지 않도록 표시합니다.
- 여러 자치구가 포함되면 지역별 통계를 구분하여 확인할 수 있도록 합니다.
- 각 데이터의 출처, 기준 시점, 집계 단위 및 점수 산출 기준을 함께 표시합니다.
- 데이터가 제공되지 않는 경우 실제 값이 `0`인 경우와 구분하여 안내합니다.

#### 6. 창업 후보지 비교

- 사용자가 선택한 관심 위치를 창업 후보지로 추가합니다.
- 여러 후보지의 주변 경쟁 카페, 점포 현황, 추정매출, 유동인구 등 주요 지표를 비교합니다.
- 후보지가 속한 구·행정동의 창업 환경 점수도 함께 확인할 수 있도록 합니다.
- 후보지별 반경 내 위치 기반 정보와 행정구역 단위 통계를 구분하여 비교합니다.
- 동일한 기준 기간과 집계 단위에서 비교할 수 있도록 안내합니다.
- 구 단위와 행정동 단위 점수는 평가 기준이 다를 수 있으므로 직접적인 우열 비교를 피합니다.
- 같은 행정동에 속한 후보지는 동일한 행정동 통계를 공유할 수 있지만, 각 위치 주변의 경쟁 카페 수와 분포는 다를 수 있음을 안내합니다.
- 데이터가 없거나 기준 시점이 다른 경우 해당 내용을 명확하게 표시합니다.
- 비교 결과를 통해 후보지별 특징을 파악하고, 창업 전 추가로 조사할 사항을 확인합니다.

**후보지 점수와 지역 점수의 구분**

- MVP에서는 개별 창업 후보지의 위치 자체에 별도의 100점 점수를 부여하지 않습니다.
- 후보지에 표시되는 창업 환경 점수는 **해당 후보지가 속한 구 또는 행정동의 평가 점수**입니다.
- 동일한 행정동에 있는 두 후보지는 같은 행정동 점수를 공유할 수 있습니다.
- 다만 각 후보지의 위치와 탐색 반경에 따라 주변 경쟁 카페 수와 분포 등의 위치 기반 정보는 달라질 수 있습니다.
- 비교 화면에서는 점수의 평가 단위를 명확히 표시하여 지역 점수를 특정 지점의 독립적인 점수로 오해하지 않도록 합니다.
- 추후 충분한 위치 기반 데이터와 검증 기준이 확보되면 개별 후보지의 반경 단위 평가 점수를 별도로 도입하는 방안을 검토합니다.

**탐색 화면 구성**

탐색 페이지는 전체 화면 지도를 중심으로 검색·필터와 확장 가능한 상세 정보 패널을 배치하는 방향으로 구성할 예정입니다.

지역 선택 후에는 창업 환경 점수를 우선적으로 표시하고, 사용자가 원하는 경우에만 점수 산출 근거와 세부 상권 데이터를 확장하여 확인할 수 있도록 합니다.

**검색 및 데이터 이용 시 유의사항**

- 서울특별시 외 지역을 검색한 경우 서비스 지원 범위를 안내하고, 서울 외 지역에 대한 상권 분석은 제공하지 않습니다.
- 검색 위치의 탐색 반경이 서울 외 지역까지 걸치면 서울특별시 내부만 분석 대상으로 포함합니다.
- 행정동별 추정매출·인구·점포 통계와 개별 카페의 위치 정보는 집계 범위가 다릅니다.
- 특정 위치 주변에 여러 행정구역이 포함되더라도 행정동 전체의 통계를 해당 위치 주변의 실제 수치로 해석하거나 단순 합산하지 않습니다.
- 서로 다른 기준 시점이나 집계 단위의 데이터를 비교할 때에는 한계를 안내합니다.
- 창업 환경 점수는 자체 평가 알고리즘에 따른 참고 지표이며, 실제 창업 성공이나 수익을 보장하지 않습니다.

#### API 인증키 발급 방법

공공데이터포털과 서울 열린데이터광장은 인증키 발급 및 API 이용 방식이 다릅니다.

**1. 공공데이터포털**

1. [공공데이터포털](https://www.data.go.kr/)에 회원가입 후 로그인합니다.
2. [소상공인시장진흥공단 상가(상권)정보 API](https://www.data.go.kr/data/15012005/openapi.do) 상세 페이지에 접속합니다.
3. **활용신청**을 클릭하고 화면에 안내되는 신청 정보를 입력합니다.
4. 활용신청을 완료한 뒤 승인 상태를 확인합니다. 해당 API는 확인 당시 개발·운영 단계 모두 자동승인 대상으로 안내되어 있습니다.
5. 마이페이지의 API 활용신청 내역에서 서비스 이용 상태와 인증키를 확인합니다.
6. API 상세 페이지의 활용 명세 및 참고문서를 확인한 뒤 발급받은 인증키로 호출을 테스트합니다.

공공데이터포털은 사용할 API 서비스별로 활용신청 및 승인 여부를 확인해야 합니다. 인증키를 보유하고 있더라도 신청하지 않은 API의 접근 권한이 자동으로 부여되는 것은 아닙니다.

**2. 서울 열린데이터광장**

1. [서울 열린데이터광장](https://data.seoul.go.kr/)에 회원가입 후 로그인합니다.
2. [Open API 인증키 신청](https://data.seoul.go.kr/together/mypage/actkeyMain.do) 페이지에 접속합니다.
3. **일반 인증키 신청**을 선택합니다.
4. 신청 정보를 입력하고 발급을 신청합니다.
5. **인증키 관리** 메뉴에서 발급된 인증키를 확인합니다.
6. 사용할 데이터의 상세 페이지에서 Open API 서비스명과 요청 매개변수를 확인합니다.
7. 발급받은 인증키와 서비스명을 이용해 호출을 테스트합니다.

서울 열린데이터광장의 일반 인증키는 여러 일반 Open API에서 사용할 수 있으므로 데이터마다 별도로 신청할 필요는 없습니다. 다만 실시간 지하철 API 등 일부 서비스는 별도 인증키가 필요합니다.

**인증키 관리 및 이용 시 주의사항**

- 발급받은 인증키는 환경변수로 관리하며 Git 저장소에 커밋하지 않습니다.
- API 인증키를 프론트엔드 코드에 포함하지 않고 서버 측에서 관리합니다.
- API별 요청 제한, 이용조건, 제공 기간 및 데이터 갱신 주기를 확인합니다.
- 서울 열린데이터광장 API는 일반적으로 한 번에 최대 1,000건을 조회하므로 데이터가 많다면 구간을 나누어 요청합니다. 개별 API의 제한은 별도로 확인합니다.
- 행정동·상권 경계처럼 파일 형태로 제공되는 데이터는 API 인증키 없이 다운로드할 수 있는지 별도로 확인합니다.

※ 데이터별 집계 단위, 기준 시점, 갱신 주기, 좌표계가 다르므로 비교·결합 전에 확인해야 합니다. 추정매출과 인구 통계는 실제 매장 매출이나 창업 성공 가능성을 보장하지 않습니다.

## 아키텍처

현재 구상 중인 아키텍처입니다. 실제 시스템 구성과 세부 기술은 구현 과정에서 변경될 수 있습니다.

### 전체 구성

```mermaid
flowchart TB
    USER(["사용자"])

    FE["Frontend<br/>React · TypeScript · Kakao Maps"]
    BE["Backend<br/>Spring Boot"]
    DB[("PostgreSQL + PostGIS")]

    SOURCE["공공데이터<br/>공공데이터포털 · 서울 열린데이터광장"]
    ETL["ETL<br/>Node.js · TypeScript"]

    USER --> FE
    FE <-->|REST API| BE
    BE <-->|데이터 조회 · 점수 산출| DB

    SOURCE -->|수집| ETL
    ETL -->|검증 · 변환 · 적재| DB
```

프론트엔드는 Kakao Maps JavaScript SDK를 이용해 지도를 표시하고, 백엔드 API를 통해 서비스에 필요한 상권 데이터와 창업 환경 점수를 조회하는 방향으로 구성합니다.

ETL은 외부 공공데이터를 수집·검증·변환한 후 PostgreSQL에 적재하는 역할을 담당합니다.

### 구성 요소별 역할

| 구성 요소          | 주요 역할                                                                             |
| ------------------ | ------------------------------------------------------------------------------------- |
| Frontend           | 메인 페이지, 지도 탐색, 검색·필터, 창업 환경 점수, 상세 분석 및 후보지 비교 UI        |
| Backend            | REST API 제공, 검색 조건 처리, 행정구역·위치 기반 데이터 조회, 점수 산출 및 응답 구성 |
| Database           | 카페 위치, 행정구역 경계, 상권 통계, 평가 결과 및 관련 데이터 저장                    |
| PostGIS            | 특정 위치와 행정구역의 공간 관계 판정, 반경 검색 및 경계 교차 영역 조회               |
| ETL                | 공공데이터 수집, 응답 검증, 데이터 정제·변환 및 DB 적재                               |
| 외부 데이터 제공처 | 카페 위치와 서울시 상권 관련 공공데이터 제공                                          |

### 주요 데이터 흐름

**1. 공공데이터 수집 및 적재**

1. ETL이 외부 공공데이터 API 또는 제공 파일에서 데이터를 수집합니다.
2. 외부 데이터의 형식과 필수 값을 검증합니다.
3. 날짜, 행정구역 코드, 좌표계, 업종 분류 등 필요한 항목을 정제·변환합니다.
4. 데이터의 기준 시점과 출처를 관리하면서 PostgreSQL에 적재합니다.
5. 적재된 데이터가 API 조회와 점수 계산에 사용할 수 있는 상태인지 검증합니다.

**2. 지역 탐색 및 상권 조회**

1. 사용자가 프론트엔드에서 구·행정동 또는 특정 장소를 선택합니다.
2. 프론트엔드는 선택한 지역과 탐색 조건을 백엔드 API에 전달합니다.
3. 백엔드는 필요한 경우 PostGIS를 사용해 탐색 반경과 행정구역 경계의 관계를 확인합니다.
4. 해당 조건에 맞는 카페 위치와 상권 통계를 조회합니다.
5. 프론트엔드는 응답받은 데이터를 지도, 상세 패널, 차트 및 표로 표시합니다.

**3. 창업 환경 점수 제공**

1. 백엔드는 선택한 구 또는 행정동의 점수 산출에 필요한 데이터를 확보합니다.
2. 검증된 평가 알고리즘을 적용해 창업 환경 점수와 항목별 결과를 산출합니다.
3. 최종 점수, 평가 지역, 기준 시점, 평가 항목 및 산출 근거를 API 응답으로 제공합니다.
4. 프론트엔드는 최종 점수를 먼저 표시하고, 사용자가 요청한 경우 상세 산출 근거를 보여줍니다.

점수 계산은 데이터 적재 후 사전 계산하는 방식을 우선 검토하고 있습니다. 실제 계산 시점과 결과 저장 방식은 평가 알고리즘을 설계한 뒤 확정할 예정입니다.

### 설계 시 고려사항

- **집계 단위 구분:** 반경 내 점포 정보와 행정구역 전체의 통계를 혼동하지 않도록 데이터 모델과 API 응답을 설계합니다.
- **데이터 정합성:** 서로 다른 출처의 데이터가 가진 행정구역 코드, 집계 기준 및 갱신 주기를 검증합니다.
- **점수의 재현성:** 평가 알고리즘의 버전, 적용 가중치 및 사용 데이터 기준 시점을 관리하는 방향으로 설계합니다.
- **보안:** 외부 공공데이터 인증키와 데이터베이스 접속 정보는 서버 측 환경변수 등으로 관리합니다.
- **검증:** ETL 데이터 검증, 점수 계산 단위 테스트, 데이터베이스 공간 조회 통합 테스트를 고려합니다.

## 데이터베이스 및 ETL 설계

핵심 공공데이터 5종의 기본 검증을 바탕으로 PostgreSQL·PostGIS의 Flyway V1~V4 스키마와 행정동·자치구 경계·서비스 업종·점포·추정매출·유동인구 통계 ETL을 구현했습니다. 경계·업종 기준 데이터와 점포·추정매출·유동인구 통계는 로컬 개발 DB에 실제 적재했습니다. 카페 ETL도 실제 인증 응답 검증·21,996건 적재·재실행 검증을 완료했으며, 후속 데이터 모델 구현은 남아 있습니다.

**아래 내용은 현재 구현과 후속 설계안을 함께 설명합니다.** V1~V4 테이블·제약조건·인덱스와 경계·서비스 업종·점포·추정매출·유동인구 통계 ETL은 구현했으며, 미구현 테이블의 상세 스키마와 후속 데이터 갱신 정책은 구현 전에 확정할 예정입니다.

- 행정동 이름은 중복될 수 있으므로 고유 식별자로 사용하지 않습니다.

- 원본 통계의 세부 합계는 반올림 및 집계 기준 차이로 전체 값과 정확히 일치하지 않을 수 있습니다.
- 서로 다른 데이터 제공처의 카페 수는 업종 분류·수집 범위·기준 시점 차이로 일치하지 않을 수 있습니다.
- 행정동 경계와 과거 통계의 기준 시점이 다를 수 있으므로 행정구역 변경 이력을 고려해야 합니다.

기본 검증은 일회성 분석으로 수행했습니다. 이후 경계 ETL로 원본 Shapefile의 행정동 425개와 이를 결합한 자치구 25개를 로컬 개발 DB에 적재했으며, 유효 425건·거부 0건과 동일 원본 재실행 시 `SKIPPED` 처리를 확인했습니다. 서비스 업종 ETL에서는 점포 211,832행과 추정매출 100,431행을 교차 검증해 고유 업종 100개를 적재했고, `CS100010`(커피-음료)과 동일 원본 재실행 시 `SKIPPED` 처리를 확인했습니다. 점포 통계 ETL로 같은 점포 원본의 211,832행을 V3에 적재했으며, `20251`~`20262`의 6개 분기와 재실행 `SKIPPED`를 확인했습니다. 추정매출 통계 ETL도 로컬 개발 DB에 100,431행 적재를 완료했습니다. 유동인구 ETL은 격리 DB에서 NUMERIC 정밀도·롤백·재실행을 검증한 뒤 로컬 개발 DB에 9,350행을 실제 적재했습니다. 22개 분기·425개 행정동, 거부 0행이며, 동일 원본 재실행 시 `SKIPPED`와 기존 출처 보존을 확인했습니다. 이 건수는 검증한 입력 버전의 결과입니다. 카페 ETL은 실제 API의 카페 분류·응답 형식을 확인하고 21,996건을 `PUBLISHED`로 적재했습니다. 재실행은 `SKIPPED`였으며 21,996행 모두 기존 게시 배치의 `source_batch_id`를 유지했습니다.

### 주요 설계 원칙

**1. 행정구역 및 식별자**

- 자치구와 행정동을 별도 테이블로 관리합니다.
- 행정동 이름이 아닌 행정동 코드를 기준으로 관련 통계를 연결합니다.
- 원본 행정구역 코드의 형식을 유지하고 외래키로 데이터 정합성을 관리합니다.
- 서울시 서비스 업종 코드와 소상공인시장진흥공단 업종 코드는 별도로 관리합니다.

**2. 통계 데이터**

- 점포·추정매출은 `분기 + 행정동 + 업종` 단위로 저장합니다.
- 길단위인구는 `분기 + 행정동` 단위로 저장합니다.
- 개업률·폐업률은 원본 집계 방식에 따라 100%를 초과할 수 있으므로 일률적인 상한을 적용하지 않습니다.
- V3의 점포 수·매출액·매출 건수는 `BIGINT`, 비율·추정 유동인구는 정밀도 손실을 피하기 위해 `NUMERIC`으로 저장합니다.
- 실제 값이 `0`인 경우와 데이터가 제공되지 않은 경우를 구분합니다.
- 서로 다른 집계 단위의 통계를 결합할 때 중복 집계되지 않도록 처리합니다.

**3. 공간 데이터**

- 경계 ETL은 원본 행정동 경계의 EPSG:5181 좌표계를 검증하고, EPSG:4326으로 변환해 DB에 저장합니다.
- 자치구 경계는 같은 자치구에 속한 행정동 경계를 결합해 생성합니다.
- 행정동 경계와 개별 카페 위치는 PostGIS 공간 컬럼으로 저장합니다.
- 주변 카페 조회에는 미터 단위 반경 검색과 행정구역 경계 판정을 활용합니다.
- 공간 검색에 필요한 GiST 인덱스를 적용하고 실제 조회 성능에 따라 추가 인덱스를 검토합니다.

**4. 개별 카페와 행정동 통계의 구분**

- 개별 카페 위치는 소상공인시장진흥공단의 상가(상권)정보를 기반으로 관리합니다.
- 행정동별 카페 점포 통계는 서울시 상권분석서비스의 별도 집계값으로 관리합니다.
- 두 데이터의 카페 수가 일치하지 않더라도 동일한 데이터로 간주하거나 임의로 보정하지 않습니다.
- 반경 내 카페 정보와 행정동 전체의 점포·매출·유동인구 통계를 구분해 제공합니다.
- 개별 카페가 최신 수집 결과에서 누락되었다는 이유만으로 폐업했다고 판단하지 않습니다.

**5. 평가 결과의 재현성**

- 창업 환경 점수는 구 또는 행정동 단위로 계산합니다.
- 점수 계산에 사용한 데이터의 기준 시점과 알고리즘 버전을 관리합니다.
- 가중치, 정규화 기준, 입력 지표, 항목별 점수 등 산출 근거를 보존하는 방향으로 설계합니다.
- 필요한 통계가 누락된 경우 임의의 값을 채워 점수를 계산하지 않습니다.
- 여러 자치구의 점수를 합산하거나 서로 다른 집계 단위의 점수를 동일한 기준으로 비교하지 않습니다.

### ETL 처리 방향

행정동·자치구 경계·서비스 업종·점포·추정매출·유동인구 통계 ETL은 Node.js·TypeScript 기반으로 구현했으며, Zod로 데이터를 검증하고 node-postgres를 이용해 PostgreSQL에 적재합니다. 경계 공간 연산은 PostGIS를 사용합니다. 카페 ETL도 같은 기술 스택과 Node.js 내장 fetch를 사용합니다. 아래 처리 흐름과 갱신 원칙은 전체 ETL의 설계 방향입니다.

**처리 흐름**

1. **수집:** 공공데이터 API 또는 제공 파일에서 원본 데이터를 가져옵니다.
2. **검증:** 데이터 형식, 필수 값, 중복, 코드, 수치, 좌표 및 수집 범위를 확인합니다.
3. **변환:** 날짜·업종·행정구역 코드와 좌표계를 서비스 데이터 모델에 맞게 변환합니다.
4. **임시 적재:** 검증한 데이터를 스테이징 영역에 적재합니다.
5. **최종 검증:** 전체 수집 여부, 데이터 건수, 고유성, 외래키 및 기존 데이터와의 차이를 확인합니다.
6. **DB 반영:** 검증에 성공한 데이터만 트랜잭션으로 서비스 테이블에 반영합니다.
7. **이력 기록:** 수집 출처, 기준 기간, 적재 결과 및 오류를 ETL 배치 단위로 기록합니다.

**데이터 갱신 및 실패 처리**

- 동일한 분기·행정동·업종 조합은 중복 저장하지 않습니다.
- 기존 분기의 수정 데이터는 수집 범위와 유효성을 검증한 후 갱신합니다.
- API 일부 페이지만 수집한 경우 기존 서비스 데이터를 유지합니다.
- 전체 스냅샷 수집이 성공한 경우에만 기존 데이터와의 삭제·누락 차이를 검토합니다.
- 행정동 경계 변경이 발견되면 관련 통계에 미치는 영향을 확인한 후 반영합니다.
- 수집·검증에 실패한 데이터는 기존 정상 데이터를 대체하지 않습니다.
- 원본 데이터와 적재 결과의 출처, 기준 시점 및 버전을 확인할 수 있도록 관리합니다.

경계·서비스 업종·점포·추정매출·유동인구 통계 ETL은 임시 스테이징, 트랜잭션 반영·롤백, 배치 이력, 동일 원본 재실행 및 기존 데이터 보존 처리를 구현했습니다. 나머지 ETL의 구체적인 스테이징·트랜잭션·재실행·보존 정책은 해당 ETL 구현 전에 확정할 예정입니다.

### DB 마이그레이션 방향

DB 스키마는 Flyway를 이용해 관리합니다.

`V1__enable_postgis.sql`은 PostGIS 확장을 활성화하고, `V2__create_core_tables.sql`은 ETL 이력·자치구·행정동·서비스 업종 테이블과 제약조건·인덱스를 생성합니다. `V3__create_dong_stat_tables.sql`은 행정동별 점포·추정매출·유동인구 통계 테이블을 생성하고, `V4__create_cafe_store.sql`은 개별 카페 테이블과 조회 인덱스를 생성합니다.

현재 마이그레이션 구성과 후속 구현 계획은 다음과 같습니다.

| 단계 | 주요 내용                              |
| ---- | -------------------------------------- |
| V1   | PostGIS 확장 활성화 (구현 완료)        |
| V2   | ETL 이력 및 행정구역·업종 기준 테이블 (구현 완료) |
| V3   | 점포·추정매출·길단위인구 통계 테이블 (구현 완료) |
| V4   | 개별 카페 및 공간 검색 인덱스 (구현·격리 DB 검증·개발 DB 적용 완료) |
| 이후 | 평가 알고리즘 확정 후 점수 관련 테이블 |

Flyway는 테이블, 제약조건, 인덱스 등 DB 스키마 변경을 관리합니다. 경계 파일·서비스 업종 기준 데이터·점포·추정매출·유동인구 통계 적재는 별도 ETL로 구현했으며, 카페 데이터도 별도 API ETL로 실제 인증 검증·수집·21,996건 적재를 완료했습니다.

#### V3 통계 컬럼과 저장 정책

서울 열린데이터광장의 [점포-행정동](https://data.seoul.go.kr/dataList/OA-22172/S/1/datasetView.do?tab=A), [추정매출-행정동](https://data.seoul.go.kr/dataList/OA-22175/S/1/datasetView.do?tab=A), [길단위인구-행정동](https://data.seoul.go.kr/dataList/OA-22178/S/1/datasetView.do?tab=A) 컬럼 설명과 공개 API 표본을 확인했습니다. 공통 분기 필드는 `STDR_YYQU_CD`이며, DB의 `quarter_code`에는 `20261`처럼 연도 4자리와 분기 1~4를 저장합니다.

- 점포·매출의 기본키는 `(dong_code, industry_code, quarter_code)`, 유동인구는 `(dong_code, quarter_code)`입니다. 행정동·업종 및 수집 출처인 `source_batch_id`는 기존 기준 테이블을 참조하며 필수 값입니다. 추가 인덱스는 만들지 않고 기본키 인덱스를 사용합니다.
- [매출 API 표본](http://openapi.seoul.go.kr:8088/sample/json/VwsmAdstrdSelngW/1/5/)에는 7,081,380,548원처럼 32비트 정수 범위를 넘는 금액이 있습니다. 정수 의미 값도 `.0`이나 지수 표기로 반환됩니다. 원천의 ‘당월’ 필드명과 분기 기준을 그대로 유지하며 월평균으로 환산하지 않습니다.
- [유동인구 API 표본](http://openapi.seoul.go.kr:8088/sample/json/VwsmAdstrdFlpopW/1/5/)에서 확인한 값은 정수였지만, 공식 스키마에 정수 보장이나 반올림 규칙은 없습니다. 비율·추정 유동인구는 소수부를 임의로 손실시키지 않도록 고정 정밀도·소수 자릿수 없는 `NUMERIC`을 선택했습니다.
- 모든 측정값은 NULL을 허용하고 기본값을 두지 않습니다. 누락·빈 값을 임의로 `0`으로 채우지 않으며 실제 `0`과 구분합니다. 저장되는 값은 유한한 0 이상 수여야 합니다.
- 개업률·폐업률의 100% 초과를 허용하고, 전체·세부 수치의 합계 일치를 강제하지 않습니다. 유동인구 표본에서도 전체와 성별 합계가 1명 차이 나는 경우를 확인했습니다.

#### V4 카페 컬럼과 후속 ETL 계약

`cafe_store`는 소진공 원본 식별자와 위치를 저장합니다. V4 스키마는 개발 DB 적용을 완료했습니다. 카페 ETL은 모의 API·격리 DB 테스트와 실제 API 검증을 거쳐 개발 DB에 21,996건을 적재했습니다. 재실행 `SKIPPED`와 기존 게시 출처 보존도 확인했습니다. 조회 API는 아직 구현하지 않았습니다.

| DB 컬럼 | 원천 필드 | 저장 정책 |
| --- | --- | --- |
| `bizes_id` | `bizesId` | `VARCHAR(20)` PK, 공백 없는 원본 문자열; 숫자 변환·접두사 고정 없음 |
| `store_name`, `branch_name` | `bizesNm`, `brchNm` | 상호명 필수, 지점명 선택 · `TEXT` |
| `semas_industry_code`, `semas_industry_name` | `indsSclsCd`, `indsSclsNm` | 소진공 업종 코드·명칭 필수 · `VARCHAR(8)`, `TEXT` |
| `ksic_code`, `ksic_name` | `ksicCd`, `ksicNm` | 별도 표준산업분류, 선택 · `VARCHAR(6)`, `TEXT` |
| `source_dong_code` | `adongCd` | 원본 숫자 문자열, 선택 · `VARCHAR(20)` |
| `dong_code` | 검증한 `adongCd` | 정확한 8자리이며 기준 테이블에 존재하는 경우만 FK 연결, 그 외 NULL |
| `road_address`, `lot_address` | `rdnmAdr`, `lnoAdr` | 선택 · `TEXT` |
| `geom` | `lon`, `lat` | 선택 · `GEOMETRY(Point,4326)`, 경도·위도 순서 |
| `source_batch_id` | ETL 배치 ID | 필수 · `etl_batch` FK |

- 서울시 `service_industry`와 소진공 업종은 별도 체계이며 두 테이블 사이에 업종 FK를 만들지 않습니다. 특정 카페 코드를 SQL에 고정하지 않았습니다. 카페 ETL은 실행 시 공식 분류 API와 인증된 업소 응답에서 코드·명칭·기준년월을 검증하며, 미검증 분류는 게시하지 않습니다.
- 필수 값과 선택 TEXT 값이 공백만 있는 경우를 거부합니다. 카페 ETL은 선택 항목의 빈 값을 NULL로 정규화합니다. 업종 코드는 공백 없는 영문 대문자·숫자로 저장하되 실제 코드 목록의 소속 여부는 SQL이 보장하지 않습니다.
- 원본 행정동 코드는 임의로 절단하지 않습니다. 미연결 코드는 원본에 남기고 `dong_code=NULL`로 보존합니다. FK가 있으면 원본 코드도 존재하며 같아야 합니다. 원본 코드가 변경되거나 연결에 실패한 갱신에서는 이전 FK를 그대로 남기지 않습니다.
- 좌표가 모두 없으면 `geom=NULL`로 보존하고 지도 검색에서 제외합니다. 일부만 있거나 잘못된 좌표는 카페 ETL에서 오류로 처리합니다. DB는 제공된 Point의 SRID·차원·비어 있지 않음·유효성 및 경도 `[-180,180]`·위도 `[-90,90]` 범위를 검증하며 NaN·무한대를 허용하지 않습니다. 주소나 행정동 대표점을 실제 좌표 대신 넣지 않습니다.
- 행정동 경계와 좌표의 불일치는 공간 진단 대상으로 남기고 자동 보정하지 않습니다. 행정동·좌표가 모두 누락된 행도 보관할 수 있으나, 서울 소속은 API의 명시적인 서울 요청 조건과 응답 행정구역 코드로 검증합니다.
- PK 외에는 최신 배치·행정동 조회용 B-tree `(source_batch_id, dong_code)`, 지도 영역용 GiST `(geom)`, 미터 반경용 GiST `((geom::geography))`를 생성합니다. 반경은 `ST_DWithin(geom::geography, 중심점::geography, 미터)`로 판정하며 geometry 인덱스만으로 geography 조회까지 지원한다고 가정하지 않습니다. 실제 성능 검증은 후속 조회 구현에서 진행합니다.

**서울 전체 최신 목록을 위한 ETL 계약**

1. `SEMAS_CAFE_STORE` 데이터셋의 게시 단위는 **서울 전체의 완전한 수집**입니다. `source_type='API'`, `scope_type='SEOUL'`, `scope_code=NULL`을 사용합니다. 검증된 JSON 문자열을 `source_reference` TEXT에 기록하고, `collection_mode='FULL_SEOUL'`, `complete=true`, 엔드포인트·허용된 요청 조건·원천 기준년월·분류 버전·페이지 및 품질 건수를 포함합니다. API 키와 키가 포함된 URL·오류는 기록하지 않습니다. 원천 `YYYYMM`은 분기 컬럼에 넣지 않고 `period_from/to`는 NULL로 둡니다.
2. 모든 페이지·원천 건수·중복 업소번호·분류 및 범위·기준년월을 검증하고, 스테이징의 실제 건수를 대조한 뒤 Upsert와 `PUBLISHED`를 한 트랜잭션으로 확정합니다. 일부 행정동·반경 표본·페이지 누락·실패 수집은 이 데이터셋의 `PUBLISHED`나 전체 목록으로 취급하지 않으며 `cafe_store`에 반영하지 않습니다. 페이지·건수 검사는 원천 API의 동시 갱신까지 원자적인 스냅샷이라고 보장하지 않습니다.
3. 새 `PUBLISHED`에서는 수집한 **모든 업소**의 `source_batch_id`를 새 배치로 연결합니다. 값이 동일한 행도 포함합니다. 최신 목록은 해당 데이터셋·서울 범위·완전 수집 메타데이터를 충족하는 최신 `PUBLISHED` 배치를 선택한 뒤, 그 배치를 참조하는 행만 조회합니다. 테이블 전체나 가장 최근 실행 배치를 그대로 전체 목록으로 사용하지 않습니다.
4. `SKIPPED`는 완전한 동일 원본과 실제 DB 값·출처가 일치할 때만 기록하고 기존 정상 행의 출처를 유지합니다. `SKIPPED`, `RUNNING`, `FAILED`는 최신 목록 기준 배치를 대체하지 않습니다. 입력에서 누락된 기존 업소는 삭제하거나 폐업으로 단정하지 않으며, 이전 배치의 행으로 보존하고 최신 목록과 구분합니다.

이 계약의 수집·검증·게시·재실행은 카페 ETL이 담당합니다. V4의 FK·CHECK가 배치 상태까지 강제하지는 않으며, 향후 조회 코드도 위 최신 목록 조건을 준수해야 합니다.

## 배포 구조

로컬 개발용 PostgreSQL·PostGIS는 Docker Compose로 실행합니다. 서비스 전체의 컨테이너 배포는 후속 단계에서 검토할 예정입니다.

클라우드 환경은 AWS EC2 또는 다른 클라우드 서비스를 후보로 두고 있으며, Nginx와 CI/CD 도입도 고려 중입니다.

**아직 실제 배포 환경이나 배포 자동화는 구성되지 않았습니다.**

### 배포 구성안

```mermaid
flowchart TB
    USER(["사용자"])
    GITHUB["GitHub Repository"]
    CICD["GitHub Actions<br/>CI/CD"]

    subgraph SERVER["클라우드 서버 · Docker Compose"]
        direction TB
        NGINX["Nginx<br/>React 정적 파일 · HTTPS"]
        API["Spring Boot API"]
        DB[("PostgreSQL + PostGIS")]
        ETL["ETL 작업"]

        NGINX -->|"/api"| API
        API -->|데이터 조회| DB
        ETL -->|데이터 적재| DB
    end

    SOURCE["외부 공공데이터 API"]

    USER -->|HTTPS| NGINX
    GITHUB -.-> CICD
    CICD -.->|배포| SERVER
    SOURCE -->|데이터 수집| ETL
```

위 구성은 배포 방향을 설명하기 위한 예시입니다. 실제 환경에서는 프론트엔드 정적 파일 제공 방식, 데이터베이스 호스팅 위치, ETL 실행 방법 및 보안 구성을 별도로 결정할 예정입니다.

ETL은 인자 없이 실행하면 사용법을 표시하며, `boundaries` 명령으로 행정동·자치구 경계를, `industries` 명령으로 서비스 업종 기준 데이터를, `stores` 명령으로 점포 통계를, `sales` 명령으로 추정매출 통계를, `foot-traffic` 명령으로 유동인구 통계를 적재할 수 있습니다. `cafes` 명령은 공식 분류와 서울 전체 API 응답 검증 후 카페를 적재합니다.

공공데이터 기본 검증, Flyway V1~V4 구현, Docker Compose 기반 로컬 PostgreSQL·PostGIS 환경 및 경계·업종·점포·추정매출·유동인구 통계 ETL의 실제 적재(행정동 425개·자치구 25개·업종 100개·점포 통계 211,832행·추정매출 통계 100,431행·유동인구 통계 9,350행)를 완료했습니다. V4 개발 DB 적용과 카페 ETL의 실제 API 검증·21,996건 적재·재실행 `SKIPPED` 확인도 완료했습니다. 행정구역 조회 API를 구현했으며, 나머지 서비스 기능·전체 컨테이너 배포·CI/CD는 남아 있습니다.

## 실행 방법

### 1. 개발 도구

- Node.js **24 LTS**, npm **11**: `frontend/`, `etl/`에서 각각 `nvm use`와 `npm ci`를 실행합니다. 두 프로젝트는 독립적인 잠금 파일을 사용합니다.
- Java **21**: 백엔드는 포함된 Gradle Wrapper(`./gradlew`, Windows는 `gradlew.bat`)를 사용합니다.
- Docker와 Docker Compose: 로컬 PostgreSQL/PostGIS DB 및 백엔드 DB 통합 테스트에 사용합니다. Backend·ETL은 호스트에서 실행합니다.

#### 로컬 DB 준비

기본 로컬 개발 환경에서는 저장소 루트의 `.env.example`만 `.env`로 복사하면 됩니다. 루트 `.env`는 Docker Compose·Backend·ETL의 공통 DB 설정에 사용합니다.

- `backend/.env.example`: Backend를 독립적인 DB 환경에서 실행할 때 참고합니다. 기본 환경에서는 복사할 필요가 없습니다.
- `etl/.env.example`: ETL을 별도로 설정할 때만 사용합니다. `etl/.env`가 별도로 있으면 Node.js가 해당 파일도 읽으므로, 공통 DB 설정을 사용할 때는 불필요한 중복 설정을 피합니다.
- `frontend/.env.example`: Vite의 API 프록시 주소를 기본값인 `http://localhost:8080`과 다르게 설정할 때만 `frontend/.env`로 복사합니다.

저장소 루트에서 실행합니다.

```bash
cp .env.example .env
# .env의 로컬 DB 이름·사용자·비밀번호·포트를 설정합니다.
docker compose config --quiet
docker compose up -d --wait db
docker compose ps db
```

DB 이미지는 Testcontainers와 동일한 `postgis/postgis:17-3.5`입니다. `DB_PORT`의 기본값은 `5432`이며 `127.0.0.1`에만 공개합니다. 이미 사용 중인 포트이면 `.env`의 `DB_PORT`를 변경합니다. 실제 `.env`는 Git에서 제외되며, 예시 비밀번호는 로컬 개발용입니다.

Docker Compose는 루트 `.env`를 자동으로 읽지만, Backend·ETL은 자동으로 읽지 않습니다. Backend·ETL을 실행할 터미널마다 저장소 루트에서 아래 명령으로 환경변수를 먼저 내보냅니다. 두 연결 URL은 같은 `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_PORT`에서 구성됩니다. 비밀번호에 URL 예약 문자를 사용한다면 `DATABASE_URL`의 비밀번호 부분을 URL 인코딩한 값으로 지정합니다.

```bash
set -a
source .env
set +a
```

DB에 접속하거나 PostgreSQL·PostGIS 동작을 확인하려면 다음 명령을 사용합니다. `psql`은 컨테이너에 포함되어 있습니다. 호스트 DB 도구에서는 `127.0.0.1`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`를 사용합니다.

```bash
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

```sql
SELECT version(), PostGIS_Version();
SELECT ST_SRID(ST_SetSRID(ST_MakePoint(127, 37), 4326));
```

`\q`로 접속을 종료합니다. DB 데이터는 named volume `recycleyoungs_postgres_data`에 유지됩니다. 초기화된 볼륨에서는 `.env`의 DB 이름·사용자·비밀번호를 바꿔도 기존 DB 계정과 데이터가 자동 변경되지 않습니다.

```bash
docker compose stop db        # 종료, 컨테이너·볼륨 유지
docker compose up -d --wait db # 다시 실행
docker compose restart db     # 재시작, 데이터 유지
```

일반적인 종료·재시작에는 볼륨을 삭제하는 옵션을 사용하지 않습니다. 아래 Backend의 `db` 프로필을 실행하면 V1·V2·V3·V4가 적용됩니다. V4의 개발 DB 적용은 완료된 상태입니다. 재시작 전후에 `flyway_schema_history`를 조회하면 마이그레이션 이력의 유지를 확인할 수 있습니다. 기존 Testcontainers 통합 테스트는 Compose와 독립된 일회용 DB를 계속 사용합니다.

### 2. Frontend

```bash
cd frontend
nvm use
npm ci
npm run dev
```

[http://localhost:5173](http://localhost:5173)에서 준비 화면을 확인합니다. `npm run build`는 타입 검사 후 정적 파일을 `dist/`에 생성하고, `npm run preview`로 빌드 결과를 확인할 수 있습니다.

`frontend/.env.example`을 `.env`로 복사하면 API 프록시 대상을 바꿀 수 있습니다. 생략하면 `/api` 요청을 `http://localhost:8080`으로 전달합니다. 프론트엔드의 실제 API 호출은 아직 구현하지 않았습니다. `API_PROXY_TARGET`은 Vite 개발 서버 전용입니다. 프론트엔드의 `VITE_*` 변수는 브라우저에 공개되므로 비밀정보를 넣지 않습니다.

Tailwind CSS 4와 shadcn/ui 설정 및 기본 Button 컴포넌트가 포함되어 있습니다. 추가 UI는 `frontend/`에서 `npx shadcn@latest add <컴포넌트>`로 설치할 수 있습니다.

### 3. Backend

```bash
cd backend
./gradlew bootRun
```

기본 포트는 **8080**입니다. 기본 실행은 DataSource·JdbcClient·Flyway 없이 가능하며, 행정구역 API는 `db` 프로필에서만 활성화됩니다. 루트 경로의 **404 응답은 정상**입니다. DB 조회 기반은 Spring JDBC·JdbcClient로 구성했습니다.

Compose DB를 사용할 때는 위에서 루트 `.env`를 셸에 내보낸 뒤 실행합니다. Spring Boot는 `.env`를 자동으로 읽지 않습니다.

```bash
cd backend
./gradlew bootRun --args='--spring.profiles.active=db'
```

`application-db.yaml`은 기존 `DB_JDBC_URL`, `DB_USER`, `DB_PASSWORD`로 서비스용 Hikari DataSource와 JdbcClient를 구성합니다. Flyway는 같은 DB 설정을 별도의 전용 연결로 사용합니다. 운영에서 계정을 분리하려면 `spring.datasource.*`와 `spring.flyway.*`를 각각 외부 설정으로 지정합니다. `db` 프로필 시작 시 Flyway가 V1·V2·V3·V4를 순서대로 적용하고, 이미 적용된 마이그레이션은 다시 실행하지 않습니다. Compose DB는 PostGIS 확장을 포함합니다. 외부 로컬 DB를 직접 준비하는 경우에는 `backend/.env.example`을 참고하고 PostGIS 설치 및 확장 생성 권한을 확인합니다.

공통 오류 응답은 `application/problem+json`의 ProblemDetail이며 `type`, `title`, `status`, `detail`, `instance`와 서비스 오류 `code`를 제공합니다. 예외 원문·SQL·접속 정보와 거부된 입력값은 포함하지 않습니다.

| 오류 코드 | HTTP 상태 | 처리 대상 |
| --- | --- | --- |
| `INVALID_PARAMETER` | 400 | 필수 파라미터 누락·형식·본문 오류, 명시적인 입력 검증 실패 |
| `REGION_NOT_FOUND` | 404 | 서비스에서 명시적으로 판정한 지역 미존재 |
| `DATA_NOT_READY` | 503 | 서비스에서 명시적으로 판정한 데이터 준비 전 상태 |
| `DATABASE_UNAVAILABLE` | 503 | DB 연결·자원 접근 실패, 조회 시간 초과 |
| `INTERNAL_ERROR` | 500 | SQL 문법·매핑·무결성 오류 및 예상하지 못한 구현 오류 |

미등록 경로의 404와 지원하지 않는 HTTP 메서드의 405 등은 MVC 상태·헤더를 유지하고 서비스 오류 코드는 붙이지 않습니다. 행정구역 조회 API는 아래 계약을 사용합니다.

| GET 엔드포인트 | 응답 |
| --- | --- |
| `/api/v1/districts` | `{items:[{districtCode,districtName}]}` |
| `/api/v1/districts/{districtCode}/dongs` | `{items:[{dongCode,districtCode,dongName,labelPoint}]}` |
| `/api/v1/districts/{districtCode}/boundary` | 자치구 GeoJSON Feature |
| `/api/v1/dongs/{dongCode}/boundary` | 행정동 GeoJSON Feature |
| `/api/v1/regions/nearby` | `{boundaryBatch,districts:[{districtCode,districtName,containsCenter}],dongs:[{dongCode,districtCode,dongName,containsCenter}]}` |

- 목록은 코드 오름차순입니다. 구 코드는 ASCII 숫자 5자리, 동 코드는 8자리 문자열로 검증하며 선행 0을 보존합니다.
- 행정동 목록의 `labelPoint`는 저장된 `administrative_dong.label_point`를 PostGIS에서 생성한 WGS84 GeoJSON Point 객체(`{type:"Point",coordinates:[경도,위도]}`)입니다. 경계 중심으로 재계산하지 않습니다.
- `SEOUL_DONG_BOUNDARY`, `SHAPEFILE`, `SEOUL`, `scope_code IS NULL`, `PUBLISHED`, `published_at IS NOT NULL`을 모두 충족하는 배치 중 `published_at → started_at → batch_id` 내림차순의 첫 배치를 사용합니다. 그 배치를 참조하는 구·동만 노출하며, 동의 부모 구도 같은 게시본이어야 합니다. `SKIPPED`·실패·과거 출처는 제외합니다.
- 경계 응답은 `application/geo+json`이며 `type="Feature"`, 문자열 `id`, PostGIS에서 생성한 WGS84(EPSG:4326) `geometry`를 제공합니다. `properties`에는 `regionType`, `regionCode`, `regionName`, `districtCode`, `boundaryBatch:{batchId,publishedAt}`을 포함합니다. 좌표는 경도·위도 순서이고 게시 시각은 ISO 8601 형식입니다.
- 형식 오류는 DB 접근 전에 400, 현재 게시본에 없는 지역은 404, 정상 게시 배치가 없으면 503입니다. 최신 게시 배치를 참조하는 구·동 경계 행이 모두 없을 때도 `DATA_NOT_READY`(503)로 처리하고 과거 배치로 대체하지 않습니다. 경계 행이 있는 게시본에서 존재하는 구에 현재 행정동이 없거나 검색 반경과 겹치지 않으면 정상 빈 목록입니다. 배치 선택과 지역 조회는 읽기 전용 `REPEATABLE_READ` 트랜잭션에서 처리합니다.

주변 행정구역 조회는 필수 `longitude`·`latitude`에 WGS84 경도 `[-180,180]`·위도 `[-90,90]`를 받습니다. `radiusM`은 생략 시 500m이며 `1~1000` 범위의 소수를 허용합니다. 좌표·반경의 NaN·무한대·빈 값과 단일 파라미터 중복은 400입니다.

`districtCodes=11110&districtCodes=11140`처럼 구 코드를 반복해 선택할 수 있습니다. 생략하면 반경 내 모든 현행 서울 지역을 검색하고 중복 코드는 제거합니다. 쉼표 목록이나 잘못된 코드는 400, 현재 게시본에 없는 지정 구는 반경과 무관하게 404입니다. 구 선택은 반경을 확장하지 않으며 행정동은 반경·선택 구·동 경계의 실제 교집합으로 판정합니다.

거리는 geography 기반 미터 단위로 계산하고 반경 접촉을 포함합니다. `containsCenter`는 해당 지역 경계의 내부 또는 경계 위에 중심점이 있는지를 뜻합니다. 구·동 목록은 각각 코드순이며 응답에 최신 `boundaryBatch:{batchId,publishedAt}`을 포함합니다. 게시본이 있어도 공간적으로 겹치지 않으면 서울 밖 좌표를 포함해 200과 두 빈 목록을 반환합니다.

Backend를 실행한 후 저장소 루트에서 DB에 접속해 다음을 확인합니다. V4까지 적용한 DB의 이력은 버전 `1`, `2`, `3`, `4`가 모두 `success = true`여야 하며, 테이블 조회는 8행을 반환해야 합니다. 아래 명령은 확인 방법이며 이번 카페 ETL 작업에서 개발 DB를 갱신하지 않습니다.

```sql
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;
SELECT tablename FROM pg_tables
WHERE schemaname = 'public'
  AND tablename IN ('etl_batch', 'district', 'administrative_dong', 'service_industry',
                    'dong_store_stat', 'dong_sales_stat', 'dong_foot_traffic_stat', 'cafe_store')
ORDER BY tablename;
```

기존 마이그레이션 파일의 수정이나 DB 초기화 없이 적용·검증합니다.

### 4. ETL

```bash
cd etl
nvm use
npm ci
npm run dev
npm run build
npm start
```

개발 실행은 TypeScript를 직접 실행하고, 빌드는 `dist/`에 JavaScript를 생성합니다. `npm start`는 빌드된 진입점을 실행합니다. 인자 없이 실행하면 사용법을 표시하며 DB에 접속하지 않습니다. 현재 구현된 적재 명령은 행정동·자치구 경계용 `boundaries`, 서비스 업종용 `industries`, 점포 통계용 `stores`, 추정매출 통계용 `sales`, 유동인구 통계용 `foot-traffic`입니다.

Compose DB를 공유하려면 위에서 루트 `.env`를 셸에 내보낸 뒤 실행합니다. 내보낸 `DATABASE_URL`은 기존 `etl/.env`보다 우선하므로 Backend와 같은 DB를 사용합니다. ETL만 별도로 설정하려면 `etl/.env.example`을 `.env`로 복사할 수 있으며, `npm run dev`와 `npm start`가 Node.js의 환경변수 파일 기능으로 읽습니다. DB 연결 시 `DATABASE_URL`, `DB_POOL_MAX`, `DB_CONNECTION_TIMEOUT_MS`를 Zod로 검증하고 `pg.Pool`을 생성하는 기반이 포함되어 있습니다. 연결 정보가 실제로 사용될 때 검증하며, 연결 풀 생성만으로 DB에 접속하지 않습니다.

**행정동·자치구 경계 적재**

로컬 DB를 실행하고 기존 Flyway 마이그레이션을 먼저 적용한 뒤, 루트 `.env`를 내보낸 셸에서 실행합니다. `DATABASE_URL`은 `localhost`, `127.0.0.1`, `::1`의 로컬 개발 DB만 허용하며, URL 쿼리로 접속 호스트를 우회할 수 없습니다.

```bash
cd etl
npm run dev -- boundaries \
  --source "/절대경로/서울시 상권분석서비스(영역-행정동).zip" \
  --expected-dongs 425 --expected-districts 25
```

빌드 결과로 실행하려면 `npm run build` 후 동일한 인자를 `npm start -- boundaries --source "/절대경로/경계.zip" --expected-dongs 425 --expected-districts 25`로 전달합니다. `npm run dev -- --help`로 사용법을 확인할 수 있습니다.

- 입력은 원본 ZIP 또는 `.shp` 경로입니다. `.shp`는 같은 이름의 `.dbf`, `.prj`, `.cpg`가 필요하며 ZIP은 메모리에서 읽습니다. 원본을 저장소에 복사하거나 커밋하지 않습니다.
- `425`행·`25`개 자치구는 기존에 검증한 입력 버전의 기준입니다. 두 건수 인자는 필수이며 다른 버전에는 해당 원본을 확인한 기준을 지정합니다.
- 현재 원본은 UTF-8이며 `ADSTRD_CD`, `ADSTRD_NM`, `XCNTS_VALU`, `YDNTS_VALU`, `RELM_AR`를 검증합니다. 원본의 `RELM_AR`는 `N(38,0)` 정수 ㎡이므로 정수 정밀도를 유지해 `area_m2`에 저장합니다. 코드 중복·빈 값·잘못된 좌표계·유효하지 않은 도형은 자동 보정하지 않습니다.
- `.prj`의 EPSG:5181 투영·타원체·단위·원점 등 실제 WKT1 매개변수를 검증합니다. PostGIS로 원본 도형의 유효성·양의 면적, 변환 후 SRID 4326·서울 인근 좌표 범위 및 대표점의 경계 내부 포함을 확인합니다. 대표점은 원본 중심 좌표 대신 `ST_PointOnSurface`로 생성합니다.
- 자치구는 행정동 코드 앞 5자리와 [행정표준코드의 서울 시군구 코드표](https://www.code.go.kr/stdcode/sggCodeIL.do?sidoCd=11&disuseAt=0&searchOk=0)를 대응하고, 행정동 경계를 결합해 생성합니다.
- 전체 검증 후 두 경계 테이블과 `PUBLISHED` 이력을 한 트랜잭션으로 반영합니다. 실패하면 경계 변경을 롤백하고 `FAILED` 이력을 별도로 기록합니다. DB 연결 자체가 불가능한 경우에는 실패 이력도 기록할 수 없습니다.
- 원본 체크섬·ETL 버전과 현재 경계·이름·면적·출처가 같으면 재실행은 `SKIPPED`로 기록합니다. 나머지는 기본키 기준으로 추가·갱신하며, 입력에 빠진 기존 코드가 있다면 삭제하지 않고 중단합니다. 유효 건수에는 검증이 끝난 행만 포함하며, 실패 시 아직 검증하지 않은 행은 유효·거부 건수에 포함하지 않습니다.

적재 결과는 저장소 루트에서 DB에 접속해 확인합니다.

```sql
SELECT batch_id, source_reference, source_checksum, status, expected_rows,
       fetched_rows, valid_rows, rejected_rows, error_message
FROM etl_batch WHERE dataset_code = 'SEOUL_DONG_BOUNDARY' ORDER BY started_at DESC;
SELECT count(*) FROM district;
SELECT count(*), bool_and(ST_SRID(geom) = 4326 AND ST_SRID(label_point) = 4326
       AND ST_IsValid(geom) AND ST_Contains(geom, label_point) AND area_m2 > 0)
FROM administrative_dong;
```

파일·CLI 단위 테스트는 기존 `npm test`에 포함됩니다. DB 회귀 테스트는 합성 데이터를 새 일회용 PostGIS 컨테이너에서만 사용하며 기존 개발 DB는 변경하지 않습니다. Docker가 실행 중일 때 `etl/`에서 `RUN_BOUNDARY_DB_TESTS=1 npm test -- src/boundaries.integration.test.ts`로 실행합니다. 이 테스트는 원본의 실제 적재 검증을 대신하지 않습니다.

**서비스 업종 기준 데이터 적재**

루트 `.env`를 내보낸 터미널에서 실행합니다. 점포 CSV가 기본 원본이고 `--sales-source`는 선택입니다. 두 원본을 함께 쓰면 매출에만 있는 유효한 업종도 합집합에 포함하며, 같은 코드의 명칭이 다르면 반영하지 않습니다. 통계 수치는 이번 명령에서 적재하지 않습니다.

```bash
cd etl
npm run dev -- industries \
  --source "$HOME/Downloads/서울시 상권분석서비스(점포-행정동).csv" \
  --sales-source "$HOME/Downloads/서울시 상권분석서비스(추정매출-행정동).csv" \
  --expected-industries 100
```

빌드 결과는 `npm run build` 후 위 명령의 `npm run dev --`를 `npm start --`로 바꿔 실행합니다. 파일 경로와 필수 `--expected-industries`는 입력 버전에 맞게 지정합니다. `100`은 검증한 두 원본의 합집합 기준이며 코드에 고정하지 않습니다.

- CSV 또는 CSV가 정확히 하나 들어 있는 ZIP을 지원합니다. ZIP은 메모리에서 읽고 무결성을 확인하며 원본을 저장소에 복사하거나 디스크에 압축 해제하지 않습니다.
- 실제 원본은 CP949이며 `서비스_업종_코드`·`서비스_업종_코드_명`을 사용합니다. UTF-8(BOM 포함)과 API 형식의 `SVC_INDUTY_CD`·`SVC_INDUTY_CD_NM` 헤더도 지원합니다. CSV의 인용부호·쉼표·개행을 파서로 처리합니다.
- 코드는 `CS`와 숫자 6자리입니다. 빈 값·앞뒤 공백·손상된 명칭·모호한 헤더·열 수 오류를 거부하며, 동일 코드·명칭의 반복은 허용합니다. 동일 코드의 명칭 충돌은 원본 내부와 두 원본 사이 모두 실패 처리합니다.
- 전체 검증 후 업종과 `PUBLISHED` 이력을 한 트랜잭션으로 반영합니다. 실패하면 업종 변경을 롤백하고 `FAILED` 이력을 남깁니다. DB 연결 자체가 불가능하면 이력을 기록할 수 없습니다. 입력에서 빠진 기존 업종은 삭제하지 않습니다.
- 원본 역할·CSV 바이트로 체크섬을 계산합니다. 경로·ZIP 포장만 바뀌어도 같은 원본으로 판단하며, 체크섬·ETL 버전과 현재 입력 업종의 명칭·출처가 모두 같을 때만 `SKIPPED` 처리합니다.
- `fetched_rows`, `valid_rows`, `rejected_rows`는 두 CSV의 원본 행 수 기준입니다. 실패하면 중단 시점까지 확인한 행만 셉니다. 고유 업종 수와 원본별 행 수·인코딩은 CLI 결과와 `source_reference` JSON에서 구분하며, 예상 고유 업종 수를 `expected_rows`에 넣지 않습니다(`NULL` 유지).

현재 원본으로 점포 211,832행·100개 업종과 매출 100,431행·63개 업종을 검증해, 유효 312,263행·거부 0행·고유 업종 100개를 로컬 개발 DB에 적재했습니다. 카페 코드 `CS100010`(커피-음료)을 확인했고 동일 원본 재실행은 `SKIPPED`였습니다.

저장소 루트에서 DB에 접속해 적재 결과를 확인합니다.

```sql
SELECT batch_id, status, source_checksum, fetched_rows, valid_rows, rejected_rows,
       source_reference, error_message
FROM etl_batch WHERE dataset_code = 'SEOUL_SERVICE_INDUSTRY' ORDER BY started_at DESC;
SELECT count(*) FROM service_industry;
SELECT i.industry_code, i.industry_name, i.source_batch_id, b.status
FROM service_industry i JOIN etl_batch b ON b.batch_id = i.source_batch_id
WHERE i.industry_code = 'CS100010';
```

업종 DB 통합 테스트는 `etl/`에서 `RUN_INDUSTRY_DB_TESTS=1 npm test -- src/industries.integration.test.ts`로 실행합니다. 경계 회귀 테스트까지 함께 실행하려면 `RUN_INDUSTRY_DB_TESTS=1 RUN_BOUNDARY_DB_TESTS=1 npm test`를 사용합니다. 각 테스트는 새 일회용 PostGIS 컨테이너와 테스트별 스키마를 사용하며 실제 개발 DB는 변경하지 않습니다.

**점포 통계 적재**

기존 Flyway V1~V3를 적용하고 경계·서비스 업종 기준 데이터를 먼저 적재합니다. 루트 `.env`를 내보낸 터미널에서 실행합니다.

```bash
cd etl
npm run dev -- stores \
  --source "$HOME/Downloads/서울시 상권분석서비스(점포-행정동).csv" \
  --expected-rows 211832
```

`--source`는 CSV 또는 CSV 하나를 포함한 ZIP 경로이며 UTF-8(BOM 포함)·CP949를 지원합니다. 필수 `--expected-rows`는 입력 버전의 전체 데이터 행 수(헤더 제외)입니다. `211832`는 검증한 파일의 기준이며 코드에 고정하지 않습니다. 빌드 실행은 `npm run build` 후 같은 인자를 `npm start -- stores …`에 전달합니다.

| 원본 CSV 헤더 | V3 컬럼 |
| --- | --- |
| `행정동_코드`, `서비스_업종_코드`, `기준_년분기_코드` | `dong_code`, `industry_code`, `quarter_code` |
| `전체_점포_수`, `일반_점포_수`, `프랜차이즈_점포_수` | `store_count`, `general_store_count`, `franchise_store_count` |
| `개업_점포_수`, `폐업_점포_수` | `opened_store_count`, `closed_store_count` |
| `개업_율`, `폐업_률` | `opening_rate`, `closure_rate` |

- 위 V3 통계 매핑 표의 API 영문 헤더도 지원하며, 필수 컬럼의 누락·중복·모호한 별칭을 거부합니다. 코드와 분기는 Zod로 검증하고 `(dong_code, industry_code, quarter_code)` 중복은 값이 같아도 실패 처리합니다.
- 측정값은 빈 셀만 `NULL`로 보존하며 실제 `0`과 구분합니다. 점포 수는 0 이상 BIGINT 범위의 정수 문자열, 비율은 0 이상 유한한 십진수 문자열로 검증합니다. 소수·지수 표기의 점포 수와 지수 표기의 비율은 거부하며, JavaScript `Number`로 변환하거나 반올림하지 않습니다. 비율의 100% 상한이나 세부 수치의 합계 일치는 강제하지 않습니다.
- 최대 1,000행씩 DB 스테이징 완료를 기다리며 전달하고, 전체 검증 후 트랜잭션 Upsert와 `PUBLISHED` 이력을 함께 확정합니다. 입력에 없는 기존 키는 삭제하지 않습니다. 실패하면 스테이징·Upsert를 롤백하고 `FAILED` 이력을 별도로 기록합니다.
- FK 불일치는 거부 행 수와 누락 코드별 영향 행 수·분기 범위·첫 데이터 레코드(헤더 제외 1부터)를 보여줍니다. 코드별 예시는 최대 10개씩이며, 한 행에서 두 FK가 누락되어도 거부 행은 한 번만 셉니다. 기준 데이터 적재 누락이나 과거 행정구역·업종 버전을 확인해야 하며 코드를 임의 치환하지 않습니다.
- CSV 바이트의 체크섬·ETL 버전과 현재 입력 키의 모든 측정값·출처가 같을 때만 `SKIPPED`로 기록합니다. NULL과 0의 차이, DB 행 누락이나 수정도 비교하며, 다른 경로·ZIP 포장의 동일 CSV는 같은 원본으로 판단합니다.

실제 원본의 `20251`~`20262` 6개 분기, 행정동 425개·업종 100개에 해당하는 211,832행을 적재했습니다. 유효 211,832행·거부 0행, 카페 코드 `CS100010` 2,550행, 재실행 `SKIPPED`와 기존 기준 데이터 보존을 확인했습니다.

```sql
SELECT batch_id, status, expected_rows, fetched_rows, valid_rows, rejected_rows,
       period_from, period_to, source_checksum, source_reference, error_message
FROM etl_batch WHERE dataset_code = 'SEOUL_DONG_STORE_STAT' ORDER BY started_at DESC;
SELECT quarter_code, count(*) FROM dong_store_stat GROUP BY quarter_code ORDER BY quarter_code;
SELECT count(*) FROM dong_store_stat WHERE industry_code = 'CS100010';
```

점포 DB 통합 테스트는 `etl/`에서 `RUN_STORE_DB_TESTS=1 npm test -- src/stores.integration.test.ts`로 실행합니다. 기존 ETL 회귀까지 포함한 전체 테스트는 `RUN_STORE_DB_TESTS=1 RUN_INDUSTRY_DB_TESTS=1 RUN_BOUNDARY_DB_TESTS=1 npm test`로 실행하며, DB 테스트는 개발 DB와 분리된 새 일회용 PostGIS 컨테이너만 사용합니다.

**추정매출 통계 적재**

추정매출 ETL은 로컬 개발 DB에 100,431행 적재를 완료했습니다. 아래는 적재·재실행 명령입니다. 기존 Flyway V1~V3와 경계·서비스 업종 기준 데이터가 필요하며, 루트 `.env`를 내보낸 터미널에서 실행합니다.

```bash
cd etl
npm run dev -- sales \
  --source "$HOME/Downloads/서울시 상권분석서비스(추정매출-행정동).csv" \
  --expected-rows 100431
```

`--source`는 CSV 또는 CSV 하나를 포함한 ZIP이며 UTF-8(BOM 포함)·CP949를 지원합니다. `--expected-rows`는 헤더를 제외한 입력 버전의 전체 행 수입니다. `100431`은 검증한 파일의 기준이며 코드에 고정하지 않습니다. 빌드 결과는 `npm run build` 후 같은 인자를 `npm start -- sales …`에 전달합니다.

| 원본 CSV 헤더 | API 영문 헤더 | V3 컬럼 |
| --- | --- | --- |
| `기준_년분기_코드`, `행정동_코드`, `서비스_업종_코드` | `STDR_YYQU_CD`, `ADSTRD_CD`, `SVC_INDUTY_CD` | `quarter_code`, `dong_code`, `industry_code` |
| `당월_매출_금액` | `THSMON_SELNG_AMT` | `monthly_sales_amount` |
| `당월_매출_건수` | `THSMON_SELNG_CO` | `monthly_sales_count` |
| `주중_매출_금액` | `MDWK_SELNG_AMT` | `weekday_sales_amount` |
| `주말_매출_금액` | `WKEND_SELNG_AMT` | `weekend_sales_amount` |

- 네 측정 컬럼은 빈 셀만 `NULL`로 저장하고 `0`과 구분합니다. `9007199254740993.0`, `9.223372036854775807e18`처럼 정수 의미인 소수·지수 표기는 문자열과 정수 연산으로 정확히 정규화합니다. 음수 표기(`-0` 포함), 비정수, BIGINT 범위 초과, NaN·Infinity·공백 값은 거부하며 반올림하지 않습니다.
- 필수 코드·분기·헤더와 복합키 중복을 검증합니다. 당월 값을 월평균으로 환산하지 않으며 주중·주말과 전체 매출액의 합계 일치를 강제하지 않습니다.
- 최대 1,000행씩 스테이징하고 실제 DB 스테이징 건수와 검증된 유효 행 수를 비교합니다. FK가 누락되면 코드별 영향 행·분기·첫 데이터 레코드를 보고하고 롤백하며, 기준 코드를 임의로 치환하지 않습니다.
- 전체 검증 후 Upsert와 `PUBLISHED` 이력을 한 트랜잭션으로 반영합니다. 원본에 없는 기존 키는 유지하고 실패하면 변경을 롤백한 뒤 `FAILED` 이력을 남깁니다. 동일 원본은 체크섬·ETL 버전과 현재 네 측정값·출처가 모두 같을 때만 `SKIPPED`로 처리합니다.

검증한 추정매출 원본은 CP949, `20251`~`20262`의 6개 분기, 행정동 425개·업종 63개, 유효 100,431행·거부 0행이며 로컬 개발 DB 적재를 완료했습니다. 원본의 카페 코드 `CS100010`은 2,525행입니다. 이 수치는 검증한 입력 버전의 결과입니다.

```sql
SELECT batch_id, status, expected_rows, fetched_rows, valid_rows, rejected_rows,
       period_from, period_to, source_checksum, source_reference, error_message
FROM etl_batch WHERE dataset_code = 'SEOUL_DONG_SALES_STAT' ORDER BY started_at DESC;
SELECT quarter_code, count(*) FROM dong_sales_stat GROUP BY quarter_code ORDER BY quarter_code;
```

추정매출 DB 통합 테스트는 `etl/`에서 `RUN_SALES_DB_TESTS=1 npm test -- src/sales.integration.test.ts`로 실행합니다. 모든 ETL의 단위·격리 DB 통합 테스트 명령은 아래 유동인구 안내를 참고하세요. 합성 테스트 데이터는 새 일회용 PostGIS 컨테이너에만 적재하며 실제 개발 DB는 변경하지 않습니다.

**유동인구 통계 적재**

`foot-traffic`은 길단위인구-행정동 원본을 `dong_foot_traffic_stat`에 적재합니다. 로컬 개발 DB에 9,350행을 실제 적재하고 동일 원본 재실행 검증을 완료했습니다. 기존 Flyway V1~V3와 행정동 경계 데이터가 필요합니다. 업종 기준 데이터는 참조하지 않습니다.

루트 `.env`를 내보낸 터미널에서 다음과 같이 실행합니다.

```bash
cd etl
npm run dev -- foot-traffic \
  --source "$HOME/Downloads/서울시 상권분석서비스(길단위인구-행정동).csv" \
  --expected-rows 9350
```

`--source`는 CSV 또는 CSV 하나가 포함된 ZIP이며 UTF-8(BOM 포함)·CP949를 지원합니다. `--expected-rows`는 헤더를 제외한 입력 버전의 전체 행 수입니다. `9350`과 22개 분기는 검증한 원본의 참고값이며 코드에 고정하지 않습니다. 빌드 후에는 `npm start -- foot-traffic …`로 실행할 수 있습니다.

| 원본 CSV 헤더 | API 영문 헤더 | V3 컬럼 |
| --- | --- | --- |
| `기준_년분기_코드` | `STDR_YYQU_CD` | `quarter_code` |
| `행정동_코드` | `ADSTRD_CD` | `dong_code` |
| `총_유동인구_수` | `TOT_FLPOP_CO` | `total_foot_traffic` |
| `남성_유동인구_수` | `ML_FLPOP_CO` | `male_foot_traffic` |
| `여성_유동인구_수` | `FML_FLPOP_CO` | `female_foot_traffic` |

- 세 측정값은 `Number`로 변환하지 않고 문자열로 검증·전달해 `NUMERIC`의 정수·소수 정밀도를 보존합니다. 소수·지수 표기를 반올림하지 않으며 PostgreSQL `NUMERIC` 범위를 벗어난 값, 음수 표기(`-0` 포함), NaN·Infinity·공백 값은 거부합니다. 빈 셀만 `NULL`로 취급하고 `0`과 구분합니다.
- 필수 헤더·행정동·분기와 `(dong_code, quarter_code)` 중복을 검증합니다. 전체와 남성·여성 합계의 일치는 강제하지 않습니다.
- 최대 1,000행씩 스테이징하고 실제 스테이징 건수를 검증된 유효 행 수와 비교합니다. 행정동 FK 누락 시 코드별 영향 행·분기·첫 데이터 레코드를 보고하고, 코드를 임의 치환하지 않습니다.
- 전체 검증 후 Upsert와 `PUBLISHED` 이력을 한 트랜잭션으로 반영합니다. 실패 시 이전 데이터·출처를 보존하고 `FAILED`를 기록하며, 입력에 없는 기존 키는 삭제하지 않습니다. 같은 체크섬·ETL 버전이어도 실제 세 측정값·출처가 다르면 다시 반영하고 모두 같을 때만 `SKIPPED`로 기록합니다.

CP949 원본을 로컬 개발 DB에 실제 적재한 결과 `20211`~`20262`의 22개 분기·425개 행정동, 유효 9,350행·거부 0행이었습니다. 동일 원본 재실행은 `SKIPPED`였으며 기존 데이터와 출처(`source_batch_id`)가 보존됨을 확인했습니다. 이 건수는 적재한 입력 버전의 결과입니다.

```sql
SELECT batch_id, status, expected_rows, fetched_rows, valid_rows, rejected_rows,
       period_from, period_to, source_checksum, source_reference, error_message
FROM etl_batch WHERE dataset_code = 'SEOUL_DONG_FOOT_TRAFFIC_STAT' ORDER BY started_at DESC;
SELECT quarter_code, count(*) FROM dong_foot_traffic_stat GROUP BY quarter_code ORDER BY quarter_code;
```


**카페 API 수집·적재**

게시 모드에는 V4와 서울 경계 기준 데이터가 필요합니다. 확인 전용 `--probe`는 DB 설정·접속 없이 실행합니다. V4는 개발 DB에 적용되었으며 실제 API의 소진공 카페 분류 `I21201`·`카페`와 응답 형식 검증을 완료했습니다. `202609` 기준 원본 21,996건을 `PUBLISHED`로 적재했고, 동일 원본 재실행 `SKIPPED` 및 기존 게시 출처 보존을 확인했습니다. 이 코드·명칭·건수는 검증한 원본의 결과이며 매 실행 시 다시 검증합니다.

[공식 상가(상권)정보 API](https://www.data.go.kr/data/15012005/openapi.do)의 활용 승인을 받은 뒤 Decoding 인증키를 `SEMAS_API_KEY` 환경변수로만 설정합니다. 키를 CLI 인자·소스·README·인증 URL에 복사하거나 출력하지 않습니다. 공식 분류에서 확인한 코드와 명칭을 각각 `SEMAS_CAFE_INDUSTRY_CODE`, `SEMAS_CAFE_INDUSTRY_NAME` 터미널 변수에 설정한 뒤 실행합니다. 아래 두 분류 변수는 셸의 인자 전달용이며 인증키가 아닙니다.

**확인 전용:** 공식 카페 분류와 업소 첫 페이지 최대 5행의 응답 형식·필수값을 확인합니다. 실제 API 요청은 발생하지만 DB 연결·배치 이력·적재는 없고, 이후 페이지는 요청하지 않습니다. 전체 수집·서울 district 대조·PostGIS 검증을 완료했다는 뜻이 아니며 결과는 `mode='PROBE'`, `databaseChecked=false`, `complete=false`로 표시합니다.

```bash
cd etl
npm run dev -- cafes --probe \
  --industry-code "$SEMAS_CAFE_INDUSTRY_CODE" \
  --industry-name "$SEMAS_CAFE_INDUSTRY_NAME"
```

**실제 게시:** 루트 `.env`의 DB 설정을 내보낸 터미널에서 `--probe` 없이 실행합니다. 모든 페이지를 수집하고 DB·공간 검증을 통과하면 로컬 개발 DB에 게시하며 `PUBLISHED`·`SKIPPED`·`FAILED` 이력을 기록합니다.

```bash
# etl/ 디렉터리에서 실행
npm run dev -- cafes \
  --industry-code "$SEMAS_CAFE_INDUSTRY_CODE" \
  --industry-name "$SEMAS_CAFE_INDUSTRY_NAME"
```

- 선택적인 `--expected-rows`는 해당 원본 전체 건수와 대조합니다. 생략해도 게시 모드는 API가 알린 전체 건수와 모든 페이지의 실제 수집·유효·스테이징 건수를 확인합니다. `--probe`에서는 원천 전체 건수 메타데이터와 비교할 뿐 전체 페이지를 수집하지 않습니다. 빌드 후에는 `npm start -- cafes …`로 실행합니다.
- 공식 분류 목록의 카페 소분류 코드·명칭과 실제 업소 응답이 정확히 일치해야 합니다. 후보 코드나 서울시 `CS100010`을 소진공 코드로 간주하지 않으며, 확인하지 못한 분류·빈 전체 목록은 `PUBLISHED`로 게시하지 않습니다.
- 고정 HTTPS 엔드포인트의 `smallUpjongList`와 `storeListInDong`을 사용합니다. 서울 시도 코드 `11`로 모든 페이지를 요청하고 기준년월·전체 건수·페이지 메타데이터·서울 범위·업소번호 중복을 검증합니다. 타임아웃·요청 간격·제한된 재시도로 요청 폭주를 막고 인증 실패·오류·비정상 JSON을 안전하게 실패 처리합니다.
- 원본 `signguCd`를 스테이징에 전달해 현재 서울 `district` 코드와 대조합니다. 미등록·서울 외 코드는 좌표·행정동이 없어도 게시·SKIPPED 전에 거부하며 코드별 영향 행 수를 보고합니다. 행정동 원문은 보존하며 원본 시군구에 속한 8자리 기준 코드가 정확히 존재할 때만 FK에 연결합니다. 좌표는 WGS84 경도·위도 순서이며 둘 다 누락되면 NULL, 일부 누락·잘못된 좌표·서울 경계 밖은 실패합니다. 행정동 경계 불일치는 `spatial_mismatch_rows`로 보고하고 자동 수정하지 않습니다. 미연결 코드·좌표 누락 건수도 출처 JSON에 기록합니다.
- 페이지별로 검증한 데이터를 최대 1,000행씩 스테이징하고, 모든 페이지 검증 후 트랜잭션 Upsert로 게시합니다. 실패 시 이전 정상 데이터·출처를 보존하고 `FAILED`를 기록합니다. 새 게시에서는 모든 수집 업소의 출처를 새 배치로 갱신하고 원본에 없는 과거 업소를 삭제하지 않습니다.
- 정규화한 원본·수집 조건의 체크섬과 최신 전체 `PUBLISHED`의 실제 값·출처가 같을 때만 `SKIPPED`로 기록합니다. 과거 동일 체크섬만으로 생략하지 않습니다. SKIPPED는 이전 게시 출처를 유지하며 전체 최신 목록의 기준 배치를 대체하지 않습니다.

최신 목록은 테이블 전체가 아닌 완전한 서울 게시 배치만 조회합니다. 과거에만 존재한 업소는 보존되지만 최신 목록에 섞이지 않습니다.

```sql
WITH latest AS (
  SELECT batch_id FROM etl_batch
  WHERE dataset_code = 'SEMAS_CAFE_STORE' AND status = 'PUBLISHED'
    AND source_type = 'API' AND scope_type = 'SEOUL' AND scope_code IS NULL
    AND source_reference::jsonb @> '{"collection_mode":"FULL_SEOUL","complete":true,"classification_verified":true}'
  ORDER BY published_at DESC, started_at DESC, batch_id DESC LIMIT 1
)
SELECT c.* FROM cafe_store c JOIN latest b ON c.source_batch_id = b.batch_id;
```

실제 적재 결과는 유효 21,996건·거부 0건입니다. 게시 배치는 `0e149f16-5b3a-45c9-8473-379cc3b67206`, 재실행 `SKIPPED` 배치는 `01a020f8-7984-48e8-bc5b-884a62dd76ed`입니다. 로컬 DB를 읽기 전용으로 확인한 결과 `cafe_store` 21,996행 모두 기존 게시 배치의 `source_batch_id`를 유지하고 있으며, SKIPPED 배치의 `published_at`은 NULL입니다.

모의 API 단위 테스트는 `npm test -- src/cafe-source.test.ts`, 카페 격리 DB 통합 테스트는 `RUN_CAFE_DB_TESTS=1 npm test -- src/cafes.integration.test.ts`로 실행합니다. API 인증키는 테스트에 필요하지 않습니다. DB 테스트는 새 일회용 PostGIS 컨테이너만 사용하며 개발 DB에 접근하지 않습니다.
