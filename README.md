# 여기 창업해도 돼? — RecycleYoungs

서울의 창업 후보 위치를 공공데이터로 분석·비교하는 대학 캡스톤 웹 서비스입니다. 예비 창업자가 지역 통계와 주변 경쟁 점포를 살펴보고 최대 3곳을 같은 조건으로 비교하도록 돕는 것이 목표이며, **카페 업종을 우선하는 MVP**를 개발하고 있습니다.

**기준일: 2026-10-12 · 개발 인원: 1명 · 최종 개발 목표: 2026-10-31까지 시연 가능한 MVP 완성**

현재 행정동 통계·추세 조회와 카카오맵의 단일 위치 선택을 구현했습니다. 좌표 기반 행정동·상권 판정, 반경 경쟁 점포 조회, 후보 비교는 미구현이며, 기존 개발 DB는 **NOT_READY**입니다. 지도와 실제 지역 분석을 연결한 전체 서비스 통합 시연은 아직 완료하지 않았습니다.

## 개발 로드맵

✅는 각 단계에 적힌 범위의 구현·검증 완료, ❌는 핵심 요구사항 미완료를 뜻합니다. [개발 과정](docs/project.md#구현-과정과-주요-결정)과 [단계별 근거·한계](docs/project.md#구현-상태와-검증-수준)는 project 문서에서 확인할 수 있으며, 과거 검증 기록과 현재 DB 적용 상태는 구분합니다.

1. **서비스 기획 및 공공데이터 조사 — ✅**
   예비 창업자가 후보지를 비교할 수 있도록 서비스 목표를 세우고, 서울시 공공데이터와 소상공인 점포 자료를 조사했습니다.

2. **DB 설계 및 기본 CSV ETL 구현 — ✅**
   PostgreSQL 기반 기본 데이터 구조와 서울시 통계 CSV 처리 코드를 구현하고 당시 검증했습니다. 기존 개발 DB에 모든 최신 자료가 적재됐다는 뜻은 아닙니다.

3. **행정동 통계 Backend API 구현 — ✅**
   Spring Boot와 JdbcClient로 행정동·업종·분기 목록 및 점포·추정매출 조회 API를 구현했습니다. 단위 테스트와 당시 격리 조회 검증 기록이 있습니다.

4. **React 통계·추세 조회 화면 구현 — ✅**
   조회 조건 선택, 점포·추정매출 조회, 2025년 1~4분기 추세와 결측·요청 오류 처리를 구현했습니다. 테스트와 당시 API 연결 검증 기록이 있습니다.

5. **공간 데이터 및 카페 업종 분석 기반 준비 — ✅**
   행정동·상권 경계와 SEMAS 카페 업종 연결을 위한 DB 변경·ETL 코드를 작성하고 격리 검증했습니다. 완료 범위는 코드와 격리 검증이며, 기존 개발 DB의 공간 변경 적용과 실제 Polygon 적재는 미완료입니다.

6. **카카오맵 연동 및 단일 위치 선택 — ✅**
   지도 클릭, 위도·경도의 React 상태 저장·표시, 단일 마커 이동을 구현하고 mock 테스트와 실제 Chrome 지도 동작을 확인했습니다. 실제 통계 API와 연결한 전체 사용자 흐름은 아직 검증하지 않았습니다.

7. **좌표 기반 행정동·상권 분석 — ❌**
   선택 좌표가 어느 행정동·상권에 속하는지 판정하는 API를 구현하고 기존 통계 조회와 연결해야 합니다.

8. **반경 내 카페 경쟁 점포 분석 — ❌**
   실제 SEMAS 카페 점포 자료의 적재·분류·검증을 거쳐 주변 경쟁 점포를 조회해야 합니다. MVP에서는 우선 500m 반경 한 가지 조건부터 검토합니다.

9. **최대 3곳 후보 위치 비교 — ❌**
   같은 업종·기간·반경·데이터 기준으로 최대 3개 후보지를 비교하는 기능을 구현해야 합니다.

10. **통합 테스트 및 최종 시연 — ❌**
    위치 선택부터 지역 분석, 경쟁 점포 조회, 후보 비교까지 연결된 흐름을 검증해야 합니다. 2026년 10월 31일까지 시연 가능한 MVP를 완성하는 것이 목표입니다.

## 어떤 문제를 해결하나요?

후보지를 비교하려면 점포와 매출 자료를 찾아야 하지만, 자료마다 제공 사이트·기준 시점·집계 지역이 다릅니다. 이 서비스는 수치와 함께 출처·기간·집계 단위를 보여줘 비교의 근거를 확인하도록 돕는 것이 목표입니다.

자료는 특정 가게의 실제 매출이나 이익을 뜻하지 않습니다. 지역 통계로 후보지의 환경을 살펴볼 수 있지만, 창업 성공·수익·폐업 가능성을 예측하거나 보장하지 않습니다. 반경 안의 수요를 지역 통계의 면적 비율로 계산하지도 않습니다.

## 지금 구현된 사용자 기능

지도에서 위치를 클릭하면 위도·경도와 마커 하나를 확인할 수 있습니다. 다른 곳을 클릭하면 같은 마커가 이동합니다. 지도 선택은 통계 조회 조건을 자동으로 바꾸거나 API를 재호출하지 않습니다.

행정동 통계는 다음 순서로 조회하도록 구현돼 있습니다.

1. 행정동을 선택합니다.
2. 지원하는 업종을 선택합니다.
3. 통계를 조회할 분기를 선택합니다.
4. **조회하기** 버튼을 누릅니다.
5. 선택 분기의 점포 수·유사점포 수·개업/폐업 점포 수·프랜차이즈 수와 추정매출·거래 건수를 확인합니다.
6. 같은 행정동·업종의 **2025년 1~4분기 추세 표**를 확인합니다.

선택 분기는 5번의 단건 통계에만 적용됩니다. 6번의 추세는 항상 2025년 네 분기를 보여줍니다. 현재 고정 입력의 지원 업종은 카페(CAFE)·미용실(HAIR)·한식(KFOOD)·주점(PUB)입니다. 모든 선택 조합에 자료가 있는 것은 아닙니다.

화면은 실제 0과 자료가 없는 경우를 구분합니다. 조회 중 안내, 오류 후 재조회, 조건 변경 시 요청 취소도 있으며, 단건과 추세 중 한쪽이 실패해도 다른 쪽의 결과는 표시합니다. 모바일에서는 표 안을 가로로 스크롤하고 키보드로도 입력과 조회를 할 수 있도록 구현했습니다.

통계 API와 화면에는 과거 연결·테스트 기록이 있고, 10월 12일에는 프론트엔드 mock 테스트와 실제 지도 브라우저 검증을 수행했습니다. 이번 문서 작업에서는 테스트나 서버를 다시 실행하지 않았으며, **현재 DB 조회나 전체 서비스 연결 성공을 새로 확인한 것은 아닙니다.**

## 최종 MVP 사용자 흐름

MVP는 처음 완성할 핵심 서비스 범위입니다. 현재 지도 위치 선택과 행정동 통계 조회는 독립적으로 동작하며, 최종적으로는 선택 위치의 주변 환경을 분석·비교하는 흐름으로 연결합니다.

| 하고 싶은 일 | 현재 구현 | 최종 MVP 목표 |
| --- | --- | --- |
| 위치 고르기 | 지도에서 단일 좌표 선택 | 선택 좌표를 지역 분석·비교와 연결 |
| 어느 지역인지 확인하기 | 선택한 동의 통계 조회 | 좌표로 행정동·상권을 판정하고 경계의 모호성도 설명 |
| 점포 살펴보기 | 행정동·업종별 집계 수치 | 선택 반경 안의 경쟁 점포 확인 |
| 통계 해석하기 | 선택 분기·고정 네 분기 수치와 단위 | 자료별 출처·기간·집계 단위·버전까지 표시 |
| 후보 비교하기 | 한 동·업종 조회 | 같은 조건으로 최대 3곳 비교 |

**좌표 기반 API·반경 경쟁 점포·후보 비교·출처/버전 표시 화면은 미구현입니다.** 공간 DB 구조와 자료 처리 코드가 있어도 사용자 기능 전체가 완성된 것은 아닙니다. 추가 인구·시설·변화 지표와 설명 가능한 점수는 자료와 계산식을 검증한 뒤 검토합니다. AI 예측·전국 확대·실시간 수집·수익 예측은 현재 MVP 범위가 아닙니다.

## 기술 스택과 시스템 흐름

화면은 React, 요청 처리는 Spring, 자료 저장과 조회는 PostgreSQL이 맡습니다. Python ETL은 CSV를 읽고 검증·변환해 DB에 미리 적재하는 별도 작업입니다. PostGIS는 앞으로 좌표와 지역 경계를 조회할 수 있게 하는 PostgreSQL의 공간 기능입니다.

| 영역 | 구성 |
| --- | --- |
| Frontend | React 19·TypeScript 6·Vite 8·Tailwind 4·shadcn Button/Card |
| Backend | Java 21·Spring Boot 4.1.1·Spring MVC·JdbcClient |
| DB | PostgreSQL 16·PostGIS 3.4·Flyway |
| 자료 처리·실행 | Python 3.12·Docker Compose·Makefile |

공공자료 → Python ETL → DB에 저장 → Spring API로 조회 → React에 표시하는 구조입니다. **조회 버튼을 누를 때 ETL이 실행되거나 원본 CSV를 다시 읽지는 않습니다.** [실제 조회 한 번 따라가기](docs/technical.md#통계-조회-한-번-따라가기)에서 코드까지 연결해 볼 수 있습니다. 정확한 버전 기준은 [기술 스택](docs/technical.md#기술-스택과-선택-이유)에 있습니다.

## 기존 개발 DB 상태

**기존 개발 DB는 NOT_READY이며, V2/V3와 행정동·상권 Polygon 적용은 마지막 확인 기록에서 미완료입니다.** 격리 테스트 성공은 기존 개발 DB 적용 성공을 뜻하지 않습니다. 기능 개발은 mock 또는 승인된 격리 환경에서 진행할 수 있지만, 실제 기존 DB 변경에는 별도의 검증과 명시적 승인이 필요합니다. 이번 문서 작업에서 DB를 재조회하지 않았으며, 상세 절차는 [db-safety](docs/db-safety.md)에 있습니다.

## 안전하게 개발 시작하기

먼저 Git branch/HEAD와 변경 파일을 확인하고 [착수 가능한 작업](docs/project.md#현재-위치와-지금-시작할-작업)에서 범위를 고릅니다. 실제 DB 없이 가짜 응답으로 화면·계약을 확인하는 mock 작업과 [DB 없는 검증](docs/technical.md#db-없는-검증)부터 준비할 수 있습니다. 의존성은 기존 lockfile을 따르고 새 clone에는 원본 자료가 없다는 점도 확인합니다.

`make db`/`db-info`/`etl`, Spring bootRun·dbTest는 기존 DB에 영향을 줄 수 있습니다. migration은 DB 구조를 SQL로 바꾸는 작업이고, full loader는 기존 자료를 지우고 다시 채울 수 있습니다. 실행 전에 [위험 명령](docs/technical.md#위험-명령과-알려진-blocker)과 대상·범위의 별도 승인을 확인합니다. 문서 수정은 DB 변경이나 Git stage/commit/push 승인이 아닙니다.

활성 문서는 README·AGENTS·project·technical·db-safety 5개입니다. [legacy](legacy/README.md)는 이전 실험의 보존 영역이고 과거 상세 보고는 고정 Git 링크로 남깁니다.
