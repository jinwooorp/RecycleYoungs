## 서비스 목적과 요구사항

예비 창업자는 후보지 주변의 경쟁 점포와 지역 통계를 여러 사이트에서 따로 확인해야 합니다. 이 서비스는 자료를 한 화면에 모아 위치별 창업 환경을 비교하도록 돕습니다.

서울에서 창업을 준비하는 사람들을 위한 MVP 서비스이며, **현재는 카페 업종만 지원**합니다. 예비 창업자를 주요 사용자로 정했지만, 사용자 인터뷰와 서비스 효과 검증은 별도로 필요합니다.

핵심 요구사항은 다음과 같습니다.

- 지도에서 후보 위치를 선택하고 해당 행정동·상권을 확인합니다.
- 주변 경쟁 카페와 지역의 점포·추정매출 통계를 보여줍니다.
- 소비규모·소비증감과 실제 변화 방향을 바탕으로 검토 근거와 추가 확인사항을 안내합니다.
- 최대 3곳을 같은 업종·반경·분기 조건으로 비교합니다.
- 출처·기간·집계 단위와 확인되지 않은 사항을 함께 표시합니다.
- 값 없음, 실제 0, 요청 실패를 구분합니다.

창업 성공·수익·폐업을 예측하거나 보장하지 않습니다. 행정동 추정매출을 후보 반경의 매출이나 개별 가게의 이익으로 바꾸지 않습니다.

## MVP와 비목표

최신 사용자 결정은 **완성도 우선: 폭넓은 데이터와 점수 검증 후 배포**입니다. 기존 2026-10-31 시연·첫 배포 일정 대신 아래 완료 조건으로 진행하며 배포일은 다시 산정합니다. 현재 구현과 확장 목표를 구분합니다.

| 구분 | 범위 |
| --- | --- |
| 현재 구현 | 서울 구·행정동 검색, 지도 위치 판정, 반경 500m 카페·브랜드 추정 필터, 공개 지원 분기 통계·추세, 두 소비 점수, 상세 분석·최대 3곳 비교 |
| 데이터 수집 상태 | 공식 API 수집·검증·영속 버전 공개와 주간 갱신, 이전 분기·원본 목록 보존. 운영 알림·보존/전체 복구는 후속 과제 |
| 데이터 확장 목표 | 인구활동·배후수요·소비·경쟁·변화·교통·시설/지역특성·비용의 공식 원천을 검증하고 가능한 자료부터 연결 |
| 제품·구조 목표 | 원지표·출처·기간·단위·한계를 화면과 후보 비교에서 확인하고 Frontend 기능별 책임·상태 소유 정리 |
| 점수 목표 | 같은 기간·공간·비교 집단의 자료로 영역별·종합지수 산식과 가중치·민감도를 검증한 뒤 공개 |
| 실행·배포 목표 | 데이터·화면·점수 검증 뒤 nginx 진입점, 배포 구성, 일반 CI·CD와 첫 배포 |

화면 업종은 CAFE로 고정하며 일반 통계 API의 기존 업종 계약은 유지합니다. API 수집은 Python ETL로 검사·적재하며 과거 자료와 원본 목록을 보존합니다. 수집 성공이나 최근 수집 시각만으로 원천 자료의 최신성·완전성을 보장하지 않습니다.

현재 필수 범위에 포함하지 않는 기능은 다음과 같습니다.

- AI·머신러닝 기반 성공률·수익 예측
- 원천 공표 주기를 넘어서는 실시간 영업 상태 보장
- 전국 확대, 임의 반경·연령 조건
- 점포별 가맹·직영·독립 운영 형태 확정

첫 배포는 운영 부하·고가용성·포괄적 접근성 검증 완료와 구분합니다.

## 현재 사용자 흐름

| 단계 | 사용자가 하는 일 | 제공되는 정보 |
| --- | --- | --- |
| 탐색 | 구·행정동 검색 또는 지도 클릭·키보드로 위치 선택 | 선택 동 경계·지역명·분기, 창업 검토 요약과 두 소비 점수 |
| 주변 확인 | 실제 선택 지점의 카페 목록·지도·종류 필터 사용 | 반경 500m 조회 수, 거리순 최대 100개 수신 목록과 브랜드 추정 |
| 상세 분석 | 상세 화면에서 분기·지표 선택 | 행정동 통계·추세·점수 근거·정확한 원값·출처와 한계 |
| 후보 비교 | 최대 3곳 저장 후 공통 분기로 분석 | 소비규모·실제 증감·주변 카페 수·다음 확인사항, 펼쳐 보는 전체 통계 |

행정동만 검색하면 지역 분석을 제공하고, 실제 지점을 선택한 뒤에만 500m 카페 조회와 후보 추가를 제공합니다. 위치 판정이 단일 동으로 확정되고 통계 지원 목록에 있을 때 해당 통계를 자동 조회합니다. 모호한 경계를 임의 선택하거나 가상 중심점을 만들지 않습니다.

초기 분기는 서버의 지원 최신값이며, 비교 분기는 지도·상세와 별도로 선택합니다. 비교는 ‘같은 분기로 후보 분석’을 실행한 뒤 갱신합니다. 앱 내 화면 전환은 지도·후보를 유지하지만 새로고침 후 후보·정확한 지점 복구는 지원하지 않습니다.

통계·점수는 행정동 전체, 주변 카페는 선택 좌표 반경 기준입니다. 같은 동의 후보는 통계를 공유할 수 있습니다. 소비규모 점수는 거래 건수의 상대 순위, 소비증감 점수는 직전 분기 대비 변화의 상대 순위이며 높은 점수에도 실제 거래는 감소할 수 있습니다. 원값·증감 방향·결측 사유를 함께 표시합니다.

주변 필터는 수신한 최대 100개에만 적용하며 반경 전체의 브랜드 구성을 뜻하지 않습니다. 상호명 기반 브랜드 추정은 가맹·직영·독립 운영 형태를 확정하지 않습니다. 검토 요약은 소비 신호와 추가 조사 항목을 안내하며 카페 수만으로 입지 우열을 판정하지 않습니다.

화면·요청 상태의 상세 동작은 [Frontend 계약](technical.md#frontend-화면과-요청-상태), 두 점수의 산식·응답은 [API 계약](technical.md#현재-get-api-계약)을 참고합니다.

| 운영 배포·부하 검증 | 미완료 | 첫 배포 목표와 운영 부하·고가용성 검증을 구분 |

검증 기록은 다음처럼 해석합니다.

- **단위·모의 검증:** 가짜 응답이나 연결로 로직을 검사합니다.
- **격리 DB 검증:** 기존 환경과 분리한 실제 DB에서 검사합니다.
- **실자료·지도 검증:** 명시한 데이터와 실제 SDK로 흐름을 확인합니다.
- **미검증·SKIP:** 확인하지 못한 항목입니다. 성공으로 계산하지 않습니다.

기록의 날짜·대상·제한은 [검증 이력](technical.md#검증-이력)에서 확인합니다. 최근 창업 검토 중심 개선은 [2026-10-17 검증 기록](technical.md#2026-10-17-창업-검토-요약근거-비교상세-통합)에 있습니다. 각 기록의 일반 테스트·브라우저 확인과 과거 격리 DB 검증을 구분합니다.

기간 확장 준비(2026-10-22 후속): 두 실패 매출 분기를 전수 조사한 뒤 사용자가 **미지원 업종의 정확한 문제2행만 명시적 격리**하도록 승인했습니다. 모든 raw를 보존하고0/NULL 보정 없이 두 행을 격리해, 45run·22분기·정상1,174,306행/격리2행의 **계약2 history 후보**를 준비·재검증했습니다. 기존13seed run 335,002행·SEMAS202606은 전수 동일하며 기존 비교 가능 분기의 카페 점수도 파일 기반 독립 계산에서 일치했습니다. 이는 실제Backend/SQL/HTTP 검증과 구분합니다. 20204·20263은 양 원천 소량 조회에서 미제공입니다.

실행 구성은 기존 스택과 EC2·Docker Compose 계획을 기준으로 검토합니다. 배포용 구성은 현재 팀 개발 환경과 구분하고 앱 배포·DB migration·데이터 갱신을 각각 검증합니다. 서버 비용·도메인·인증키·secret 관리, 배포 실행 대상과 범위는 먼저 확정해야 합니다.

지원 분기·추세·화면 검사의 2025년 고정을 제거하고 최신 기본 분기를 공개 지원 목록에서 선택하도록 구현했습니다. 통계·추세·점수·후보 요청은 공개 버전을 고정하며 버전이 바뀌면 목록 갱신을 안내합니다. 별도 API 서비스에서 여섯 분기·기본 20262·연도 경계 추세와 오래된 버전 요청의 HTTP 409를 확인했습니다. 기본 진입점은 `docker compose up -d`이며 DB·API 수집·Backend·Frontend를 새 `recycleyoungs-dev`에 자동 준비합니다. 기존 `make api-*`는 별도 API 환경, `make db`·`etl`은 명시적 legacy Compose를 유지합니다.

**API 전수 검증:** [공공 API 전환 준비](technical.md#공공-api-전환-준비)에 README 개선 항목별 가능 범위·필드 매핑·구현 순서를, [인증 전체 수집과 CSV 대조](technical.md#인증-전체-수집과-csv-대조)에 실행 결과를 정리했습니다. 서울시 2025년 4개 분기의 전체 키·정규화 필드가 고정 `real-data-v2` CSV와 일치합니다. 2026년 1·2분기도 수집했으나 기존 패키지에 비교 대상은 없습니다. 원천의 공간 기반·역사적 경계 호환성 검증은 별도입니다.

DB에 접속하지 않는 점포 통계·매출 전체 필드·SEMAS baseline 수집기와 대조기를 구현했습니다. 사용자가 선택한 서울시 공식 HTTP와 SEMAS HTTPS로 13개 범위·335,002행을 수집했습니다. 원본 manifest는 수집 완료·미공개 이력으로 보존하며 격리 DB의 공개 catalog와 구분합니다. SEMAS는 외곽 공백 정규화 뒤에도 173개 점포의 쉼표/세미콜론 차이가 있어 엄격 대조 결과는 `DIFFERENT`입니다. API 표기를 보존한 자료를 격리 DB에서 공개·검증했습니다. 상세 결과와 전환 순서는 [API 격리 통합 검증](technical.md#api-격리-통합-검증과-전환-준비)에 기록합니다. [설정·실행 안내](technical.md#로컬-키-설정과-수집-실행)를 따르며 실제 키 값은 문서·채팅·로그에 남기지 않습니다. 시간대·고객 구성은 기존 매출 자료로 확장하며 인구·시설·교통 등은 새 원천 계약을 검증합니다. 개별 임대료·운영비·점포 운영 형태는 별도 근거가 필요하며 전국 확대는 이번 범위에 포함하지 않습니다.

Frontend는 기존 요청 취소·정밀 숫자·결측·접근성 계약을 보존하며 기능별로 정리합니다. 구체 폴더·라우팅·상태 관리 도구는 설계 확정 전 구현된 구조처럼 문서에 적지 않습니다.

기존 Compose와 고정 fingerprint는 동일한 고정 데이터의 재실행 보존을 위한 것입니다. API 성공을 이유로 guard·fingerprint를 갱신하거나 V4를 기본 migration 위치에 넣지 않습니다. 승인된 별도 API 환경·역할·Backend profile·주간 공개와 다음 입력 목록 승계를 연결했고 [소스 이미지 빌드](technical.md#소스-이미지-빌드와-신규-환경-준비)를 추가했습니다. 새 기본 Compose의 실제 초기 준비·여섯 분기 HTTP 조회·재실행 생략·DB 재시작 보존을 확인했습니다. 참고5종/소비보류의 저장·조회·화면을 구현했고 격리 최종 검증 완료입니다. 이후에는 현재dev 전환을 별도 검토합니다. 별도 PC/EC2 재현·전체 worker 복구·알림·보존 정책과 nginx·CI/CD는 배포 전 남은 과제로 유지합니다. 기존 구성의 퇴역·삭제는 별도 판단입니다.

## 현재 blocker와 미확정 사항

- **점포 자료의 기준일·완전성:** 파일명 `202606`을 정확한 관측일이나 모든 영업 점포의 목록으로 볼 수 없습니다.
- **점포 운영 형태:** 상호명 기반 브랜드 추정만 제공하며 가맹·직영·독립 운영은 미확인입니다. 정확한 점포 식별/주소·브랜드 소속·점포별 운영 형태 근거·기준일·확인 상태를 갖춘 자료를 확보·검증한 뒤 별도 API/ETL 확장으로 다룹니다. 브랜드별 집계나 미등록 이름만으로 개별 점포를 확정하지 않습니다.
- **역사적 경계 호환성:** 현재 경계가 2025년 통계 집계 당시와 같다는 근거가 부족합니다.
- **원본 경계의 겹침·속성 충돌:** 행정동 겹침과 홍지문 상권의 충돌을 보존합니다. 임의 보정하지 않습니다.
- **원천 API 계약:** 승인 범위의 전체 paging·건수·중복·정밀 값과 2025년 CSV 호환성을 확인했습니다. SEMAS 명칭 구두점 차이는 API 표기 보존으로 처리합니다. 다른 업종·기간, 원천 개정·호출 한도와 동일 시점 snapshot 보장은 별도 확인 대상입니다.
- **자료 갱신 정책:** 영속 대상 writer·주간 자동 공개·이전 run 목록 승계·새 완료 분기 탐색·상태를 구현했습니다. 최신 지원 분기·서울 카페를 전수 재수집하며 과거 분기는 보존합니다. 오래된 분기 정정·호출 한도 운영·외부 알림·보존 기간은 미확정입니다. 원천별 기준 시점이 다르며 수집 시각을 관측일로 대체하지 않습니다.
- **복구 범위:** DB snapshot 백업·독립 복원은 검증했습니다. 원본 run 파일·제어 기록·secret을 포함한 별도 장비의 전체 worker 복구와 정기 백업 운용은 남아 있습니다.
- **테스트 대상 구분:** 과거 V1 전용 `dbTest`의 기대값을 현재 팀 DB에 그대로 적용하면 안 됩니다.
- **시연·운영 범위:** 예정한 EC2/Compose 배포의 구체 구성·자동화, 부하 기준, 팀원 PC 재현, 포괄적 접근성 검증이 남아 있습니다.
- **기존 DB 변경 경로:** 실제 감사 자료 수집기와 안전 실행기는 미구현입니다. 현재 팀 개발 경로와 별개의 보류 과제입니다.

## 추가 지표와 점수 정책

인구·시설·변화 지표를 추가하려면 지역 단위와 기간, 중복 여부부터 확인합니다. 서울 전체 수치를 모든 후보지의 지역 수요로 반복해서 넣지 않습니다.

2026-10-22 인증 수집은 아파트 포함7종·22개 분기·원문65,189행이며 소비 음수6행은 격리했습니다. **최신 활용 범위는 아파트 제외6종**입니다. 인구3종은원값/한계참고,시설은종류별개수만참고,변화는업종미구분유형/평균개월참고로연결합니다. 소비는전체보류하며기존카페매출/거래와분리합니다. 아파트원천/구분가구와시설총수는공개하지않고기존수집본은보존합니다. 직장인구414동의누락과집계·시점충돌을0/추정으로채우지않습니다. 신규모든자료는점수미허용이며교통·주차·관광/행사·임대/공실은별도후속후보입니다. [채택·저장·조회계약](technical.md#신규-6종-통합의-채택저장조회-계약)과[화면설계](technical.md#신규-자료의-화면-연결)를따릅니다.

규칙 기반 점수를 도입할 경우 계산식·가중치·비교 집단·버전을 공개해야 합니다. 원지표도 함께 보여주며, 필수 자료가 없으면 점수를 만들지 않습니다.

추가 SEMAS 업종은 공식 분류와 포함·제외 기준을 확인한 뒤 연결합니다. 상호명이나 서울시 업종 코드만으로 점포를 임의 분류하지 않습니다.

## 기존 DB 적용을 위한 보류 과제

과거 V1 DB의 V2/V3·경계 적용과 감사 도구는 현행 팀 개발 환경 및 앞으로의 공공 API 수집과 별개의 보류 과제입니다. 퇴역 DB를 재생성·복원하거나 이 도구를 팀 환경 준비의 선행 조건으로 사용하는 계획이 아닙니다.

`source_validation.py`·`source_audit.py`·`source_control.py`는 제공된 자료의 비교·형식 검증·모의 단계 모델이며 실제 DB 감사 수집기·변경 실행기는 미구현입니다. 요구사항과 검증 gate는 [DB 안전 정책](db-safety.md#기존-db-감사-수집기와-provenance-요구)을 따릅니다. 테스트 PASS·READY·과거 검증은 실제 변경 승인이 아닙니다.
