## 2. 읽기 전용 내보내기와 파일 보호

기존 `scoreSnapshotExport`를 `SCORE_SNAPSHOT_EXPORT_ENABLED=1`과 외부 절대 출력 경로를 명시해 한 번 실행했습니다. 구·동 전체 입력은 하나의 읽기 전용 `REPEATABLE_READ` 트랜잭션에서 조회했습니다.

도구가 DB에서 확인한 기본값과 현재 트랜잭션의 읽기 전용 상태는 모두 `on`이고, 격리 수준은 `repeatable read`입니다. Flyway는 구성하지 않았습니다. `ROLLBACK` 완료 통지를 확인하고 DB Context를 닫은 뒤에만 파일을 보존했습니다. INSERT·UPDATE·DELETE·DDL·ETL·마이그레이션·재게시를 실행하지 않았으며 스키마·데이터·Flyway 이력을 변경하지 않았습니다.

저장소 밖에 현재 사용자 소유의 비공개 `0700` 디렉터리를 새로 준비했습니다. 상위 경로의 소유권·쓰기 권한·링크 여부를 검사했고 도구의 경로 보호 검사도 통과했습니다. 고유한 새 이름으로 한 묶음 파일을 저장했으며, 최종 파일은 현재 사용자 소유의 일반 파일·`0400`입니다. 구·동 전체 아티팩트와 제외 목록·출처·정책·정확한 결과를 함께 보존했습니다.

보관 디렉터리는 처음에 없었고 기존 파일도 없었습니다. 저장 뒤에는 완성 파일 하나만 있으며 `.part` 잔여 파일은 없습니다. 기존 파일 덮어쓰기나 심볼릭 링크 우회는 없었습니다. 오프라인 검증 전후에도 파일 식별자·크기·수정 시각·권한·해시가 같았습니다. 실제 JSON은 Git에 추가하지 않았습니다.

내보내기 표준출력에서 확보한 위 세 해시를 별도 기준값으로 `SCORE_SNAPSHOT_EXPECTED_FILE_SHA256`, `SCORE_SNAPSHOT_EXPECTED_DISTRICT_ID`, `SCORE_SNAPSHOT_EXPECTED_DONG_ID`에 전달했습니다. 파일에서 읽은 내부 해시를 기준값으로 복사하지 않았습니다.

DB·Spring·Flyway 및 내보내기 관련 환경변수를 제거한 별도 프로세스에서 기존 `scoreSnapshotVerify`를 실행했습니다. DB 연결이나 Spring Context 없이 지정 파일 하나만 읽었으며 `VERIFIED externalPins=3`과 종료값 0을 확인했습니다. 파일 전체 SHA-256은 Python 표준 라이브러리로도 대조했습니다.

기존 codec·`replay()`·A 계산기를 통해 정규 JSON·SHA-256·실제 행 출처·전체 경계와 완비/제외 분할·정확한 정규화·기여·최종 점수·동률 평균 순위를 검증했습니다. 구·동은 독립 집단으로 재현됐고, 446개 결과의 기여 합과 최종 점수 일치도 보존 분수로 별도 확인했습니다. 새로운 계산식이나 모델 실험은 추가하지 않았습니다.

세 기준 해시는 같은 내보내기 실행의 출력에서 확보한 대조값입니다. 오프라인 파일의 무결성·재현성을 확인하지만 원천의 독립 신뢰나 정책·판본·커버리지 승인을 뜻하지 않습니다.

## 5. 미검증 사항과 후속 과제

- 과거 2026-11-02 12:17의 전체 입력 fixture는 여전히 없습니다. 이번에 현재 전체 입력을 보존했어도 과거 R03 완전 재현은 미완료입니다.
- 매출·점포 모집단, 집계 기간, 인구 중복, 과거 경계 호환성과 누락 원인 등 원천 의미의 미확인 사항은 유지합니다. 실제 창업 성과·정책 적합성을 검증하지 않았습니다.
- 현재 보관은 로컬 단일 사본입니다. 백업·복원 검증, 보존 기간, 장기 보관 위치, 접근 권한·운영 책임과 독립 해시 보관 체계는 후속 결정 사항입니다. 전원 장애 내구성이나 백업 체계 구축 완료로 보고하지 않습니다.
- 승인 manifest는 생성하지 않았습니다. 모든 결과는 계속 `NOT_APPROVED`, `sourceTrust=NOT_ESTABLISHED`입니다. 공개 API·승인 우회 기능도 추가하지 않았습니다.
- 코드가 변경되지 않아 전체 단위·통합 테스트·빌드·Spotless는 재실행하지 않았습니다. 이번 실행 도구의 성공과 문서 Prettier·상대 링크·표·신규 파일 공백 검사를 확인했습니다. 커밋·Push는 하지 않았습니다.
