# 창업 환경 점수 입력 스냅샷과 오프라인 재현

**구현 상태:** 승인 전 A 후보의 전체 입력을 메모리에서 불변 아티팩트로 만들고, 정규 JSON·SHA-256을 검증한 뒤 DB 없이 재계산할 수 있습니다. 합성 전체 집단으로 R01·R02를 검증합니다. 해시 일치나 재현 성공은 정책·데이터·커버리지 승인과 다릅니다.

기준은 [계산 계약 6.2절](score-v1-contract.md#62-승인-입력-스냅샷을-불변-배포-아티팩트로-보존)과 [R01·R02·R03](score-v1-contract.md#74-재현기존-결과-회귀)입니다. 이번에는 실제 개발 DB·CSV를 읽거나 저장하지 않았고, [기존 R03 실행 기록](archive/score-r03-validation.md)을 재실행·수정하지 않았습니다.

## 1. 책임과 실행 경계

| 클래스                                                                                                 | 역할                                                                                                   |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |

| [ScoreSnapshotCodec](../backend/src/main/java/kr/ac/recycleyoungs/score/ScoreSnapshotCodec.java)       | 정규 JSON 바이트·SHA-256 생성, 엄격한 역직렬화·해시·재현 검증                                          |
| [ScoreCohortEvaluator](../backend/src/main/java/kr/ac/recycleyoungs/score/ScoreCohortEvaluator.java)   | 기존 Service의 입력 검증·집단 계산만 추출한 공통 순수 로직. 기존 A 계산기 재사용                       |

이 클래스들은 파일·DB·HTTP·Spring Context를 사용하지 않습니다. Service의 요청 검증·트랜잭션·경계→지역→데이터셋 준비 순서와 상태·오류 처리는 그대로입니다. 스냅샷 생성은 Service 호출에 자동 연결하지 않았습니다. 파일 내보내기·덮어쓰기·manifest 생성·자동 실행 작업도 없습니다.

## 2. 스키마와 전체 집단 검증

아티팩트의 최상위는 다음 네 필드입니다. nullable 필드도 키 자체는 반드시 있어야 합니다. 정의에 없는 필드는 거부합니다.

| 필드              | 내용                                                     | 입력 해시 대상             |
| ----------------- | -------------------------------------------------------- | -------------------------- |
| `payload`         | 아래 전체 입력 스키마                                    | 전체 포함                  |
| `inputSnapshotId` | 정규 payload 바이트의 소문자 SHA-256 64자리              | 제외                       |
| `expected`        | 완비 수·제외 사유·집단 보류 사유·모든 결과의 정확한 분수 | 제외, 재계산으로 별도 대조 |
| `requestedAt`     | nullable 요청 시각. 감사용이며 계산에 사용하지 않음      | 제외                       |

`payload`는 다음 필드를 가집니다.

| 필드                    | 내용                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `snapshotSchemaVersion` | `score-input-v1`. 다른 버전 거부                                                       |
| `algorithmVersion`      | `a-rank-v1-candidate.1`. 재현 시 이 후보 버전만 지원                                   |
| `policy`                | 입력 컬럼·방향·네 비중·순위 정규화·검증/제외·집단 보류·정밀도·표시·분기·업종·보상 규칙 |
| `coverage`              | 전체 경계·완비·제외 수. 각 목록의 실제 크기와 대조                                     |
| `input`                 | 기존 `ScoreInputSnapshot` 전체. 단위·분기·업종·경계·준비 상태·모든 지역과 네 원본 입력 |
| `boundaryRegionCodes`   | 호출자가 명시적으로 전달한 전체 경계 코드 목록                                         |
| `batches`               | 실제 참조한 모든 경계·통계 배치의 메타데이터, UUID별 한 건                             |
| `eligibleRegionCodes`   | 검증을 통과한 모든 입력 코드. 지표 전체 동일로 계산 보류해도 목록은 보존               |
| `excludedRegions`       | 제외 코드와 모든 지표별 사유                                                           |

`input.regions`는 코드·명칭·부모 구 코드/명칭, `sales`·`footTraffic`·`storeCount`·`closureRate`를 보존합니다. 각 지표는 `raw` 문자열 또는 NULL, `source.rowPresent`, 실제 `sourceBatchId`, `eligible`, 안전한 `batch` 메타데이터를 담습니다. 행 없음·NULL·실제 0·부적격 출처·비유한 값·음수·N=0을 합치지 않습니다. 원본 숫자를 다시 포맷하지 않으므로 `1.0`과 `1.00`은 입력 해시가 다릅니다.

배치 메타데이터는 기존 모델의 UUID·데이터셋·원천 종류·범위·기간·체크섬·ETL 버전·상태·시작/종료/게시 시각입니다. 동일 UUID의 메타데이터 충돌, 실제 행 ID와 메타데이터 ID 불일치, 적격성 모순은 거부합니다. 원천 경로·`source_reference`·오류 원문·인증정보 필드는 없습니다.

전체 경계 코드와 모든 입력 행의 코드가 정확히 일치해야 합니다. 완비·제외 목록도 중복·누락 없이 전체 경계를 분할해야 합니다. 배치 목록은 행들이 실제 참조한 배치와 같아야 합니다. 재현 시 제외 사유와 완비 목록을 다시 계산합니다. 따라서 기록된 전체 목록에서 지역 한 건만 빼거나 제외 지역을 숨긴 아티팩트는 해시를 다시 만들어도 거부됩니다.

**완전성의 한계:** 전체 경계 목록 자체가 진짜 서울 전체인지는 이 파일만으로 증명할 수 없습니다. 호출자가 행과 전체 목록을 함께 축소하고 새 해시·기대 결과까지 만들면 독립적인 승인 목록 없이는 탐지할 수 없습니다. 생성 시 Repository의 동일 스냅샷 전체 경계 목록을 전달해야 하며, 후속 승인 manifest는 이 목록·출처·해시를 독립적으로 고정해야 합니다. 25구·421동을 영구 승인 수치로 하드코딩하지 않았습니다.

생성 대상은 기존 Service가 지원하는 `20262`·`CS100010`의 준비된 전체 경계·데이터셋입니다. 구와 동은 각각 별도 아티팩트입니다. 경계/데이터셋 미준비 자료를 완전한 재현용 입력으로 봉인하지 않습니다. 완비 n≤1 또는 지표 전체 동일은 기존 내부 후보 규칙대로 점수 없이 보류 사유를 재현하며, 0점으로 대체하지 않습니다.

## 3. 정규 JSON과 R01

1. 지역·완비·제외 코드는 Unicode 코드 포인트 오름차순, 배치는 UUID 문자열 오름차순으로 정렬합니다. 사유는 기존 `ReasonCode` 선언 순서 뒤 지표 선언 순서입니다. 같은 목록의 중복은 거부합니다.
2. 모든 객체 키는 로케일과 무관한 Unicode 코드 포인트 순서입니다. UTF-16 코드 유닛 순서와 다른 보충 문자도 검증합니다.
3. UTF-8, BOM·불필요한 공백·끝 개행 없음. 비ASCII와 `/`는 그대로, 따옴표·역슬래시는 이스케이프합니다. 제어문자는 `\b`·`\f`·`\n`·`\r`·`\t`를 우선 사용하고 나머지는 소문자 4자리 `\u` 표기입니다. 잘못된 UTF-8·짝 없는 surrogate는 거부합니다.
4. UUID는 소문자, 모든 시각은 UTC ISO-8601 `Z`로 씁니다. 소수 초 끝 0은 제거하며 정수 초에는 소수부가 없습니다. 예: `09:00:00.100+09:00` → `00:00:00.1Z`.
5. 숫자 입력·분수 분자/분모는 문자열입니다. 집단 크기·동률 수만 JSON 정수입니다. 분수는 기존 계산기처럼 약분하고 분모를 양수로 유지합니다.
6. 이 규칙으로 만든 **payload 전체 바이트**의 SHA-256을 계산합니다. 요청 시각·해시 자신·기대 결과·승인 메타데이터는 입력 해시 대상이 아닙니다.

`decode`는 중복 키·누락 필드·알 수 없는 필드·잘못된 버전·JSON 손상·추가 JSON 값·잘못된 자료형·primitive NULL·해시 불일치를 거부합니다. 유효한 JSON의 공백·키 순서 등은 정규화하고, 정상화된 payload의 해시를 대조합니다. 기대 결과를 변조해도 입력 해시는 같을 수 있지만 **재현 대조가 실패하므로 decode는 거부**합니다. 오류 메시지에 입력·접속정보·원본 예외를 붙이지 않습니다.

독립 검산은 Python 표준 `json`·`hashlib`로 별도 작성한 합성 5지역 payload를 사용했습니다. 정규 바이트 14,935개의 기대 해시는 `c671ee9b6263f5ff92334f7cc2a5e522f5f84872fe0cda2d38c1f1db71759f95`입니다. 별도 작은 JSON 벡터로 제어문자·한글·보충 문자 정렬과 SHA-256도 검증합니다. 실제 원본 fixture는 아닙니다.

## 4. DB 없는 생성·해시 검증·재현 절차

다음은 내부 Java 호출 예시입니다. `fullBoundaryCodes`는 선택 지역 코드가 아니라 같은 Repository 조회가 반환한 전체 경계 코드 목록입니다. 이 코드는 파일을 쓰지 않습니다.

```java
var artifact = ScoreSnapshotArtifact.capture(input, fullBoundaryCodes, requestedAt);
var codec = new ScoreSnapshotCodec();
byte[] json = codec.encode(artifact);

// DB 연결이나 Spring Context 없이 바이트를 검증하고 다시 계산한다.
var restored = codec.decode(json);
var reproduced = restored.replay();
String hash = restored.inputSnapshotId();
// publicationState()는 항상 NOT_APPROVED이다.
```

`replay`는 지원 알고리즘·정책을 확인하고 공통 입력 검증 → 기존 `AScoreCalculator` 순서로 계산합니다. 보존된 완비·제외 목록, 지표별 사유, 보류 사유, 모든 지역의 정규화·기여·최종 A·평균 순위·동률 수가 정확히 같아야 합니다. 분수와 원본은 표시용 소수로 바꾸지 않습니다. 다른 정책을 봉인하면 해시는 달라지지만, 그 정책을 지원하는 것으로 자동 채택하지 않으며 재현은 거부합니다.

테스트는 합성 5지역의 A `40, 40, 45, 65, 60`, 평균 순위 `4.5, 4.5, 3, 1, 2`와 '라'의 기여 `22.5, 22.5, 15, 5`를 검증합니다. 제외 입력·실제 0·큰 정수·긴 소수·집단 보류·구/동 분리와 정확한 결과 변조 거부도 확인합니다.

실행 위치는 `backend/`입니다. DB 없는 R01·R02 테스트만 실행하려면 다음을 사용합니다.

```bash
./gradlew test --tests '*ScoreSnapshotTests'
```

전체 검증 명령은 다음과 같습니다. 통합 테스트는 기존 방식의 Docker 일회용 PostGIS만 사용하며 개발 DB 환경변수가 필요하지 않습니다.

```bash
./gradlew test
./gradlew integrationTest
./gradlew build
./gradlew spotlessCheck
```

## 5. 검증 범위와 후속 승인 작업

2026-11-02 검증 결과: 신규 스냅샷 테스트 **44개**, 전체 단위 **526개**, 일회용 DB 통합 **828개**가 모두 통과했고 실패·건너뜀은 없습니다. 빌드·Spotless, 문서 Prettier·링크·표, 신규 파일을 포함한 공백 검사도 확인했습니다. 실제 개발 DB 회귀 도구는 실행하지 않았습니다.

- **R01:** 합성 전체 payload의 순서·시각 불변성, 변경 탐지, 고정 해시, JSON 왕복 및 손상 거부를 검증합니다.
- **R02:** 합성 전체 집단과 원본 표현을 보존하고, DB 없이 기존 계산기의 정확한 결과·제외/보류를 재현합니다. 현재 구현은 승인된 실데이터 보존본의 재현 성공을 뜻하지 않습니다.
- **R03:** 과거 2026-11-02 12:17 전체 입력 fixture가 없어 완전 재현은 계속 미완료입니다. 이전 대표 6곳·현재 446개 검산과 이번 합성 테스트는 서로 다른 증거입니다.
- 정책·원천 판본의 의미적 비교 가능성·커버리지 승인, 실제 창업 성과 검증은 수행하지 않았습니다. 모든 결과는 계속 `NOT_APPROVED`입니다.

후속 작업에서는 실제 전체 경계·입력·행별 출처·제외 목록을 명시적 절차로 보존하고, 승인 manifest와 해시의 연결을 검증해야 합니다. 보관 위치·쓰기 방지·기존 파일 덮어쓰기 방지·접근 권한·백업·배포 책임, 기대 결과/승인 아티팩트의 진위 검증도 별도로 정해야 합니다. 해시는 내용의 동일성만 확인하며 승인 서명이나 신뢰할 수 있는 최초 수집을 대신하지 않습니다.
