# 공간 데이터 도입 전 검증 절차

이 문서는 향후 대표 좌표 검산과 Polygon 도입의 검사·판정·결과 기록 기준입니다. 현재 보유 자료와 공식 CRS 확인은 [데이터 목록](data-catalog.md), 장기 설계·업종/기간 정책은 [아키텍처](architecture.md), 실행 순서는 [로드맵](roadmap.md)에 둡니다. 아래 검사는 아직 수행하지 않았으며 이번 작업은 문서 정리만 합니다.

## 1. EPSG:5181 대표 좌표 변환 검산

영역-상권의 현재 공식 데이터셋 CRS 메타데이터 확인과 보관 CSV의 출처·배포 버전 및 실제 변환 결과 검증을 분리합니다. 후속 검산은 DB·환경 설정을 변경하거나 ETL을 실행하지 않고 수행합니다.

1. 보관 CSV의 파일명·SHA-256과 선택한 상권 코드·이름·원본 X/Y를 기록합니다. 서울 동서남북과 중앙의 대표 샘플, 좌표 범위 양끝 사례를 포함합니다.
2. 원천 EPSG:5181·목표 EPSG:4326·사용 도구/버전·축 순서를 기록합니다. 현재 ETL의 `always_xy=True`와 출력 `(경도, 위도)` 순서를 대조합니다.
3. 각 변환 결과가 유한값이고 경위도 범위·서울 위치와 맞는지 확인합니다. 독립 변환 도구 또는 공식 위치 근거와 대조하고, 비교 기준·허용 오차·실측 차이를 기록합니다. 허용 오차는 대조 자료의 정확도를 근거로 검산 전에 결정합니다.
4. 단순 범위 통과나 같은 변환 코드 재실행만으로 검증 완료하지 않습니다. 불일치 원인·해결 결과를 남기며 검산 전 결과를 서비스 기준으로 사용하거나 상권을 재적재하지 않습니다. 대표 POINT 검산은 Polygon 포함 판정 검증을 대신하지 않습니다.

## 2. Polygon 원본과 버전 고정

- 행정동 경계를 먼저 확보하고 이후 상권 경계를 검토합니다. 파일마다 공식 데이터셋 URL·제공기관·다운로드일·파일명·SHA-256·포맷/레이어·인코딩·이용 조건·원천 CRS를 기록합니다. 원본은 변경하지 않고 검사합니다.
- 경계의 기준 시점·유효 기간·공표/갱신 버전과 코드 체계의 공식 정의를 확인합니다. 다운로드일·페이지 갱신일을 경계 기준일로 대체하지 않습니다. 공식 페이지에 ZIP이 있다는 사실은 보관 파일의 geometry나 호환성 검증이 아닙니다.
- 2025 Q1~Q4 각각의 통계와 경계가 호환되는지 확인합니다. 행정동 신설·폐지·분동·통합·이름/코드 변경 이력을 확인하며, 동일 코드가 유지돼도 경계가 바뀌었는지 검사합니다. 한 경계 버전으로 네 분기를 설명할 수 없다면 분기별 버전 연결 또는 분석 범위를 별도 결정합니다. 근거가 없으면 호환성은 미확인입니다.

## 3. 행정동 Polygon 검사표

원본 feature 단위 결과와 서비스에서 사용할 논리적 행정동 단위 결과를 구분합니다. 코드·이름은 원문을 보존하고 비교용 문자열의 공백 정리 규칙을 기록합니다. 숫자 변환·임의 자릿수 절단·접두어 제거로 코드를 맞추지 않습니다. 같은 `행정동_코드` 컬럼 이름만으로 코드 체계가 같다고 판단하지 않습니다.

| 검사 | 반드시 기록할 결과·판정 기준 |
| --- | --- |
| geometry type | 레이어별 type/차원별 건수. Polygon/MultiPolygon을 대상으로 하고 POINT·LineString·GeometryCollection 등 예상 밖 형상은 해결 전 도입 보류 |
| SRID / CRS | 공식 정의·파일 CRS 선언·실제 좌표 범위를 대조하고 원천 SRID와 향후 변환 목표 SRID를 기록. 누락/혼재/불일치가 있으면 추측해 SRID만 부여하지 않음 |
| feature count | 전체 feature 수·유효 feature 수·고유 `dong_code` 수를 각각 기록. 425개 통계 행정동과 대조하되 feature 수만 같다고 통과시키지 않음 |
| `dong_code` NULL / unique | NULL·공백 코드 건수와 해당 feature, 코드별 중복 건수/목록 기록. 사용 대상의 NULL·공백은 0건, 한 버전에서 논리적 `dong_code`는 유일해야 함 |
| 이름 | NULL/공백 이름·동일 코드의 복수 이름 및 두 통계 원본과 경계의 이름 불일치 목록 기록. 공백 차이와 실제 명칭 변경을 구분하고 공식 근거 없이 자동 치환하지 않음 |
| NULL / empty geometry | geometry NULL과 empty를 별도로 세고 코드/feature 목록 기록. 사용 대상은 모두 0건이어야 함 |
| invalid geometry | 유효성 검사 도구/버전·invalid 건수·원인·feature 목록 기록. 사용 대상은 invalid 0건이어야 하며, 자기 교차 등 오류는 자동 보정으로 숨기지 않고 해결 전후 형상·면적 변화와 근거를 검토 |
| 중복 geometry / logical key | 바이트 동일 형상과 꼭짓점 순서 등이 달라도 공간적으로 동일한 형상을 구분해 검사. 같은/다른 코드의 중복 형상과 `(경계 버전, dong_code)` 중복 목록을 기록하고 미해결 중복은 도입 보류 |
| 여러 feature로 나뉜 같은 코드 | 섬·분리 영역인지 중복 레코드인지 원천 정의로 확인. 필요하면 추후 MultiPolygon 통합 규칙을 정하되 원본 feature 수와 변환 후 논리 객체 수를 함께 기록하고 임의 삭제하지 않음 |
| 중첩·경계선 | 서로 다른 행정동의 내부 면적 중첩과 공유 경계선 접촉을 구분해 기록. 면적/거리의 CRS·단위·허용 오차를 명시하고 경계선 위 후보 좌표·다중 매칭 처리 규칙을 API 설계 전에 결정 |

## 4. 통계 코드 집합과 이름 대조

1. 보관한 2025 점포·매출 CSV 전체에서 업종 매핑 여부와 관계없이 코드·이름을 추출합니다. 두 자료를 각각 분기별 및 Q1~Q4 전체로 비교합니다. 현재 기준은 각각 425개이며 전체 코드 집합이 같다는 기존 manifest/검증 기록입니다. 이번에는 이 검사나 DB 조회를 다시 실행하지 않았습니다.
2. `S_store`를 점포 통계 코드 집합, `S_sales`를 매출 통계 코드 집합으로 두고 동등 여부와 양방향 차이를 기록합니다. 두 집합이 같아야 공통 기준 `S`로 사용합니다. 카페 한 업종이나 현재 API lookup만 추출해 전체 통계 집합을 대신하지 않습니다.
3. 선택한 한 경계 버전의 고유 행정동 코드 집합을 `P`로 두고 다음을 기록합니다. 여기서 **intersection count는 공간 형상 교차 건수가 아니라 코드 집합의 교집합 수**입니다.

| 결과 항목 | 정의 | 425개 전체 통계를 지원하는 목표 |
| --- | --- | --- |
| 통계 코드 수 / 경계 코드 수 | `count(S)` / `count(P)` | 각각 425 |
| intersection count | `count(S ∩ P)` | 425 |
| 통계에만 존재하는 코드 | `S - P`의 건수와 전체 코드/이름 목록 | 0 |
| 경계에만 존재하는 코드 | `P - S`의 건수와 전체 코드/이름 목록 | 0 |
| 같은 코드의 이름 불일치 | 자료·분기·코드·통계 이름·경계 이름·공식 변경 근거 | 미해결 0 |

분기별 비교도 같은 결과 형식으로 남깁니다. 두 파일이 모두 425개여도 코드가 다를 수 있으므로 실제 집합을 비교합니다. 코드/이름이 맞아도 2절의 시점·버전 호환성 검사를 별도로 통과해야 합니다. 차이가 있으면 누락을 숨기거나 최근접 지역으로 연결하지 않고 원인·공식 대응표·지원 가능한 범위를 검토하며, 425개 전체 호환 완료로 표시하지 않습니다.

## 5. 이후 상권 Polygon 대조

행정동 검사 항목을 상권 코드와 경계 버전에 맞게 적용합니다. 경계 코드 집합을 영역 CSV의 1,650개 상권 코드와 먼저 대조하고, 2025 상권 매출의 1,577개 코드와도 분기별/전체 교집합·양방향 차집합·이름을 별도로 비교합니다. 영역에는 있지만 매출에는 없는 73개 코드라는 기존 사실과 새 경계의 누락을 혼동하지 않습니다. 대표 POINT·면적·상권의 `dong_code` 참조만으로 실제 경계나 행정동 포함 관계를 확정하지 않습니다.

## 6. 결과 기록과 도입 판단

검증 보고서에는 검사일·원본/통계 파일 해시·경계 버전·코드/이름 비교 규칙·도구/버전·모든 검사 건수·불일치 전체 목록·공식 근거·해결/미해결 사유를 포함합니다. 현재의 미완료 항목을 다음처럼 각각 관리합니다.

- 대표 좌표: 공식 CRS 메타데이터 확인과 실제 좌표 검산 결과를 분리합니다.
- 행정동/상권 Polygon: 파일 확보, geometry/SRID 검사, 코드/이름 대조, 2025 분기별 버전 호환성을 각각 기록합니다.
- 소상공인 업종: 공식 분류 버전과 원본 소분류 코드/명칭별 분포·CAFE 포함/제외 기준을 검증한 뒤 출처 `SEMAS` 매핑을 별도 결정합니다. `SEOUL / CS100010`으로 대체하지 않고 점포 `industry_id=NULL` 정책을 유지합니다.
- 기간: 공간 결과에도 2025 통계 분기·파일명 기준 2026-06 점포 스냅샷·경계 시점/버전을 별도로 기록합니다. 점포 소실은 폐업의 근거로 사용하지 않습니다.

미해결 오류나 버전 근거 부족이 있으면 도입을 보류합니다. 대표 좌표 검산과 행정동 Polygon 정합성 결과를 먼저 검토한 뒤 공간 스키마·Flyway V2를 설계합니다. 이 문서는 새 테이블·migration·Polygon ETL·공간 조회 SQL/API·지도 UI를 구현하거나 기존 DB를 변경하는 작업을 포함하지 않습니다.
