# 창업 환경 점수 설계·데이터 적합성 검토

> **후속 실험 안내:** 1~8절과 부록은 기존 데이터 검토·문서 정리 당시의 기록입니다. 점수·순위 미계산 및 실험 미실행 표현도 당시 범위입니다. 이후 [9절의 후보별 1차 비교](#9-탐색-실험-abc-후보의-1차-비교-2026-11-01)와 [10절의 정규화 방식 2차 비교](#10-정규화-방식-2차-비교-실험-2026-11-01)를 추가했으며, 정규화·가중치 채택과 서비스 구현은 여전히 미확정입니다.

이 문서는 창업 환경 점수에 사용할 데이터가 충분하고 서로 비교 가능한지 검토한 결과입니다. **실제 점수·순위는 계산하지 않았으며, 점수 산식·가중치·정규화·새 API·저장 스키마는 확정하지 않았습니다.**

검토일은 2026-11-01(KST)이며, 당시 `project-upgrade` 작업 트리를 기준으로 했습니다. 대상은 `20262`(2026년 2분기), 카페 업종 `CS100010`(DB 명칭 `커피-음료`)입니다. 유동인구는 업종 구분 없이 지역·분기로만 연결합니다.

기존 [서비스 요구사항](service-spec.md), [데이터 계약](data-design.md), [자치구 통계 정책](district-statistics-policy.md)을 유지합니다. 아래 DB 수치는 기존 읽기 전용 분석 기록이며, 이번 문서 정리에서는 DB 조회나 새 분석을 수행하지 않았습니다.

## 1. 결론과 근거 수준

- **검증된 사실:** 분석 당시 로컬 개발 DB의 최신 정상 경계는 25구·425동입니다. 대상 분기의 정상 게시 점포·인구는 모든 지역에 존재하고, 매출은 자치구 25/25, 행정동 421/425입니다. 존재하는 행의 14개 측정값에는 NULL이 없지만 실제 0은 있습니다.
- **설계 제안:** 구·동별로 분리된 같은 분기·업종의 비교 집단에서 정규화하고, 원본과 출처를 보존합니다. 매출이 필수인 점수 후보에서는 매출 행이 없는 4개 동을 산출 불가로 두는 안을 제안합니다. 규모형 지표와 점포당 지표를 비교하되 어느 후보도 현 단계에서 채택하지 않습니다.
- **미확정 사항:** 통계 경계의 시점과 자료별 카페 모집단의 일치 여부, 개폐업률의 정확한 분모·반올림, 매출·인구의 세부 기간 의미, 결측 사유가 남아 있습니다. 가중치·정규화·소규모 기준·기간 안정성도 미확정입니다.

**행 존재와 수치 품질은 확인했지만 점수의 타당성이 입증된 것은 아닙니다.** 다음 단계는 입력의 의미·호환성과 결측 원인을 확인한 뒤 정규화·가중치 후보를 비교하는 것입니다. [미확정 사항과 다음 검증](#7-미확정-사항과-다음-검증)에서 확인할 수 있습니다.

### 반드시 유지할 게시 조건

1. 경계는 `SEOUL_DONG_BOUNDARY / SHAPEFILE / SEOUL / scope_code IS NULL / PUBLISHED / published_at IS NOT NULL` 중 `published_at, started_at, batch_id DESC` 첫 배치를 선택한 **후** 실제 구·동 경계 행 존재를 검사합니다. 최신 적격 배치가 비었다고 과거 경계로 되돌아가지 않습니다.
2. 구는 선택 경계 게시본을 참조해야 하고, 동은 자신과 부모 구 모두 그 게시본을 참조해야 합니다. 이번 커버리지의 분모도 이 조건을 사용합니다. 현재 경계의 코드 일치가 통계 시점의 경계 일치까지 증명하지는 않습니다.
3. 통계는 아래 데이터셋과 `CSV / SEOUL / scope_code IS NULL / PUBLISHED / published_at IS NOT NULL`을 **행별 `source_batch_id` JOIN**으로 검사합니다. `FAILED / RUNNING / SKIPPED` 및 잘못된 출처는 제외합니다.

| 단위   | 점포                        | 매출                        | 인구                               |
| ------ | --------------------------- | --------------------------- | ---------------------------------- |
| 자치구 | `SEOUL_DISTRICT_STORE_STAT` | `SEOUL_DISTRICT_SALES_STAT` | `SEOUL_DISTRICT_FOOT_TRAFFIC_STAT` |
| 행정동 | `SEOUL_DONG_STORE_STAT`     | `SEOUL_DONG_SALES_STAT`     | `SEOUL_DONG_FOOT_TRAFFIC_STAT`     |

통계에는 전역 최신 배치 제한을 추가하지 않습니다. ETL이 보존한 과거 정상 행을 새 빈 배치나 `SKIPPED`가 가리지 않아야 합니다. 이번에는 자료별 한 배치씩 관찰했지만 이를 단일 배치 제약으로 일반화하지 않습니다. 점포·매출·인구의 UUID가 서로 다르다는 것은 정상입니다.

유효한 실제 행이 전체에 하나라도 있어야 해당 데이터셋이 준비된 상태입니다. 기존 API는 다음을 구분합니다.

- 경계·데이터셋 미준비: 503.
- 현행 지역 미존재: 404.
- 데이터셋 준비 후 조건별 행 미존재: `200, data: null`.
- 측정값 전부 NULL인 실제 행: `data` 객체와 출처 유지.

점수 산출 불가를 향후 어떻게 표현하더라도 이 통계 API 계약은 유지합니다.

## 3. 검증된 사실: 실제 DB 분석

### 실행 범위와 재현성

아래는 2026-11-01에 수행한 기존 분석 기록입니다. 당시 `compose.yaml`의 로컬 `db` 서비스(127.0.0.1에 공개)를 사용했습니다. 최초 Docker 소켓 접근은 샌드박스 권한으로 차단되어 읽기 전용 상태 확인·SQL 실행 권한을 사용했습니다. DB 시작·적재·마이그레이션·API 서버 실행은 하지 않았습니다.

- 기본 분석: 2026-11-01 **13:36:33.855834 KST**.
- 파생지표·극값 추가 분석: 같은 날 **13:37:04.191417 KST**.
- 각각 `BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY`, `SET LOCAL statement_timeout='30s'`, 마지막 `ROLLBACK`으로 종료했습니다. `PGOPTIONS=-c default_transaction_read_only=on`도 적용했고 DB 응답에서 `transaction_read_only=on`, `transaction_isolation=repeatable read`를 확인했습니다.
- 두 분석은 **별도의 트랜잭션**입니다. 각 분석 내부는 같은 스냅샷이며, 두 시점이 하나의 스냅샷이라고 주장하지 않습니다. 원본 파일·공공 포털을 재수집하거나 과거 문서의 검증을 재수행한 것은 아닙니다.
- `source_reference`의 경로·인증정보는 출력하거나 문서에 싣지 않았습니다.

**실제 0이 있는 값**

실제 0은 다음 행정동 측정값에서 관찰했습니다.

- 프랜차이즈 점포 수: 4행.
- 개업 점포 수·개업률: 각각 95행.
- 폐업 점포 수·폐업률: 각각 102행.
- 주중·주말 매출액: 각각 1행.

다른 측정값의 0은 없고 자치구의 14개 측정값에도 0은 없습니다. 개·폐업 수가 양수인데 대응 비율이 0인 행은 없었습니다. 매출액의 실제 0 표본은 다음과 같습니다.

### 분포 산출 기준

아래 표는 DB의 원본 수치를 사용합니다. 점포는 개, 비율은 %, 매출액은 원, 인구는 원천 추정 유동 규모입니다. `당월`을 분기 총액·월평균으로 환산하지 않았고 인구를 고유 방문자·카페 고객·일평균으로 해석하지 않았습니다.

표는 범위·커버리지와 분위수를 나누어 표시했습니다. `유효값 n`은 분석에 포함한 값의 수, `0`은 실제 0인 행 수, `IQR 후보`는 아래 기준에 해당하는 행 수입니다.

- **분위수:** Q1·중앙값·Q3·P95는 지역 단위별 `percentile_disc`이며 NULL·없는 행을 제외합니다. **0은 포함**합니다.
- **탐색용 이상치:** IQR(사분위 범위) 후보는 `x < Q1 - 1.5×IQR` 또는 `x > Q3 + 1.5×IQR`인 행 수이고 경계값은 포함하지 않습니다. 이는 오류·삭제·점수 제외 판정이 아닙니다.
- **분모 차이:** 매출 분포는 421동, 점포·인구는 425동으로 계산했습니다. 이 단변량 분포를 그대로 하나의 최종 정규화 집단으로 쓰면 안 됩니다.

## 4. 설계 제안: 집계 단위·분기·입력

### 단위와 기준 분기

- 구 점수는 공식 `district_*_stat`, 동 점수는 `dong_*_stat`만 사용합니다. 동 점수 평균으로 구 점수를 만들거나 공식 구 결측을 동 합산으로 대체하지 않습니다. 구·동 각각 서울 전체 같은 단위 내에서 비교하며 선택한 구의 동들만으로 요청마다 재정규화하지 않습니다.
- 이번 기준은 명시된 `20262`로 고정합니다. 자료마다 가장 최신 분기를 따로 고르지 않고 같은 지역의 점포·매출·인구가 모두 같은 분기인지 확인합니다. 게시일이 늦다는 이유로 기준 분기가 최신이라고 판단하지 않습니다.
- 향후 기본 분기를 고른다면 자료별 최신 분기의 최솟값만 취하지 말고 정상 출처·현재 대상 지역의 실제 커버리지까지 확인한 공통 분기를 검토합니다. 대체 분기가 있다면 사용자에게 기준 변경을 명시하고, 요청 분기의 결측을 다른 분기로 자동 채우지 않습니다.
- 구·동의 점수는 비교 집단이 다릅니다. 구 70점과 동 70점의 직접 비교, 여러 구의 점수 합계, 반경 500m·1km 및 개별 후보지 고유 점수로의 해석을 허용하지 않습니다.

개폐업률은 **원천 비율**을 사용하며 `개폐업 수/현재 store_count`로 재계산하지 않습니다. 순개업 수·개업률−폐업률을 곧바로 성장·안정성 점수로 해석하지 않습니다.

면적당 밀집도는 통계 시점 경계·면적 기준을 확인하지 않았으므로 이번 검토에서 계산하지 않았습니다.

소규모 점포는 10개·20개 등을 **검증할 임계값 후보**로만 남깁니다. 둘 중 어느 값도 확정하지 않았고 현재 자료를 일괄 제외하지 않았습니다.

신뢰 가능한 최소 표본 기준이 정해지기 전 작은 분모의 비율·점포당 지표를 무조건 최고 평가하지 않습니다. 분모 안정성·여러 분기 민감도를 먼저 확인하고, 미달을 경고만 할지 산출 불가로 할지 결정해야 합니다.

개업률·주중/주말·성별처럼 설명용으로만 쓰는 값의 결측은 곧바로 전체 점수 불가를 뜻하지 않습니다. **채택한 버전의 필수 입력 목록**으로 판정해야 하며 이 문서의 14개 필드를 모두 필수로 정한 것은 아닙니다.

## 6. 설계 제안: 정규화와 가중치 후보

### 정규화 대안

| 방식                                        | 장점                                 | 이번 데이터에서의 제한                                                          |
| ------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------- |
| 원시 min-max                                | 단순하고 값 차이를 직접 반영         | 역삼1동 등 극값에 민감하고 대부분의 매출 차이가 압축됨; 기본 채택은 권하지 않음 |
| 동률 평균 순위 기반 0~1 변환                | 긴 꼬리·단위 차이에 강하고 설명 가능 | 값 차이의 크기를 잃음; 25구는 순위 간격이 크고, 개폐업률은 동률이 많음          |
| `log(1+x)` 후 P05~P95 winsorization·min-max | 0을 유지하며 규모 차이와 꼬리를 완화 | 꼬리의 서로 다른 값이 같은 점수로 묶임; 소규모 분모·의미 불일치를 해결하지 못함 |

**우선 비교할 제안**은 동률 평균 순위 방식과 log/winsor 방식입니다. 양쪽의 지역 순위·동률·상하위 변동을 비교한 뒤 선택하며, 아직 어느 방식도 채택하지 않았습니다.

각 후보의 수학적 정의는 다음과 같습니다. **구현·채택·최종 점수 계산은 하지 않았습니다.**

- **순위 후보:** 증가 방향 지표는 `R(x)=(평균 순위(x)-1)/(n-1)`, 감소 방향은 `1-R(x)`입니다. 같은 값은 같은 점수를 받고, 0 동률을 코드순으로 나누지 않습니다.
- **log 후보:** 먼저 `y=ln(1+x)`, 같은 비교 집단의 P05·P95로 `y`를 제한한 후 두 경계로 0~1 변환합니다. 경계가 같으면 계산하지 않습니다. winsorization은 이처럼 분석값의 꼬리를 정해진 경계로 제한하는 변환입니다.

log는 순서를 바꾸지 않으므로 순위 방식 앞에 log를 중복 적용할 이유는 없습니다. 개폐업률처럼 이미 비율인 지표에 log를 일괄 적용하는 것도 보류합니다.

원본을 100%로 자르는 것과 분석 변환에서 꼬리를 제한하는 것을 구분해야 합니다. 원본·변환값·기준은 따로 설명합니다.

**비교 집단의 전제**

- 단위·분기·업종·정상 출처·필수 입력·소규모 정책을 고정한 뒤 구성합니다.
- 현재 입력만 보면 구 25개, 동 421개가 공통 완비 후보입니다. 추가 제외 기준을 정하면 집단을 다시 확정해야 합니다.
- 지표마다 편한 지역만 골라 서로 다른 기준으로 정규화하지 않습니다. 품질 보고의 425동 단변량 분포와 최종 점수 비교 집단을 혼동하지 않습니다.

### 가중치 후보

아래 숫자는 분포와 해석의 차이를 검토하기 위한 **예시 제안**입니다. 사용자 합의·성과 데이터 학습·검증으로 정한 값이 아니며 어느 후보로도 점수나 순위를 계산하지 않았습니다. `+`는 증가, `−`는 감소 방향의 정규화 결과를 뜻합니다.

**입력·방향·가중치 후보**

| 후보             | 입력과 가중치(합계 1)                                                          |
| ---------------- | ------------------------------------------------------------------------------ |
| A: 규모형 기준선 | 당월 매출액(+) 0.30, 총 유동인구(+) 0.30, 전체 점포 수(−) 0.20, 폐업률(−) 0.20 |
| B: 점포당 대안   | 당월 매출액/점포 수(+) 0.40, 총 유동인구/점포 수(+) 0.35, 폐업률(−) 0.25       |
| C: B의 비중 비교 | B의 같은 세 지표에 각각 1/3                                                    |

**후보별 장점과 한계**

| 후보             | 장점                                       | 확인할 문제                                                             |
| ---------------- | ------------------------------------------ | ----------------------------------------------------------------------- |
| A: 규모형 기준선 | 현재 직접 제공 지표로 근거를 추적하기 쉬움 | 규모 편향·매출/점포 상관, 점포 감소의 의미가 불명확                     |
| B: 점포당 대안   | 규모 보정 가능성을 비교할 수 있음          | 동일 분모가 두 번 반영됨, 작은 분모·매출 모집단 불일치·인구 업종 불일치 |
| C: B의 비중 비교 | 특정 축의 우대를 줄인 민감도 기준          | 균등 비중도 객관적 정답이 아니며 B의 입력 한계는 그대로                 |

세 후보에서는 개업률을 가중치 0인 설명 지표로 두는 안을 제안합니다. 총매출과 점포당 매출, 총인구와 점포당 인구, 총·성별 인구, 전체·일반·프랜차이즈 점포를 동시에 독립 점수로 더하지 않습니다.

각 후보의 점수 형식은 향후 `100 × Σ(wᵢ × 정규화 지표ᵢ)`를 검토할 수 있으나 이번에는 실행하지 않았습니다.

**현재 권고:** 최종 가중치를 확정하지 않습니다. A는 규모 편향 확인용 기준선, B·C는 분모 효과 확인용 대안입니다. 입력의 의미가 검증된 뒤에만 후속 비교를 진행합니다.

후속 비교에서 확인할 항목은 다음과 같습니다.

- 단위별 분포·동률·순위 상관·상하위 변동.
- 가중치 ±0.05 변화에 대한 민감도. 다른 비중을 명시적으로 조정해 합계 1을 유지합니다.
- 정규화 대안과 소규모 기준에 대한 민감도.
- 폐업률과 점포 수를 모두 감소 방향으로 반영하는 가설.

결측 동 4개를 제외해도 전체 대상 425동 중 누락 사실을 공개해야 합니다. 표본 부족·동일값일 때 임의 중립 점수를 주지 않고 해당 버전의 비교 기준을 재검토합니다.

0~100은 상대평가 범위입니다. 80점을 성공 확률 80%로 설명하거나 실제 검증 없이 좋음/나쁨 구간을 고정하지 않습니다.

## 7. 미확정 사항과 다음 검증

아래 항목은 모두 후속 확인이 필요합니다. 입력의 의미·품질 검증과 정규화·가중치 후보의 채택 결정을 구분합니다.

2. **결측 원인:** 4개 동의 매출 원천 행 존재 여부와 미제공·비공개·적재 차이를 대조해야 합니다. 이번에는 원본 재열람·외부 조회·재적재를 하지 않았습니다.

4. **이상치 사유:** 북아현동 인구, 둔촌1동 낮은 인구, 삼성동·돈암1동 매출 등은 오류로 확정하지 않습니다. 기준 시점·개발/정비·표본·공간 배분 등의 가능성을 실제 근거로 확인해야 합니다.

5. **기간 안정성:** 이번 검토는 20262 단면입니다. 과거 분기 추세·최신 분기 탐색·구/동 합계 차이·정규화/가중치별 실제 순위·백테스트·불확실성은 미실행입니다.

6. **채택 결정:** 필수 입력, 개업률 방향, 소규모 기준, 비교 집단의 최소 크기·필요 커버리지, 이상치 처리, 정규화·가중치·표시 반올림·점수 구간은 미확정입니다. 전처리·입력의 호환성이 확인되기 전에는 공개 점수로 확정하지 않습니다.

7. **재현성·저장:** 채택 시 지역 단위/코드·분기·업종·경계 배치·각 통계 행의 실제 배치·원본 지표·필수 입력 및 제외 사유·비교 집단 목록·정규화 기준·가중치·알고리즘 버전을 보존하는 방향을 제안합니다.

## 8. 검증 범위와 미실행 이유

**기존 DB 분석에서 확인한 범위**

실제 로컬 DB에서 정상 게시 조건·현행 경계·대상 행·14개 측정값의 커버리지/NULL/0/분위수/IQR·합계 차이·극값·소규모 분모·상관·점포당 탐색을 읽기 전용으로 확인했습니다. SQL은 오류 시 중단하도록 `ON_ERROR_STOP=1`을 사용했습니다. 분석 중 데이터 변경 SQL·DDL·임시 테이블·파일 산출은 사용하지 않았습니다.

**기존 검토에서 실행하지 않은 범위와 이유**

당시에는 문서만 추가했으므로 제품 동작 테스트·빌드·마이그레이션·ETL·DB 통합 테스트는 실행하지 않았습니다. 기존 문서에 기록된 합성 테스트·적재 검증과 이 문서의 실제 읽기 전용 분석은 구분합니다.

당시 최종 문서 검증은 링크·표·SQL 실행 결과 대조·변경 파일 범위·공백 오류 확인을 대상으로 했습니다. 원천 의미·성과에 대한 검증과 실제 점수 계산은 위 미확정 목록에 남겨 둡니다.

**이번 문서 정리의 범위**

가독성만 개선하며 DB 조회·새 분석·점수 계산은 수행하지 않았습니다. 기존 제목·링크·표·수치·배치 정보·수식·재현 SQL의 보존 여부와 Markdown·Prettier·공백 오류를 확인합니다.

### 계산·동률·검산 기준

각 단위의 공통 집단에서 증가 방향 지표는 `R(x)=(평균 순위(x)-1)/(n-1)`, 감소 방향은 `1-R(x)`로 정규화했습니다. 원본 값은 오름차순으로 순위를 매기고 같은 값에는 평균 순위를 부여했습니다. 코드순으로 동률을 나누지 않았습니다. 같은 집단에서 나눗셈 후 얻은 점포당 지표도 별도로 순위를 매겼습니다.

가중치는 6절의 A·B·C를 그대로 사용했습니다.

- A: 매출액 0.30, 총 유동인구 0.30, 점포 수 감소 방향 0.20, 폐업률 감소 방향 0.20.
- B: 매출액/점포 수 0.40, 유동인구/점포 수 0.35, 폐업률 감소 방향 0.25.
- C: B의 같은 세 지표에 정확한 **1/3**씩 적용했습니다. `0.3333`으로 근사하지 않았습니다.
- 세 후보의 가중치 합계는 모두 **1**이며 `100 × Σ(wᵢ × 정규화 지표ᵢ)`로 환산했습니다. 결측 대체·자동 비중 재분배·log·winsorization·최소 점포 수 제외는 적용하지 않았습니다.

SQL은 평균 순위의 정수 분자·분모를 유지해 점수 동률을 판정했습니다. 반환한 네 원본 입력을 Python 표준 라이브러리의 `Fraction`으로 다시 읽고, 정밀도 손실 없는 비율·평균 순위·정확한 가중합으로 검산했습니다. SQL의 점포당 NUMERIC 나눗셈과 유리수 비교 사이에도 순위 불일치는 없었습니다.

- 입력 정규화 순위 **2,676건**: 446지역 × 6지표가 일치했습니다.
- 점수 **1,338건**과 점수 순위 **1,338건**: 446지역 × 3모델이 각각 일치했습니다.
- 분포·평균·동률 건수와 Spearman 상관도 독립 계산과 일치했습니다. 상관의 DB 부동소수 근사 차이는 `1e-12` 미만이었습니다.
- 유효 집단은 모두 n>1이며, 사용한 지표가 전부 동일한 집단은 없었습니다. 입력별 서로 다른 값은 구에서 매출·인구·점포·점포당 두 지표 각각 25개, 폐업률 17개였고, 동에서는 매출·인구·점포당 두 지표 각각 421개, 점포 수 148개, 폐업률 20개였습니다.

최종 순위는 **반올림 전 점수의 내림차순 평균 순위**이며 1등부터 시작합니다. 0.5 단위 순위가 있을 수 있습니다. 점수·분포·표준편차는 소수 둘째 자리, 상관은 소수 넷째 자리로 표시했습니다. 표시 점수가 같다는 이유만으로 새 동률을 만들지 않았습니다. 코드순은 표에서 동률 지역을 나열할 때만 사용했습니다.

### 소규모 점포 지역의 영향

아래 구간은 위험을 관찰하기 위한 것이며 채택한 제외 정책이 아닙니다. **10개 미만은 20개 미만의 부분집합**입니다. 425동 기준 10개 미만 15동·20개 미만 66동에서 매출 결측을 제외한 결과, 공통 집단에서는 각각 12동·62동입니다. 자치구에는 두 구간에 해당하는 곳이 없습니다.

상위 약 10%는 `ceil(n×0.10)`번째 높은 점수 이상인 지역을 동률까지 포함한 집합으로 정했습니다. 421동에서는 세 모델 모두 43곳이었으며, 별도의 재정규화 없이 기존 점수를 집계했습니다.

| 점포 수 구간 | 동 수 | A 평균 | B 평균 | C 평균 | 상위 43동 진입 A·B·C |
| ------------ | ----- | ------ | ------ | ------ | -------------------- |
| <10          | 12    | 41.08  | 62.05  | 64.38  | 0·4·6                |
| <20          | 62    | 40.75  | 55.02  | 56.43  | 0·13·16              |
| >=20         | 359   | 51.60  | 49.13  | 48.89  | 43·30·27             |

62/421동인 20개 미만 집단에서 B의 상위 집단 13/43동, C의 16/43동이 나왔습니다. 10개 미만 12동만 보면 B에서 4동, C에서 6동이 상위 집단에 포함되었습니다. 상계9동·상계8동은 점포 7개로 B·C의 4·5위였습니다. **작은 분모에 민감한 결과는 관찰했지만, 실제 성과 자료 없이 과대평가나 부적합을 확정한 것은 아닙니다.**

공통 집단의 폐업률 실제 0인 99동은 평균 원시 순위 50을 공유합니다. 따라서 증가 방향 `R(0)=49/420`, 감소 방향은 `1-R(0)=371/420`이며, 0이라고 무조건 정규화값 1을 부여하지 않았습니다. 작은 모집단의 폐업률 0과 큰 인구/점포가 함께 점수를 높일 수 있다는 가설을 검증해야 합니다.

### 계산 정의와 산출 불가 조건

**순위 방식**은 [9절 정의](#계산동률검산-기준)를 그대로 사용했습니다. 각 단위의 공통 집단에서 입력의 오름차순 동률 평균 순위를 r이라 할 때 `R(x)=(r−1)/(n−1)`입니다. 감소 방향인 점포 수·폐업률은 `1−R(x)`로 반전합니다.

**혼합 방식**에서 규모형 입력은 당월 매출액 S, 총 유동인구 F, 전체 점포 수 N, 파생지표 S/N·F/N입니다. 각 입력마다 같은 비교 집단 전체를 사용해 아래 순서로 처리합니다.

1. 원본의 비음수 여부와 분모를 확인하고 `y=ln(1+x)`를 계산합니다. 점포당 입력은 원본의 정확한 비율을 먼저 계산한 뒤 log를 적용합니다.
2. **log 변환값의 P05·P95는 선형 보간 분위수(type 7)**입니다. 정렬한 값을 0부터 센 `y[0]…y[n−1]`, `h=(n−1)p`, `j=floor(h)`, `t=h−j`라 하면 `q(p)=(1−t)y[j]+t y[j+1]`입니다. t=0이면 y[j]만 사용합니다. p는 0.05·0.95이며, 원본의 분위수를 구한 뒤 log한 값으로 바꾸지 않습니다.
3. `L=q(0.05)`, `U=q(0.95)`, `W(x)=(min(max(y,L),U)−L)/(U−L)`로 정규화합니다. 원본을 삭제·수정하거나 꼬리 지역을 비교 집단에서 제거하지 않습니다.
4. 점포 수는 `1−W(N)`로 반전합니다. 폐업률은 log·winsor를 적용하지 않고 **원천 폐업률의 `1−R(폐업률)`**을 그대로 사용합니다. 비율의 log 적용은 별도 검토 사항입니다.

n≤1, 필수 입력의 NULL·음수·비유한 값, 분모 0·NULL 또는 필수 규모형 입력의 U=L이면 해당 모델을 산출하지 않고 사유를 남기는 실험 규칙입니다. 임의 중립값이나 자동 비중 재분배로 채우지 않습니다. 어느 모델의 필수 입력이 불가하면 그 모델만 별도 지역 집단으로 다시 비교하지 않고 공통 집단 조건부터 재검토합니다. 이번에는 모든 입력에서 U>L이고 이 중단 조건은 발생하지 않았습니다.

가중치는 9절과 같으며 각 합계는 **1**입니다. 아래에서 Z는 순위 방식에서는 R, 혼합 방식의 규모형 입력에서는 W를 뜻합니다. 폐업률은 두 방식 모두 R입니다.

| 모델 | 점수(0~100)                                                        |
| ---- | ------------------------------------------------------------------ |
| A    | `100 × [0.30 Z(S) + 0.30 Z(F) + 0.20(1−Z(N)) + 0.20(1−R(폐업률))]` |
| B    | `100 × [0.40 Z(S/N) + 0.35 Z(F/N) + 0.25(1−R(폐업률))]`            |
| C    | `100 × [Z(S/N) + Z(F/N) + (1−R(폐업률))] / 3`                      |

최종 점수 순위는 반올림 전 점수의 내림차순 동률 평균 순위입니다. 구·동을 섞거나 모델마다 별도 집단을 사용하지 않습니다.

## 부록: 읽기 전용 재현 SQL

아래 명령과 SQL은 **기존 분석을 재현하기 위한 예시**이며 이번 문서 정리에서는 실행하지 않았습니다. 재실행 결과는 실행 시점의 DB 상태를 반영하므로, 과거 분석 시각의 스냅샷과 구분해야 합니다.

실행할 때는 저장소 루트에서 기존 Compose DB에 접속합니다. 사용자·DB는 컨테이너의 기존 환경변수를 사용하며 비밀번호를 출력하지 않습니다. 이 명령 자체는 접속만 수행하므로, 이후 SQL을 실행하고 반드시 `ROLLBACK`으로 종료합니다.

DB 접근이 불가능한 환경에서는 실행 결과를 추정하지 말고 미실행 사유를 남겨야 합니다.

```sh
docker compose exec db sh -c 'PGOPTIONS="-c default_transaction_read_only=on" psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

아래는 기존 분석의 **커버리지·전체 분포 재현용 SQL**입니다. `raw`를 현행 지역에 LEFT JOIN하므로 없는 행과 NULL 셀을 구분합니다. 최신 적격 경계에 실제 행이 없다면 분모가 사라지므로 정상 분석으로 해석하지 않습니다.

다른 분기·업종을 검토할 때는 `raw`의 여섯 분기 조건과 점포·매출 네 업종 조건을 함께 바꿔야 합니다.

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
SET LOCAL statement_timeout='30s';
SELECT transaction_timestamp(),current_setting('transaction_read_only'),
       current_setting('transaction_isolation');
WITH boundary AS (
 SELECT batch_id FROM etl_batch WHERE dataset_code='SEOUL_DONG_BOUNDARY'
 AND source_type='SHAPEFILE' AND scope_type='SEOUL' AND scope_code IS NULL
 AND status='PUBLISHED' AND published_at IS NOT NULL
 ORDER BY published_at DESC, started_at DESC, batch_id DESC LIMIT 1
), regions AS (
 SELECT 'district'::text AS unit,d.district_code AS code,d.district_name AS name,d.district_code
 FROM district d JOIN boundary b ON d.boundary_batch_id=b.batch_id
 UNION ALL
 SELECT 'dong',a.dong_code,a.dong_name,a.district_code
 FROM administrative_dong a JOIN district d ON d.district_code=a.district_code
 JOIN boundary b ON a.boundary_batch_id=b.batch_id AND d.boundary_batch_id=b.batch_id
), raw AS (
 SELECT 'district'::text AS unit,'store'::text AS kind,s.district_code AS code,
 s.source_batch_id, b.dataset_code,b.source_type,b.scope_type,b.scope_code,b.status,b.published_at,
 to_jsonb(s) AS val,
 (b.dataset_code='SEOUL_DISTRICT_STORE_STAT' AND b.source_type='CSV' AND b.scope_type='SEOUL'
 AND b.scope_code IS NULL AND b.status='PUBLISHED' AND b.published_at IS NOT NULL) AS eligible
 FROM district_store_stat s JOIN etl_batch b ON b.batch_id=s.source_batch_id
 WHERE s.quarter_code='20262' AND s.industry_code='CS100010'
 UNION ALL
 SELECT 'district'::text AS unit,'sales'::text AS kind,s.district_code AS code,
 s.source_batch_id, b.dataset_code,b.source_type,b.scope_type,b.scope_code,b.status,b.published_at,
 to_jsonb(s) AS val,
 (b.dataset_code='SEOUL_DISTRICT_SALES_STAT' AND b.source_type='CSV' AND b.scope_type='SEOUL'
 AND b.scope_code IS NULL AND b.status='PUBLISHED' AND b.published_at IS NOT NULL) AS eligible
 FROM district_sales_stat s JOIN etl_batch b ON b.batch_id=s.source_batch_id
 WHERE s.quarter_code='20262' AND s.industry_code='CS100010'
 UNION ALL
 SELECT 'district'::text AS unit,'foot'::text AS kind,s.district_code AS code,
 s.source_batch_id, b.dataset_code,b.source_type,b.scope_type,b.scope_code,b.status,b.published_at,
 to_jsonb(s) AS val,
 (b.dataset_code='SEOUL_DISTRICT_FOOT_TRAFFIC_STAT' AND b.source_type='CSV' AND b.scope_type='SEOUL'
 AND b.scope_code IS NULL AND b.status='PUBLISHED' AND b.published_at IS NOT NULL) AS eligible
 FROM district_foot_traffic_stat s JOIN etl_batch b ON b.batch_id=s.source_batch_id
 WHERE s.quarter_code='20262'
 UNION ALL
 SELECT 'dong'::text AS unit,'store'::text AS kind,s.dong_code AS code,
 s.source_batch_id, b.dataset_code,b.source_type,b.scope_type,b.scope_code,b.status,b.published_at,
 to_jsonb(s) AS val,
 (b.dataset_code='SEOUL_DONG_STORE_STAT' AND b.source_type='CSV' AND b.scope_type='SEOUL'
 AND b.scope_code IS NULL AND b.status='PUBLISHED' AND b.published_at IS NOT NULL) AS eligible
 FROM dong_store_stat s JOIN etl_batch b ON b.batch_id=s.source_batch_id
 WHERE s.quarter_code='20262' AND s.industry_code='CS100010'
 UNION ALL
 SELECT 'dong'::text AS unit,'sales'::text AS kind,s.dong_code AS code,
 s.source_batch_id, b.dataset_code,b.source_type,b.scope_type,b.scope_code,b.status,b.published_at,
 to_jsonb(s) AS val,
 (b.dataset_code='SEOUL_DONG_SALES_STAT' AND b.source_type='CSV' AND b.scope_type='SEOUL'
 AND b.scope_code IS NULL AND b.status='PUBLISHED' AND b.published_at IS NOT NULL) AS eligible
 FROM dong_sales_stat s JOIN etl_batch b ON b.batch_id=s.source_batch_id
 WHERE s.quarter_code='20262' AND s.industry_code='CS100010'
 UNION ALL
 SELECT 'dong'::text AS unit,'foot'::text AS kind,s.dong_code AS code,
 s.source_batch_id, b.dataset_code,b.source_type,b.scope_type,b.scope_code,b.status,b.published_at,
 to_jsonb(s) AS val,
 (b.dataset_code='SEOUL_DONG_FOOT_TRAFFIC_STAT' AND b.source_type='CSV' AND b.scope_type='SEOUL'
 AND b.scope_code IS NULL AND b.status='PUBLISHED' AND b.published_at IS NOT NULL) AS eligible
 FROM dong_foot_traffic_stat s JOIN etl_batch b ON b.batch_id=s.source_batch_id
 WHERE s.quarter_code='20262'
), wide AS (
 SELECT r.*,s.val AS stores,x.val AS sales,f.val AS foot,
 s.source_batch_id AS store_batch,x.source_batch_id AS sales_batch,f.source_batch_id AS foot_batch
 FROM regions r
 LEFT JOIN raw s ON s.unit=r.unit AND s.code=r.code AND s.kind='store' AND s.eligible
 LEFT JOIN raw x ON x.unit=r.unit AND x.code=r.code AND x.kind='sales' AND x.eligible
 LEFT JOIN raw f ON f.unit=r.unit AND f.code=r.code AND f.kind='foot' AND f.eligible
), metrics AS (
 SELECT w.unit,w.code,w.name,w.district_code,v.kind,v.metric,v.value,v.present
 FROM wide w CROSS JOIN LATERAL (VALUES
 ('store','store_count',(w.stores->>'store_count')::numeric,w.stores IS NOT NULL),
 ('store','general_store_count',(w.stores->>'general_store_count')::numeric,w.stores IS NOT NULL),
 ('store','franchise_store_count',(w.stores->>'franchise_store_count')::numeric,w.stores IS NOT NULL),
 ('store','opened_store_count',(w.stores->>'opened_store_count')::numeric,w.stores IS NOT NULL),
 ('store','closed_store_count',(w.stores->>'closed_store_count')::numeric,w.stores IS NOT NULL),
 ('store','opening_rate',(w.stores->>'opening_rate')::numeric,w.stores IS NOT NULL),
 ('store','closure_rate',(w.stores->>'closure_rate')::numeric,w.stores IS NOT NULL),
 ('sales','monthly_sales_amount',(w.sales->>'monthly_sales_amount')::numeric,w.sales IS NOT NULL),
 ('sales','monthly_sales_count',(w.sales->>'monthly_sales_count')::numeric,w.sales IS NOT NULL),
 ('sales','weekday_sales_amount',(w.sales->>'weekday_sales_amount')::numeric,w.sales IS NOT NULL),
 ('sales','weekend_sales_amount',(w.sales->>'weekend_sales_amount')::numeric,w.sales IS NOT NULL),
 ('foot','total_foot_traffic',(w.foot->>'total_foot_traffic')::numeric,w.foot IS NOT NULL),
 ('foot','male_foot_traffic',(w.foot->>'male_foot_traffic')::numeric,w.foot IS NOT NULL),
 ('foot','female_foot_traffic',(w.foot->>'female_foot_traffic')::numeric,w.foot IS NOT NULL)
 ) v(kind,metric,value,present)
), stat AS (
 SELECT unit,kind,metric,count(*) AS expected,
 count(*) FILTER(WHERE present) AS present_rows,
 count(*) FILTER(WHERE present AND value IS NULL) AS null_cells,
 count(*) FILTER(WHERE NOT present) AS absent_rows,
 count(*) FILTER(WHERE value=0) AS zero_cells,
 count(*) FILTER(WHERE value<0 OR value>='Infinity'::numeric) AS invalid_cells,
 min(value)::text AS min,percentile_disc(0.05) WITHIN GROUP(ORDER BY value)::text AS p05,
 percentile_disc(0.25) WITHIN GROUP(ORDER BY value) AS q1,
 percentile_disc(0.5) WITHIN GROUP(ORDER BY value)::text AS median,
 percentile_disc(0.75) WITHIN GROUP(ORDER BY value) AS q3,
 percentile_disc(0.95) WITHIN GROUP(ORDER BY value)::text AS p95,max(value)::text AS max
 FROM metrics GROUP BY unit,kind,metric
)
SELECT json_build_object('label','profiles','rows',(SELECT json_agg(t) FROM (
 SELECT s.*, (SELECT count(*) FROM metrics m WHERE m.unit=s.unit AND m.metric=s.metric
 AND (m.value<s.q1-1.5*(s.q3-s.q1) OR m.value>s.q3+1.5*(s.q3-s.q1))) AS tukey_outliers
 FROM stat s ORDER BY unit,kind,metric
) t));
ROLLBACK;
```

결측·실제 0·일관성과 파생 분포를 확인하려면 공통 `WITH boundary ... metrics AS (...)` 뒤의 마지막 SELECT를 아래 중 하나로 바꿉니다. 아래 SELECT들은 공통 WITH 없이 단독 실행하는 쿼리가 아닙니다.

각각 위와 같은 읽기 전용 트랜잭션에서 실행하고 `ROLLBACK`으로 종료합니다.

```sql
-- 없는 행과 실제 0을 지역 코드·이름으로 구분합니다.
SELECT unit,code,name,stores,sales,foot
FROM wide
WHERE stores IS NULL OR sales IS NULL OR foot IS NULL
   OR (sales->>'weekday_sales_amount')::numeric=0
   OR (sales->>'weekend_sales_amount')::numeric=0
ORDER BY unit,code;
```

```sql
-- 성별 합계와 총인구의 원천 차이를 보정하지 않고 조사합니다.
SELECT unit,
  count(*) FILTER (WHERE (foot->>'total_foot_traffic')::numeric
    <> (foot->>'male_foot_traffic')::numeric
     + (foot->>'female_foot_traffic')::numeric) AS mismatch_rows,
  min((foot->>'total_foot_traffic')::numeric
     -(foot->>'male_foot_traffic')::numeric
     -(foot->>'female_foot_traffic')::numeric) AS min_delta,
  max((foot->>'total_foot_traffic')::numeric
     -(foot->>'male_foot_traffic')::numeric
     -(foot->>'female_foot_traffic')::numeric) AS max_delta
FROM wide GROUP BY unit;
```

```sql
-- 분모 0·NULL은 나눗셈에서 제외하며, 없는 매출을 0으로 채우지 않습니다.
SELECT unit,v.metric,count(v.value) AS n,min(v.value) AS min,
  percentile_disc(0.5) WITHIN GROUP (ORDER BY v.value) AS median,
  percentile_disc(0.95) WITHIN GROUP (ORDER BY v.value) AS p95,
  max(v.value) AS max
FROM wide
CROSS JOIN LATERAL (VALUES
  ('sales_per_store',(sales->>'monthly_sales_amount')::numeric
    /NULLIF((stores->>'store_count')::numeric,0)),
  ('foot_per_store',(foot->>'total_foot_traffic')::numeric
    /NULLIF((stores->>'store_count')::numeric,0))
) v(metric,value)
GROUP BY unit,v.metric ORDER BY unit,v.metric;
```
