# 구현 로드맵

- [x] CORS와 `/api` 개발 프록시
- [x] 공용 DB Compose·7개 테이블 초기 SQL
- [x] 원본 CSV 6개 배치, 파일 해시·기간·건수 목록
- [x] 원본·비밀값·생성물 Git 제외와 데이터 폴더 `.gitkeep`
- [x] Python ETL 모듈과 입력 검증·선택 실행
- [x] 문서 역할 분리, 기존 실험 코드 보존
- [ ] 실제 PostgreSQL 적재·원본 수치·재실행 검증
- [ ] Spring DB 접근·마이그레이션·통계 API
- [ ] React 서비스 화면

파일·스키마·ETL 코드가 존재하는 것과 서비스 연결 완료를 구분합니다. 전체 기능의 완료율을 임의로 계산하지 않습니다.

## 1차: 행정동 통계를 화면까지 연결

현재 확보한 **행정동 매출·점포** 자료는 행정동 425개와 2025년 4개 분기를 공유합니다. 카페(CS100010)·행정동 2~3곳·공통 분기 하나로 시작합니다. 상권 매출은 별도 자료이며 상권 단위 점포 통계를 확보하기 전 행정동 통계와 직접 결합하지 않습니다. 지도·공간 분석·점수 기능은 1차 범위에 포함하지 않습니다.

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 행정동 매출·점포 선택 적재 및 원본 대조 | 실제 PostgreSQL/PostGIS 적재 결과로 원본 행 수·복합 키(행정동 코드 + 서울시 업종 코드 + 분기)·2025년 4개 분기·대표 샘플 수치를 대조하고 NULL 보존·BIGINT 정밀도·서울시 업종 코드와 내부 업종 매핑 확인 |
| 2 | ETL 재실행·실패 복구 검증 | 동일 입력을 재실행해도 중복 없이 동일 결과 유지, 실제 PostgreSQL 트랜잭션에서 중간 실패를 발생시켜 이전 DB 상태 유지 확인 |
| 3 | Spring DB 접근·마이그레이션 책임 결정 | 공용 PostgreSQL 접근 방식·마이그레이션 도구를 결정하고 `sql/001_schema.sql`과 backend migration의 책임 정리. 동일 스키마의 중복 관리를 피하고 기존 DB 볼륨을 고려한 migration/baseline 전략 검토 |
| 4 | API 계약 확정 | 코드 구현 전에 backend·frontend가 API 경로·요청 파라미터·행정동 코드/서울시 업종 코드/분기 검증·응답 DTO·숫자 범위와 BIGINT 금액의 JSON 표현·NULL 의미·자료 없음 표현·값의 단위·기준 기간·출처 표현 합의 |
| 5 | 행정동·업종·분기 목록과 통계 조회 API 구현 | 실제 PostgreSQL에서 행정동·업종·분기 목록과 매출·점포 통계를 조회하고 값·단위·기준 기간·출처·결측 또는 자료 없음 사유 반환, 정상·오류·자료 없음 케이스 테스트 통과 |
| 6 | React 조건 선택과 결과 표 | 실제 Spring API에 연결해 행정동·업종·분기 선택과 통계 결과 표시, 로딩·오류·자료 없음 상태 처리 |
| 7 | 공통 4개 분기 추세와 vertical slice 재현 | 카페 `CS100010`·행정동 2~3곳의 2025년 공통 4개 분기 추세를 표시하고 `CSV → ETL → PostgreSQL → Spring API → React` 전체 흐름에서 데이터 일치 확인, 다른 팀원이 새 환경에서 같은 흐름을 재현하도록 문서화 |

1·2단계는 ETL 코드나 mock 테스트의 존재·통과만으로 완료하지 않습니다. fake/mock connection 테스트는 실제 DB rollback 검증을 대신하지 않습니다.

3단계에서는 API가 출처·기간 메타데이터를 제공할 방식, 1차에 필요한 최소 dataset metadata의 DB 관리 필요 여부, 상세 적재 이력·스냅샷 버전 관리와 이후 단계의 연결 방안을 함께 검토합니다. 사용자 API 요청 중 원본 CSV를 직접 읽지 않으며 React는 DB에 직접 접근하지 않습니다. 결측은 임의로 0으로 바꾸지 않습니다.

## 2차: 지도·경쟁 점포·후보 비교

- [ ] 상권 좌표계의 원천 메타데이터 확인과 변환 검산
- [ ] 통계 버전과 호환되는 Polygon 경계 확보
- [ ] 소상공인 코드 → 내부 업종 매핑 검증
- [ ] 점포 기준일·데이터 버전·적재 이력 DB 관리
- [ ] 미터 단위 반경 조회 및 공간 인덱스 검증
- [ ] 지도 SDK 선택, 위치 선택·점포·기준 경계 표시
- [ ] 최대 3곳을 같은 조건·기간·버전으로 비교
- [ ] 후보지 2~3곳의 공간 결과 수작업 검산

현재 서울시 전체 인구 22행은 위치별 수요 자료로 사용할 수 없습니다. 지도 기능에 필요한 경계도 현재 ZIP에 없습니다.

| 단계 | 도입 자료·기능 | 완료 기준 |

| 4-1차 | 상주·직장인구 | 원천 갱신·반복 값·중복 합산 정책 검증 |

자료마다 원본 확인 → 저장 규칙·마이그레이션 → ETL 검증·적재 → API → 화면 순서를 반복합니다. 최신 4~8개 분기 확대는 자료별 공통 기간과 경계 호환성을 확인한 뒤 진행합니다.

## 공통 완료 기준

- 입력 행 수 = 유효 행 수 + 제외 행 수를 대조하고 제외 사유 기록
- 출처·파일 해시·원본 기준 기간·적재 시각·공간 버전 구분
- 중복·잘못된 좌표·지역 연결 실패 처리 검증
- 정정 파일 반영 범위와 실패 시 기존 자료 유지 검증
- 추정매출을 실제 창업 수익 예측으로 표시하지 않음
- 미지원 지역·누락 자료에 대한 API·화면 정책 일치
- 새 환경에서 DB 준비·적재·서버 실행 재현

## 작업 분담과 기존 코드 정리

Backend는 조회·분석 API와 스키마 변경 이력, ETL은 원본 입력·정제·품질·적재, frontend는 단계별 조건·결과·상태 표시를 담당합니다. 열·키·단위·버전과 API 요청·응답 형식은 함께 합의합니다.

기존 코드는 `legacy/csv_server/`에 보존했습니다. 필요한 자료·설계 이전과 새 흐름의 검증이 끝난 후 별도 변경으로 제거합니다. 기존 DB 볼륨·자료는 백업과 보존 여부 확인 없이 삭제하지 않습니다.
