## 1차: 행정동 통계를 화면까지 연결

현재 확보한 **행정동 매출·점포** 자료는 행정동 425개와 2025년 4개 분기를 공유합니다. 카페(CS100010)·행정동 2~3곳·공통 분기 하나로 시작합니다. 상권 매출은 별도 자료이며 상권 단위 점포 통계를 확보하기 전 행정동 통계와 직접 결합하지 않습니다. 지도·공간 분석·점수 기능은 1차 범위에 포함하지 않습니다.

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 행정동 매출·점포 선택 적재 및 원본 대조 | 실제 PostgreSQL/PostGIS 적재 결과로 원본 행 수·복합 키(행정동 코드 + 서울시 업종 코드 + 분기)·2025년 4개 분기·대표 샘플 수치를 대조하고 NULL 보존·BIGINT 정밀도·서울시 업종 코드와 내부 업종 매핑 확인 |
| 2 | ETL 재실행·실패 복구 검증 | 동일 입력을 재실행해도 중복 없이 동일 결과 유지, 실제 PostgreSQL 트랜잭션에서 중간 실패를 발생시켜 이전 DB 상태 유지 확인 |
| 3 | Spring DB 접근·마이그레이션 책임 결정 | 공용 PostgreSQL 접근 방식·마이그레이션 도구를 결정하고 `sql/001_schema.sql`과 backend migration의 책임 정리. 동일 스키마의 중복 관리를 피하고 기존 DB 볼륨을 고려한 migration/baseline 전략 검토 |
| 4 | API 계약 확정 | 코드 구현 전에 API 경로·요청 파라미터·행정동 코드/내부 업종 코드와 서울시 원본 매핑/분기 검증·응답 구조·숫자 범위와 BIGINT 금액의 JSON 표현·NULL 의미·자료 없음 표현·값의 단위·기준 기간·출처 제공 범위 확정 |
| 5 | 행정동·업종·분기 목록과 통계 조회 API 구현 | 실제 PostgreSQL에서 계약에 따른 행정동·업종·분기 목록과 매출·점포 통계를 조회하고 값·단위·기준 기간·결측 또는 자료 없음 사유 제공, 정상·오류·자료 없음 케이스 테스트 통과. 출처·버전 응답은 계약의 metadata 유예 범위 적용 |
| 6 | React 조건 선택과 결과 표 | 실제 Spring API에 연결해 행정동·업종·분기 선택과 통계 결과 표시, 로딩·오류·자료 없음 상태 처리 |
| 7 | 공통 4개 분기 추세와 vertical slice 재현 | 카페 내부 업종 `CAFE`(서울시 `CS100010` 매핑)·행정동 2~3곳의 2025년 공통 4개 분기 추세를 표시하고 `CSV → ETL → PostgreSQL → Spring API → React` 전체 흐름에서 데이터 일치 확인, 다른 팀원이 새 환경에서 같은 흐름을 재현하도록 문서화 |

1·2단계는 ETL 코드나 mock 테스트의 존재·통과만으로 완료하지 않습니다. fake/mock connection 테스트는 실제 DB rollback 검증을 대신하지 않습니다.

1·2단계는 2026-10-03에 실제 DB로 검증했습니다([결과와 검증 범위](project-status.md)). 원본에 빈 필드가 없어 NULL 보존은 별도 임시 CSV로 확인했으며, 재실행은 내부 `id`를 제외한 복합 키·통계 값 기준으로 동일합니다.

3단계도 2026-10-03에 완료했습니다. JdbcClient·Flyway를 선택하고 초기 SQL을 backend V1로 이전했습니다. 기존 DB는 V1 대조 후 baseline 1로 편입했고 데이터 보존·Spring 조회를 확인했습니다. 별도 임시 DB에서 Spring 없이 migration 및 Spring 연결을 검증했습니다.

4단계는 [행정동 API 계약](api-contract.md)으로 확정했습니다. 내부 업종 code·문자열 분기·BIGINT 문자열, 통계 부분별 NO_ROW와 metric NULL, 공통 오류를 결정하고 실제 DB와 예시를 대조했습니다. 첫 조회는 DB의 분기를 제공하며 출처·dataset version 응답은 후속 metadata 관리로 유예합니다. 5단계의 목록·통계 조회 API도 실제 PostgreSQL과 Spring MVC/HTTP로 검증했습니다. 6단계 React 조건 선택·결과 표와 7단계 추세·새 환경 재현까지 완료했으며, 다음은 2차 공간 데이터 검증입니다.

5단계는 네 GET API·JdbcClient 조회·strict query·정상/부분·전체 NO_ROW·BIGINT 문자열·NULL/0·무결성 오류 처리를 검증했습니다. 일반 테스트 33개, populated DB 테스트 16개, 격리 DB 경계값 테스트 10개, 실제 HTTP 요청 8개가 통과했고 기존 DB 건수·전체 행 checksum·Flyway 이력이 유지됐습니다([검증 결과](project-status.md)). API 계약·V1·ETL·React는 변경하지 않았습니다.

6단계는 2026-10-04에 완료했습니다. React core·Vanilla CSS로 세 조건 선택과 점포/추정매출 표를 구현했습니다. lookup·통계 로딩/오류, network 실패, NULL/0, 부분·전체 NO_ROW, BIGINT 정밀도와 요청 취소를 자동 테스트하고 lint·build를 통과했습니다. 브라우저에서 Vite `/api` 프록시 → Spring → PostgreSQL의 정상·부분/전체 NO_ROW와 오류/재시도·기본 반응형을 확인했으며 기존 DB checksum·Flyway 이력은 유지됐습니다([검증 결과](project-status.md)). 지도·추세·metadata UI는 구현하지 않았습니다.

7단계는 2026-10-07에 완료했습니다. 고정 2025년 4분기 API·Frontend semantic table과 기존 선택 분기 상세 조회를 유지하고, clean tracked checkout·별도 fresh PostgreSQL volume·V1 SQL migration에서 CSV → ETL → PostgreSQL → Spring API → React를 처음부터 재현했습니다. 원본 9개 metric의 4분기 값과 실제 화면을 대조하고 Backend/Frontend 테스트·대표 정상/NO_ROW·390px/1280px를 검증했으며 기존 개발 DB는 보존했습니다. 팀원 절차는 [새 환경 재현 안내](reproduction.md), 실제 결과는 [검증 기록](project-status.md#2026-10-07-새-환경-vertical-slice-재현)에 있습니다. Chart·지도·metadata는 별도 후속 범위입니다.

3단계에서 출처·기간 메타데이터의 제공 경로와 DB 관리 필요 여부, 상세 적재 이력·스냅샷 버전 관리의 후속 연결을 검토했습니다([설계와 남은 결정](architecture.md)). 최소 dataset metadata 테이블은 아직 도입하지 않았습니다. 사용자 API 요청 중 원본 CSV를 직접 읽지 않으며 React는 DB에 직접 접근하지 않습니다. 결측은 임의로 0으로 바꾸지 않습니다.

## 2차: 공간 데이터 검증 후 지도·경쟁 점포·후보 비교

2026-10-07에는 공식 CRS 메타데이터 확인에 이어 대표 8점의 변환/의미 검산과 공식 행정동 ZIP 확보·파일 검사를 수행했습니다. 전체 1,650점의 변환 sanity·독립 투영 수치도 통과했지만 추가 참조 대조 예외 1건을 발견했습니다. 통계/경계의 코드·이름 425개는 일치하나 2025 참조 경계/재집계에 대한 공식 근거 부족으로 **B 판정**, 4단계는 미완료입니다([실제 결과](project-status.md#2026-10-07-공간-데이터-24단계-실제-검증)). 후속 조사에서 현재 공식 영역/점포/매출 CSV와 보관 파일의 byte·SHA 동일성은 확인했으나 참조 경계 정책은 찾지 못했고, 홍지문은 현재 CSV/SHP의 행정동 귀속 차이를 확인한 **H5**입니다([조사 기록](project-status.md#2026-10-07-공간-검증-4단계-미완료-원인-조사)). 작은 면적 중첩 13쌍은 공간 판정 정책·geometry 정밀도 기준 설계 전에 별도로 검토합니다. 최초 배포 이력과 소상공인 업종 매핑도 미확인입니다.

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 (완료) | 상권 공식 데이터셋 CRS 메타데이터 확인 | 현재 서울 열린데이터광장 영역-상권 OA-15560 본문에서 EPSG:5181 명시 확인; URL·확인일 기록. 보관 CSV의 배포 버전/현재 제공 파일과의 동일성 확인·실제 좌표 검산과 구분 |
| 2 (완료: 대표 샘플 범위) | EPSG:5181 → EPSG:4326 대표 좌표 수작업 검산 | 고정 8점의 원본 코드/X/Y·변환 좌표·공식 행정동 포함 대조, 전체 1,650점의 sanity·독립 PyGeodesy 수치 비교 완료; 추가 참조 예외 홍지문 1점은 원인 미확인, 전체 참조 정합성 보증은 제외 |
| 3 (완료: 원본 확보) | 행정동 Polygon 원본 확보 | OA-22160 공식 ZIP·SHA·provenance·CRS/축 선언·UTF-8 schema·425개 Polygon 확인; 실제 경계 기준 시점/버전은 미확인으로 4단계에서 확인 |
| 4 (미완료) | 행정동 Polygon과 2025 통계 정합성 검증 | geometry valid 425·코드/이름·네 분기 대조 완료, 차집합/이름 불일치 0. 현재 공식 2025 점포·매출 ZIP도 이전 행정동 코드를 유지하지만 표준단위구역 → 행정동 환산/재집계·참조 기준일과 OA-22160 geometry의 연결 근거가 부족해 B/unresolved 유지. 작은 면적 중첩 13쌍은 공간 판정 정책·정밀도 기준 설계 전에 별도 검토 |
| 5 | 상권 Polygon 확보 및 정합성 검증 | 별도 경계를 영역 1,650개·매출 1,577개 상권 코드/이름과 대조하고 통계·경계 버전 호환성 확인 |
| 6 | 소상공인 개별 점포 업종 매핑 검증 | CAFE부터 공식 분류와 실제 소분류 코드/명칭 분포·포함/제외 기준을 대조하고 SEOUL/SEMAS 분리 검증; 추측 코드 등록 금지 |
| 7 | 공간 스키마·Flyway migration 설계 | 검증 결과를 보고 대표 POINT/경계 분리·코드/버전 연결·점포 기준일·출처/적재 이력·기존 DB 보존 전략 결정 |
| 8 | Polygon ETL·공간 인덱스 | 승인된 설계의 migration과 ETL을 별도 구현하고 geometry·SRID·행 수·실패 복구·인덱스 검증 |
| 9 | 후보 좌표 → 행정동/상권 판정 API | 검증된 경계로 코드 결정, 기존 행정동 stats/trend 연결; 경계선·중첩·미지원 결과와 후보 2~3곳 수작업 대조 |
| 10 | 300m/500m/1km 경쟁 점포 반경 조회 | 검증된 점포 업종 매핑·미터 단위 거리/인덱스·대표 결과 검산; 2025 통계와 2026-06 스냅샷 시점 구분, 스냅샷 누락을 폐업으로 판정하지 않음 |
| 11 | 지도 SDK 선택·지도 UI | 데이터/API 검증 이후 위치 선택·점포·경계·각 자료의 기간/버전 표시 |
| 12 | 최대 3개 후보 비교 | 같은 업종·반경·통계 분기·점포 스냅샷·경계 버전으로 비교하고 후보별 결과 수작업 대조 |

다음은 **제공기관의 공식 설명/과업 원문에서 실제 경계 기준 시점·2025 통계 참조 경계/분동 반영·재집계 정책 확인**과 홍지문 대표점/행정동 귀속 정의·현재 CSV/SHP 차이의 이유 확인입니다. 작은 면적 중첩 13쌍은 향후 point-in-polygon 경계/다중 매칭 정책과 geometry 정밀도 기준 설계 전에 별도로 검토합니다. 경계 버전 근거를 검토하기 전 공간 스키마·Flyway V2·ETL 적재·공간 API·지도 UI로 넘어가지 않습니다. 행정동 Polygon 우선 정책과 5~12단계의 순서는 유지합니다([공간 설계 정책](architecture.md#공간-기준)).

현재 서울시 전체 인구 22행은 위치별 수요 자료로 사용할 수 없습니다. 공식 행정동 경계와 후속 홍지문 조사용 공식 상권 ZIP은 별도 Git 제외 로컬 공간에 확보했습니다. 상권 전체 코드/이름·geometry·통계 버전 정합성은 미검증이므로 5단계 완료를 뜻하지 않습니다.

자료마다 원본 확인 → 저장 규칙·마이그레이션 → ETL 검증·적재 → API → 화면 순서를 반복합니다. 최신 4~8개 분기 확대는 자료별 공통 기간과 경계 호환성을 확인한 뒤 진행합니다.

## 공통 완료 기준

- 입력 행 수 = 유효 행 수 + 제외 행 수를 대조하고 제외 사유 기록
- 출처·파일 해시·원본 기준 기간·적재 시각·공간 버전 구분
- 중복·잘못된 좌표·지역 연결 실패 처리 검증
- 정정 파일 반영 범위와 실패 시 기존 자료 유지 검증
- 추정매출을 실제 창업 수익 예측으로 표시하지 않음
- 미지원 지역·누락 자료에 대한 API·화면 정책 일치
- 새 환경에서 DB 준비·적재·서버 실행 재현

## 작업 분담과 기존 코드 정리

Backend는 조회·분석 API와 스키마 변경 이력, ETL은 원본 입력·정제·품질·적재, frontend는 단계별 조건·결과·상태 표시를 담당합니다. 열·키·단위·버전과 API 요청·응답 형식은 함께 합의합니다.

기존 코드는 `legacy/csv_server/`에 보존했습니다. 필요한 자료·설계 이전과 새 흐름의 검증이 끝난 후 별도 변경으로 제거합니다. 기존 DB 볼륨·자료는 백업과 보존 여부 확인 없이 삭제하지 않습니다.
