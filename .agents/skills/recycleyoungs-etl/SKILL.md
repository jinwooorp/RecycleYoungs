# RecycleYoungs ETL

1. 대상 자료와 작업 목적을 먼저 확인한다. 저장소 루트 기준으로 명령 분기는 `etl/src/cli/`, 자료별 처리는 `etl/src/domains/`, 여러 단계를 잇는 처리는 `etl/src/workflows/`에서 찾는다. [ETL 가이드](../../../docs/ETL.md)와 CLI 도움말에서 해당 자료의 옵션·출처 조건을 확인한다.
2. 실행 전에 외부 요청 여부와 DB 접근 여부를 각각 확인한다.

   | 모드 | 확인할 범위 |
   | --- | --- |
   | 로컬 파일 전용 검사 | 해당 명령의 파일 검사 옵션을 사용한다. 파일만 검사하는 경우에는 외부 API 요청이나 DB 연결이 없다. |
   | 외부 API 검사 | 서울시 통계의 `--api --probe`와 카페 API의 `cafes --probe`는 네트워크 요청을 보낸다. 실제 키 전송 전에 대상 주소·전송 방식·호출 범위에 대한 승인을 받는다. 평문 HTTP가 필요한 경우 노출 위험을 설명한다. CLI 옵션의 지정 자체는 승인이 아니다. |
   | 읽기 전용 DB 대조 | 자치구별 길 단위 유동인구의 `--compare-db`는 로컬 게시 DB를 읽는다. API 검사와 함께 지정하면 외부 요청과 DB 읽기가 모두 일어난다. 읽기 대상과 필요한 CSV를 확인한다. |
   | DB 게시 | 대상 로컬 DB·백업·쓰기 범위를 확인하고 별도 승인을 받는다. 승인된 API 검사나 파일 검사는 게시 승인까지 포함하지 않는다. |

   [전송과 인증 조건](../../../docs/ETL.md#전송과-인증-조건) · [검사와 게시에 쓰는 인자](../../../docs/ETL.md#검사와-게시에-쓰는-인자)
3. 게시 전 원천 자료의 판본과 범위, 건수, 필수 대조, 마이그레이션과 기준 데이터를 확인한다. 대상이나 승인 범위가 불명확하면 해당 작업을 멈춘다. 검사 오류, 필수 대조 불일치, 대상 DB 검증 실패가 있으면 게시를 보류한다. 원인 조사에는 합성 입력이나 격리 DB를 우선 사용한다.
4. `etl/`에서 `npm run dev -- --help`로 사용법을 확인하고, 코드 변경은 `npm test -- 파일경로`로 관련 테스트부터 실행한다. DB가 필요하면 [ETL 격리 DB 통합 테스트](../../../docs/TESTING.md#etl-격리-db-통합-테스트)의 대상 플래그와 테스트 파일을 선택한다. 실제 게시 후에는 배치 상태·건수·범위·출처·체크섬을 [게시 결과 확인](../../../docs/ETL.md#게시-결과-확인)에 따라 대조한다. 재실행 검증은 승인된 범위에서만 수행하고, 확인한 범위와 남은 차이를 인증정보 없이 보고한다.
